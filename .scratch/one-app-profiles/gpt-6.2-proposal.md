**Design decision.** One Wind sign-in opens a personal workspace. Ride, Send and Shop are things a customer does. Captain and each named shop are workspaces the same person can enter from Account. The route, order number, status, proof and receipt stay recognizable across services. [proposal]

## 2. Identity and mode

[proposal] Keep one personal profile in the ONE-01 sense: verified contact and settings belong to the person. “Switch profile” is the UI for entering a workspace backed by a distinct server capability. Buying from shops uses Customer. Running a shop uses that shop's named workspace. Update the SRS wording and ACC/MER acceptance alongside implementation so personal profile and active workspace have explicit meanings. [source docs/requirements/SRS-2026-11-16-wind-one-app.md:102] [source docs/requirements/SRS-2026-11-16-wind-one-app.md:176] [source docs/requirements/SRS-2026-11-16-wind-one-app.md:366]

| Workspace | Creation and states |
|---|---|
| **Customer · شخصي** | Present for every personal account. Password or existing Entra flow signs in the person. Maintain existing contact, block, deletion and recovery policy. A global account block disables all access, while a captain or shop restriction applies to that capability. [proposal] |
| **Captain · كابتن** | Account → Switch profile → Become a captain. Save and resume vehicle, plate where required, towns, requested lines and document checklist. Submit once. Account shows Under review, Action needed with reviewer reason, Approved, or Paused with next action. Approval grants only the reviewed lines. Document submission uses the gated private channel when configured and an operations appointment when unavailable. [proposal] [source docs/requirements/SRS-2026-11-16-wind-one-app.md:183] |
| **Named shop · اسم المحل** | Account → Switch profile → Open a shop. Reuse existing merchant application and admin review, collect pin, contact, category, hours, trade licence/expiry and approved payout setup. Keep draft/under review/action needed visible beside the store name. Before publication require approval, valid licence, published hours and at least one available item. Keep each approved branch as its own mode. Launch with one shop per owner and add the second-shop application only after ownership/settlement isolation is verified. [proposal] [source server/domain/shop.ts:166] [source docs/requirements/SRS-2026-11-16-wind-one-app.md:374] |
| **Admin** | Operator enrollment and existing scoped staff authority. Keep the operator console outside the personal switcher and the mode-switch API unavailable to operator sessions. ### Switcher and continuity

- [proposal] Account's top identity card is one large Switch profile control with avatar, current workspace and chevron. Tapping the workspace header is a shortcut to the same sheet. The sheet shows Personal, Captain and shop names with town if needed, current checkmark, availability/review text and actionable counts for other workspaces. Example `Al Amana Bakery · 2 new orders`. Count actions the user can take, such as a consent request, review decision or new shop order. Use a labeled dot on Account when another workspace needs attention. Keep badge counts free of order/customer details.
- [proposal] One tap on an available row requests a switch. Keep focus in the sheet while switching, then land at that workspace's Home and announce its name. Pending or paused rows open the permitted status/setup screen and explain the next action. Show Become a captain and Open a shop in an Add profile section. Keep Edit personal details in Account settings. Workspaces change identity header, tabs and primary actions while retaining Wind's base colors and type.
- [proposal] Remember the last **server-confirmed** workspace per session/device. Restore it through a valid server bootstrap. New sign-ins default to Personal, except a migrated old captain session keeps its work context. If an entitlement was revoked, show why and route to the appropriate status view or Personal. Returning to Captain starts offline unless an already validated active assignment must resume. Cache customer drafts and cart for the person and shop drafts per shop. Back restores only a still-authorized route.
- [proposal] Switching off Captain while idle means going offline first. Serialize exit with job acceptance and assignment. The server ends the current shift lease and rejects newer dispatch/location from an old generation. The phone stops the foreground-service task, location watchers and pending uploads and discards unneeded buffered fixes. Show the new workspace only after switch receipt/reconciliation, and complete local teardown before rendering it. Retry teardown on foreground/restart. “Use my location” in Customer is a distinct, user-initiated pickup fix.
- [proposal] A live captain assignment blocks leaving Captain, including assigned, at pickup, in transit, on hold, returning and handed-over custody. Show “Finish your current job to switch” with Resume job. Offer a support or permitted release path from the job, never inline silent release. On other sessions the same person can read their authorized Customer activity, but their Customer Ride create is denied during captain work, and they cannot accept or be assigned their own order. Shop work stays live across switches. If new/unfinished orders exist, show their count and require Continue once on exit, without closing the shop; provide Pause new orders separately.
- [proposal] Route push and in-app attention by event class plus target workspace and entity. Show recipient-safe notification text with order/service or shop name. A tap stages the notification, hydrates the session, verifies the current membership and object on the server, then prompts to switch when needed. If Captain is locked, keep the event in Account with its count. Expired or revoked events land on a safe status view. Keep polling and in-app alerts through the provider gate; avoid treating denials and duplicates as state transitions. ## 4. Scenario flows

### 4.1 First launch

1. [proposal] A short Wind launch frame yields to Home. New users can browse local towns, choose language and start a local draft. Returning users see the confirmed workspace and cached active-order summary while the session refreshes.
2. [proposal] Ask for GPS only from Use my location on the pickup step. Present Search, Saved places when any exist, and Pin with landmark as peers. Denial or no fix keeps the text path available. City-only search results stay approximate until the user records an exact place.
3. [proposal] At first request, open a single sign-in/create-account sheet and resume the draft on success. Retain the existing password, consent and pilot contact requirements until a separate account-policy decision changes them. Show optional setup only after returning to the draft. If the phone is already registered, preserve the draft and offer sign-in/recovery, subject to the server's existing response policy. A gated SMS provider cannot be assumed. [source server/main.ts:890] [source docs/requirements/SRS-2026-11-16-wind-one-app.md:176]

### 4.2 Private ride now

1. [proposal] Home → Where to? → select saved place or search. Default to one rider and Now. Show the proposed pickup inline if a fresh enough location or confirmed saved place is available. A town result opens the shared pin/landmark sheet. Verify service area for both ends.
2. [proposal] Review the route, rider count, ETA range, private fare and “Cash to the captain at drop-off. Bring exact change if you can.” The confirm button includes the server total. Use the single booking state machine and a captured quote. If the fare changes or route is unavailable, keep the route and require fresh consent to the new fare. Surface Later only as a secondary option when a slot exists.
3. [proposal] Request → Finding a captain after the server confirms. Keep support and free cancellation visible when allowed. When matched, show plate, vehicle, pickup landmark and call/chat. At drop-off pay, then give the trip code. The captain submits it with the payment/completion command. A locked code uses support and the audited reset. The order ends with the shared receipt. [source docs/requirements/SRS-2026-11-16-wind-one-app.md:221] [source docs/requirements/SRS-2026-11-16-wind-one-app.md:618]
4. [proposal] If the person already has an active ride, open it with “You already have a ride” and an explicit action. Other parcel and shop orders stay available in Orders. [source docs/requirements/SRS-2026-11-16-wind-one-app.md:145] [source server/main.ts:1863]

### 4.3 Shared seats between towns

1. [proposal] Home → Ride → two towns/pins → Private or Shared seats on the review sheet only where enabled. Show “₪ per seat”, the party total, your meeting point, and a plain-language explanation that other riders and parcels can be picked up along the way. Use the tariff and server-approved capacity. Keep one booker and one order for the party. [source docs/requirements/SRS-2026-11-16-wind-one-app.md:617]
2. [proposal] Set seat count → check route range and cash → Request → track. If the last seat was taken, offer a fresh shared match, a private quote or Later where available. Require explicit confirmation for a different fare or service. Preserve the trip code and free cancellation rules per state.
3. [proposal] Captain → Jobs → Heading to Nablus. Show eligible passing parcels and shared riders under one board, with added pickup time where reliable and current run-sheet stops. The server uses the heading corridor, service/vehicle scope, remaining seats, parcel limits and cash exposure. Private rides, freight and shop stay exclusive. Riders see their own trip and a shared-run delay, with other parties' details omitted. Keep admission atomic for capacity across all paths. ### 4.4 Send a parcel to a recipient without Wind

Keep prohibited-item acknowledgement next to Request, show amount/payer before Request and ask to correct a refused destination or contact inline. 2. [proposal] Once the order exists, show Share with recipient as the single next action. Prepare a WhatsApp/SMS share with minimal tracking information using the recipient's normalized international number and the sender's explicit send. The view-only link works in a browser with no sign-in, expires or can be revoked, and shows status/ETA and a way to reach support. Deliver the separate handoff code privately to the intended recipient by message or direct contact. The public URL and generic track page carry no proof secret. Use automated SMS only once its provider and authority are ready. Failed proof shows remaining attempts and audited support reset. If absent/unreachable, call or use the active-order help flow. Record the typed failure and hand the reattempt/return decision to support according to custody rules. Update the same order for sender and recipient. No failed-delivery cash collection.
