# WP12 backend: courier/freight resource contracts and private objects, storage off

Migration 15 (`server/db/postgres-resource-scope.sql`, registered in `server/db/postgres-schema.ts` after verifying 14 was the maximum) adds five PostgreSQL-only tables, allowlisted for legacy import in `server/migrate.ts` (`NON_LEGACY_TABLES` plus the auxiliary table list). `order_declared_scope` holds one customer-declared contract per parcel/freight order: item count, per-piece dimensions (length/width/height mm), mass grams, summed bounding volume cm3, declared value in ILS minor units, freight equipment needs, crew count, loading window, access constraints, and promised pickup/dropoff windows, with a revision counter and an optional merchant `source_ref`. `custody_records` (`collected`/`handed`/`returned` with actor, role and server time) and `order_scope_checks` (driver-reported actual load at pickup) are append-only under the existing `wp05_append_only` trigger. `private_objects` and `private_object_reads` back the coded-but-off evidence store. `quotes` gains a nullable `declared_scope` JSONB column. SQLite gains no tables or columns and the frozen SQLite schema is unchanged: every WP12 route returns `409 scope_unavailable` (objects: `409 objects_unavailable`) there.

Declared scope is a contract, never a measurement. Validation (`validateDeclaredScope` in `server/domain/resource-scope.ts`) rejects negative or overflowing dimensions/mass/value, partial dimension triples, volume that disagrees with the summed per-piece bounding volume (the WP05 measured-cm3 rule), freight fields on parcels, and missing freight crew/loading data; nothing invents dimensions for an order that has none. Volume is always recomputed server-side. The merchant reference follows the `partner_orders` pattern: `source_ref` carries a unique index as the atomic claim, a replay with the same payload returns the committed row without a new revision, and the same reference with a different payload fails `409 idempotency_conflict`, including the loser of a concurrent insert race (23505 re-read).

Booking and quotes accept `declaredScope` additively. `POST /api/price` validates and stores it on the immutable quote; a quote-bound booking must match it (`409 itinerary_changed`) and commits it with the order in the same transaction; a legacy booking commits it directly, and on SQLite a scoped booking is gated `409 scope_unavailable` rather than silently dropped. Order serialization gains the additive `declaredScope` object only when a row exists (customer owner, assigned driver, searching drivers evaluating the job, and admins; never foreign accounts). Precedence is explicit in code (`Eligibility.guard`, `ResourceScope.effective`): an operator-measured `order_requirements` row always wins over declared scope when both exist; declared data never overwrites a measurement.

`Eligibility.guard` reserves capacity from declared scope only when no measured row exists. The declared certificate reuses the measured math — pieces/grams/cm3 sums, fixed-axes packing, piece caps, equipment subset, stop windows — with freight access constraints enforced as equipment needs and freight crew enforced through the existing seats check, all in the existing error vocabulary (`measured_capacity_exceeded`, `equipment_unavailable`, `seats_unavailable`, `dimensions_unavailable`, `stop_window_infeasible`). Declared reservations hold until the pickup instant (declared scope carries no route duration) while the promised dropoff bound is still enforced; a declared order with no promised bound cannot be reserved. Coverage for declared orders is proven from confirmed pickup/dropoff points inside approved areas on an approved route permission (`coverageDeclared`, same permit checks; no corridor geometry is invented), and operator approach attestation now binds to the effective revision (measured, else declared). Acceptance still reserves the full planned load including accepted pickups: `capacity_reservations` and per-stop `capacity_stops` deltas are written at acceptance, before any pickup. Migration 15 also replaces `wp05_assignment_guard` with a version that accepts the declared certificate as a second canonical reservation (same tuple, revision, equipment, dimension and aggregate checks); every measured check is unchanged, so a direct SQL writer cannot bypass declared capacity either.

A pickup mismatch pauses the job on existing machinery. `POST /api/orders/:id/pickup-check` (matched driver at `at_pickup`) compares the reported actual load with the effective scope; any exceedance writes an append-only `order_scope_checks` row, moves the order to `on_hold` with `exception_reason='scope_mismatch'`, and audits `PICKUP_SCOPE_MISMATCH`. Resolution is one of three recorded paths back to `at_pickup`: customer-approved scope change (the customer revises the declaration to cover the actual load), inspected capacity (an admin confirms the actual load still fits the assigned vehicle alongside its other reserved load), or support exception (an admin with a reason of at least five characters, audited as `SCOPE_RESOLVED`). No mismatch, scope or resolution path writes price, commission or cash rows — there is no driver-added fee, and `newWaitingFeeMinor`/`newCancellationFeeMinor` remain 0. Legacy unknown size keeps the inspection gate: with neither measured nor declared scope, acceptance and pickup checks fail `measured_requirements_missing` and no dimensions are invented.

Freight keeps the negotiated-offer flow untouched — the 50%–200% band and 600-second negotiated life (`negotiatedOfferSeconds`) are a different object from WP10's 15-second dispatch offers, and neither was merged or retimed. Declared equipment/crew/access validation now runs inside `Eligibility.guard` on both the driver-offer and customer-acceptance paths, so a vehicle/equipment mismatch is rejected with `equipment_unavailable` (crew beyond the cab with `seats_unavailable`) before any assignment. Promised loading/dropoff windows are recorded on the scope row and serialized as data; no ML or routing behaviour changed.

Private objects are coded-but-off in `server/domain/private-objects.ts`, following the native-push/phone-provider shape: an injectable store and scanner behind a configuration gate. Authorization is per order and per purpose (`condition-photo`, `signature`, `document` — driver ID scans are never a purpose); only the customer owner, the assigned driver, or an admin may upload or read, and other accounts get `403`. Uploads enforce the purpose content-type allowlist, the adapter size cap (`PRIVATE_OBJECT_MAX_BYTES = 10_240`, bounded by the installed JSON body limit; direct-to-Blob upload replaces it when real storage exists), and a client-supplied SHA-256 that must match the decoded bytes (`checksum_mismatch`). Objects start quarantined as `pending` and move through the injectable scanner to `clean` or `rejected` (deterministic fake in tests); only clean objects are readable. Reads require a five-minute, subject-bound grant stored as a token hash (`private_object_reads`); expired grants return `read_expired`, guessed IDs without a grant `read_invalid`, and purpose-based retention (`condition-photo` 90 days, `signature`/`document` 365 days) is recorded at upload. Without Blob configuration — no connection string exists in staging, and no Azure transport is claimed — every operation returns `409 objects_unavailable` on both backends. An upload writes no order or custody row and can never complete a handover; no client photo/signature UI was activated.

## API contract

New additive routes, registered only through `docs/implementation/contracts/additive-endpoints.json`: `POST /api/orders/:id/scope` (customer owner or admin; `400 invalid_input`, `403 forbidden` for drivers, `404 not_found`, `409 scope_unavailable`, `409 order_changed`, `409 idempotency_conflict`), `GET /api/orders/:id/scope` (participants and searching drivers), `POST /api/orders/:id/custody` (`409 custody_unavailable` before assignment), `POST /api/orders/:id/pickup-check` (matched driver; `409 cannot_check_pickup`, `409 safety_hold`, `409 measured_requirements_missing`), `POST /api/orders/:id/scope/resolve` (admin; `action: inspect|support`, `400 reason_required`, `409 cannot_resolve`, `409 measured_capacity_exceeded`), `POST /api/orders/:id/objects`, `GET /api/orders/:id/objects`, `POST /api/orders/:id/objects/:objectId/read`, and `GET /api/orders/:id/objects/:objectId/content` (objects: `403 forbidden`, `400 invalid_content_type`/`object_too_large`/`invalid_checksum`/`checksum_mismatch`, `401 read_invalid`/`read_expired`, `409 objects_unavailable`/`object_scan_pending`/`object_rejected`). Existing `POST /api/price`, `POST /api/orders`, `POST /api/jobs/:id/accept`, `POST /api/jobs/:id/offer` and `POST /api/orders/:id/offers/:driver/accept` accept the additive `declaredScope` field only; no existing field changes shape.

The PG suites are registered in `scripts/check-persistence.mjs`; the SQLite suite is registered in `scripts/run-tests.mjs`. Real results in this session: `node scripts/check-contracts.mjs` passes (174 frozen exchanges unchanged, 90 installed + 45 additive endpoint boundaries); the `resource-scope`, `private-objects`, `dispatch`, `ride-lifecycle`, `quotes`, `eligibility`, `capacity` and `coverage` persistence subsets pass serially; `tests/pg-import.mjs` passes standalone (29 legacy tables, 135 rows, pg_dump/pg_restore + HTTP parity — one earlier attempt in this session hit the known 30-second `pg_dump` spawn timeout flake also recorded in WP10/WP11 and passed on the standalone rerun, with no WP12 code in the dump path); `npm test` passes 62 suites (61 before, plus the new SQLite suite); `npm run lint` and `npm run typecheck` exit 0.
