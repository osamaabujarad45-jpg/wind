## Import, reconciliation and recovery contract

`snapshotSqlite(source,newDestination,freezeWrites?)` uses Node's online backup API to include committed WAL pages in one consistent image. Destination must be new and distinct. Read-only inspection checks SQLite integrity and the reviewed v3 version. The optional short freeze holds a separate `BEGIN IMMEDIATE` only during snapshot creation; it is a rehearsal, not a production cutover coordinator. Tests prove an online snapshot excludes an uncommitted writer and a subsequent frozen snapshot includes its completed WAL commit.

`importSnapshot(snapshot,persistence,schema,reportPath?)` installs the reviewed schema explicitly and imports in one advisory-locked transaction. Accounts precede assignment rows; foreign keys are deferred then checked before commit. Source rows are never rewritten to satisfy a unique index, fabricate a driver, drop custody, normalize a conflicting email or invent capacity. Per-row reports identify table, hashed key, SQLSTATE/constraint and static failure category without source credential/PIN/contact values. Non-cent money exceptions include the original financial amount and chosen integer result for review. A failed import is never accepted because its remaining rows look valid.

Reconciliation compares exact old-column values and row multiplicities; counts and sorted row/key digests; fare, commission, discount and cash totals; finished-job commission/discount totals; every driver's open and pending cash obligations; and every active custody ID. Equality covers sessions/password hashes, installed request IDs/payload hashes, partner references, proof counters/codes, returns, chat and security history, subscriptions, promotions/referrals, saved places, checkpoints and Arabic/timezone values. Original proof/password/session formats are unchanged.

The tested dataset contains **29 nonempty legacy tables, 135 rows, two open-custody orders, two rounding exceptions and two distinct promo redemptions**. Successful report has zero mismatches. Every identity sequence is checked above the imported maximum, including after restore. Money is summed as exact integers for reconciliation rather than trusting floating totals.

Recovery uses actual PostgreSQL18 `pg_dump --format=custom --schema <isolated schema> --no-owner --no-acl`, creates a fresh isolated database, installs PostGIS there and restores with `pg_restore --exit-on-error`. It then reruns complete row/key/financial/custody reconciliation, identity, geometry and immutable-cash checks, plus HTTP parity against the original SQLite and imported database. The derived live `ageSeconds` field is independently checked against current elapsed time before comparison normalization; stored fix coordinates/timestamps remain exact. This is a local logical-backup rehearsal on a separate database, not Azure PITR/failover/RTO evidence.
