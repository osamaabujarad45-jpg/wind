## Numbering and identity boundaries

Primary sources checked:

- [ITU Palestine numbering notice, published29 November2024](https://www.itu.int/dms_pub/itu-t/oth/02/02/T02020000FF0001PDFE.pdf): the ministry describes an incomplete +970 transition and cautions against an operational switch until notice. Accordingly, parsing a +970 representation never selects the carrier route or rewrites an existing account's login key.
- [ITU Operational Bulletin1008, +972 mobile allocation table](https://www.ituob.org/issues/1008/) and [Ministry of Communications2023 numbering decision](https://www.gov.il/BlobFolder/policy/09022023_3/he/Decision-Adjusting_the_numbering_plan.pdf): Palestinian operator ranges are distinct from arbitrary +972 mobile numbers. Prefix recognition is not a claim about a subscriber's current carrier or nationality.
- [Ooredoo Palestine contact guidance](https://www.ooredoo.ps/%D8%B9%D9%86-ooredoo/%D8%A7%D8%AA%D8%B5%D9%84-%D8%A8%D9%86%D8%A7.html): local056 and international00970 examples establish representation, not delivery permission or cross-carrier support.

The new parser accepts explicit `countryContext:'PS'`, local `056/059` ten-digit numbers, nine-digit national mobile forms, and `+970`/`00970`/applicable `+97256`/`+97259` forms. Arabic/Persian digits and ordinary separators are handled. Explicit `e164`/calling code and display text are preserved. Arbitrary +972 prefixes, fixed lines, extensions and malformed lengths are rejected. PS context is an explicit numbering context, never an inference about nationality.

`canonicalGroup` is a **collision review key**, not a new user identifier or automatic operational +970 route. Migration creates empty mapping/alias tables. Admin review checks every supported legacy representation under a shared group lock, rejects another user's ownership or conflicting legacy records, and records reviewer/reason/provenance/version. It never merges, renumbers or deletes users. The selected routing number is separately supplied and must represent the same reviewed mobile group.

Mappings start reviewed, not phone-verified. Only a successful control proof marks them verified. Existing numeric IDs, local phone keys, scrypt hashes and hashed sessions stay valid. Installed local/+970 login runs its original lookup first. A reviewed **and verified** +972 alias may then resolve to the same existing account; all aliases share the installed login throttle. Phone change explicitly requires authenticated current password, identity revision, reviewed target and new-number proof. On success it changes the requested contact key, retains account ID/password/history, retires the former verified mapping and revokes every session/push subscription. A number owned by another account cannot be claimed.

Phone control grants no driver identity, biometric/background-check or vehicle/operating approval. Admin recovery remains operator-controlled; public phone recovery excludes admin accounts. No identity scan field or upload is added.

## Provider contract and external gates

Sources: [Palestine developer catalogue](https://developer.ooredoo.com/palestine-developer-portal), [Communication Management documentation](https://developer.ooredoo.com/api/communication-management), [downloaded v4 OpenAPI](https://developer.ooredoo.com/sites/default/files/apidoc_specs/CommunicationManagement_0.yaml). The inspected API supports server-authored SMS content, unlike provider-owned CAMARA OTP. No CAMARA verification is represented as a local HMAC check.

The implemented contract is:

1. `POST https://api.ooredoo.com/tmf-api/oauth/v4/token`: `client_id`/`client_secret` headers; form `grant_type=client_credentials`. Validate `access_token`, `token_type:'Bearer'` and bounded integer `expires_in`.
2. `POST https://api.ooredoo.com/tmf-api/communicationManagement/v4/communicationMessage`: Bearer authorization, configured `countryCode`, UUID `transactionId`, JSON `{content,messageType:'sms',receiver:[{phoneNumber}],sender:{name}}`.
3. HTTP201 is **accepted**, never proof of handset delivery. Response content is bounded/validated, not persisted or logged. The published schema provides no guaranteed external message ID; `provider_reference` stays null. The stored transaction UUID is our correlation ID, not a provider delivery receipt or idempotency promise.

The inspected specification publishes no authenticated delivery callback/query route or transaction-ID idempotency guarantee. Both capability flags are false; no undocumented endpoint, signature, polling success or sender/cross-carrier permission is invented. Generic marketing descriptions do not establish those contracts. Current catalogue wording describes Ooredoo-network messages; actual Jawwal support and each +970/+972 route remain external validation gates.

OAuth timeout3seconds; SMS timeout5seconds; responses at most16KiB. Tokens are reused and concurrent refreshes coalesce. An explicit401 permits at most one token refresh/retry with another authority check; a network timeout, malformed accepted response or5xx is unknown and never automatically replayed. Definite nonacceptance is failed. Raw provider errors/echoed content/token/secret are never logged or journalled.

Required enablement settings are `WIND_PHONE_ENABLED=1`, provider `ooredoo_communication`, `WIND_PHONE_HMAC_KEY` (base64, at least32bytes), `WIND_PHONE_HMAC_VERSION`, Ooredoo client ID/secret/sender/countryCode, `WIND_PHONE_APPROVED_PREFIXES`, `WIND_PHONE_PROVIDER_EVIDENCE`, daily message limit, daily budget and conservative maximum per-SMS cost. Exact names are in `phoneConfig`. No country header is guessed from an example or from the number. Prefix allowlist is limited to +97056/+97059/+97256/+97259, and only operator-confirmed routes may be configured.

Secrets belong in server secret storage/Key Vault, never client settings or this document. Sender approval, exact country header, contracted upper-bound billing units/currency, approved content, opted-in Jawwal/Ooredoo handset delivery and both applicable calling-code paths require real operator evidence before activation. Configured budget and maximum-cost values must use the same confirmed billing minor unit. These settings are not evidence those gates passed. There has been no real provider test in this packet.

`WIND_PHONE_TEST_PROVIDER_URL` is accepted only with `NODE_ENV=test`, test-only PG flag, allowed isolated schema and loopback DB/provider URL. ## Challenges, replay, cost and authority

The server generates random six-digit OTPs. A challenge stores only HMAC-SHA256 over code plus ID/purpose/number/actor/role/device/session/identity and mapping revisions, with a secret version. Plaintext code exists only in server memory during one send; it is never stored in the DB, public event, log or client bundle. Comparison uses `timingSafeEqual`. Server time alone sets300second expiry, five attempts and45second resend cooldown.

Phone and device request admission uses shared rolling3/15minutes and10/24hours. Suppressed requests are counted; changing purpose does not reset the phone budget. More than30 requests/hour behind one IP creates an audit review signal, not an IP-only hard block of a shared carrier NAT. Phone-change current-password attempts separately use the existing five-per-ten-minute security pattern before invoking scrypt.

Public recovery challenge storage also has serialized global fixed-window limits of 1,000 per hour and 10,000 per day. Beyond those limits the generic response records only that the request was received; no challenge, receipt or provider spend is created. It does not claim an SMS was sent.

Before any SMS call, a short transaction locks/reserves both a message slot and the conservative per-send cost against a provider-wide UTC-day hard budget. Concurrent final-slot claims across two APIs admit one sender. Definitive **no-send** outcomes release the reservation once. Any attempted send, accepted message, crash or uncertain outcome retains it. This is conservative admission accounting, not a claim about the provider's actual invoice or a refund. Unknown outcomes require operator/provider reconciliation under a future established external contract; there is no blind resend or guessed automatic refund.

Phone commands have actor-session or public-device scopes and UUID command IDs. Scope/device lookup hashes derive from high-entropy session material/UUIDs and stay stable across OTP secret rotation; non-password payload/proof fingerprints remain keyed. Successful password-bearing commands store only an independently salted scrypt password fingerprint, checked on replay. Failed command receipts store no password-dependent verifier, so a changed password alone on replay of a failed receipt returns the same failure; a changed proof or other field conflicts. Migration8 replaces preexisting payload digests with random values so old command IDs fail closed without resending. Same command/payload replays its receipt without a second send, attempt increment or reset. Wrong proof replay counts once; five distinct failed attempts lock the challenge. Concurrent valid reset applies once and revokes all sessions/subscriptions; consumed proof cannot be reused under a new command. Successful recovery also clears the installed/alias login throttle.

The synchronous password KDF runs **only after** a valid, unexpired, unconsumed, correctly bound recovery OTP and current identity/collision checks. Invalid UUID targets, wrong/locked codes and unknown accounts do not invoke scrypt. Cheap password-format validation remains uniform. Proof consumption/password update/revocation are atomic under the same locks; no provider await occurs there.

Issuance commits challenge, receipt, audit and reserved budget before detaching provider work. Short phone-only command serialization fixes lock ordering between authenticated verification and public recovery; driver/other HTTP commands do not use that lock. No DB transaction is held across OAuth/SMS. Authority is rechecked after OAuth, before every send and after the response. Logout, phone/password/role/status change, mapping revision, expiry and supersession invalidate proof. A send already in flight cannot be recalled; its result becomes obsolete and its code grants no action authority.

Each new issued challenge supersedes older challenges for that number/purpose, so delayed/out-of-order SMS cannot restore old proof. A new delivery never extends the original expiry. Stale prepared/requested leases become durably **unknown** at startup/admin review, retaining the budget. No plaintext code can be recovered for a resend. Private issuance replay exposes current `deliveryState`; public issuance remains only a generic request receipt, concealing account existence, admission denial and provider failure.

Key rotation invalidates outstanding old-version proof. With only the new key configured, old keyed request fingerprints conflict safely under the same stable command lookup instead of creating another paid send. Rotate all API replicas consistently; mixed keys are not an accepted deployment topology. No old-key acceptance or transparent keyring is claimed.

## Privacy, operations and rollback

Profiles/mappings/challenge numbers and routing metadata are private identity data; challenges also contain session/device hashes and a code HMAC. Access is current user/session or admin, never public event viewers. Public events contain safe challenge/user IDs and fixed actions only. Audit stores actor/reason/provenance, never provider bodies, code or bearer/OAuth secrets. Client source has no phone-provider/server-secret import. No raw IP is stored; the IP review key is HMACed.

Expiry and one-use proof are enforced automatically, but expiry is not a legal retention policy. Production access/retention/deletion and legally required audit holds need a separately approved identity-data schedule before activation. This packet introduces no destructive purge, identity export, scan collection or biometric process. Existing account deletion remains the installed workflow; production anonymization/financial holds remain the broader D27/operator gate.

Provider outcomes/cost reconciliation remain limited by the published send-only contract. Unknown means uncertain; inspect transaction IDs and private audit with the carrier, retain the budget and never mark delivered or refund/retry from speculation. No automatic dispatch worker replays SMS because plaintext codes are not persisted. Lists/startup stale reconciliation are bounded100 records; repeated admin review can drain a larger review backlog. Local test evidence is not carrier deliverability, production throughput, device attestation, PITR or regional latency evidence.

Disable `WIND_PHONE_ENABLED` to stop new provider work; existing password login/email/operator enrollment continue. Preserve phone mappings, proof/audit/command receipts, budget reservations, users and sessions through code rollback. Do not remove migration6/7 or revert accepted PG writes to stale SQLite. Missing/rotated secrets invalidate proof safely; coordinate all replicas before resuming the cohort. No runtime cutover, real provider activation or irreversible action is authorized by these local results.
