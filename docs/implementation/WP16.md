# WP16 local Azure cutover code

WP16 preparation and local code are not deployment approval or proof of a working Azure staging environment. Workloads remain disabled by default. No Azure access, what-if, deployment or paid resource creation was performed in this code task.

## Audit dispositions

- File DNS zone, link, private endpoint and DNS zone group now share the `enableWorkloads` condition. The graph share remains in the foundation; private file connectivity is available only when workloads are enabled, so the graph staging procedure must account for that dependency.
- The API and worker have no database URL, Key Vault reference or other persistent database binding. This is an **owner gate**, not a completed cutover: enabling these apps as currently configured would use ephemeral SQLite. Owner must arrange and review the staging database secret, Key Vault access and bindings for both apps, enable the staging mode, and verify the actual runtime backend before activation. Registry identity and AcrPull are also required. No secrets or roles have been invented here.
- PostgreSQL readiness now reports the maximum applied migration version and fails unless every version 3–18 is applied; SQLite retains its existing readiness contract. The threshold is proven in `tests/db-api.test.mjs` (absent table → 503, version 17 → 503, complete 3–18 → 200) and `tests/pg-contracts.mjs` asserts the real value 18 before normalizing for the frozen SQLite fixture. Image values are checked when workloads are enabled. Compiled enabled parameters and resource conditions are covered locally, not an Azure deployment evaluation.
- `WIND_POSTGRES_STAGING=1` requires `WIND_DATABASE_URL` with a non-loopback PostgreSQL host and `sslmode=verify-full`, and selects `wp16_staging`. API startup does not migrate. The runner now accepts the `wp16_staging` schema (`isolatedSchema` in `server/db/postgres-schema.ts`), so migrations 3–18 can be rehearsed locally under `MIGRATION_LOCK`; the `server/migrate.ts` CLI remains loopback-only by design, so executing against the real Azure target is a reviewed cutover step (step 2), not a local command. Do not enable workloads until that and the database binding gate are closed.

## Cutover order and owner-only work

1. Owner chooses and authorizes the Azure subscription, resource group, budget and deployment; validate quota, policy, private connectivity, DNS and image/mount behavior. Provision the foundation only under that authorization.
2. Complete the runner change, create the staging schema and run migrations 3–18 once under `MIGRATION_LOCK`. Establish Azure PostgreSQL 16/PostGIS compatibility with persistence tests; local PostgreSQL 18 evidence does not establish Azure 16 parity. Rehearse synthetic import and reconciliation, then a real backup, restore to a fresh target and reconciliation.
3. Owner builds and pushes reviewed API/worker and OSRM images to ACR, provides immutable image digests, arranges AcrPull and Key Vault secrets and access, and reviews the database environment binding for both API and worker. Configure the staging build's API origin and graph data/mount; do not use the Railway literal.
4. After all gates pass, owner authorizes staging deployment with workloads enabled. Verify PostgreSQL readiness, synthetic journeys, API/worker restart and outbox recovery, rollback, and latency measurements. Keep push and PubSub unconfigured until their own gates pass.
5. Owner creates or links the EAS projectId, authorizes a preview build, and tests the physical device against the staging backend. Production, paid customers and provider activations require their separate owner approvals and evidence.
