# WP15 backend: operations, support and safety

The existing admin role, disputes, safety incidents and SOS holds, security events, support credits and account deletion remain in place. Migration 18 adds nullable staff sub-roles, support cases with severity, ownership and escalation, append-only case events and staff actions, and financial approval records. Policy versions are deferred; existing settings remain authoritative. New records do not implement payments, financial transfers, emergency dispatch or automatic response.

## Scope and availability

A legacy admin with a null staff role is a platform admin. Current staff authority is read from the database on each action, including ledger import and payment refund; only finance and platform admins can perform those two operations. Granting a staff role requires a platform admin and an admin target. Removing a role restores the legacy platform-admin fallback. This compatibility behavior requires careful operator control. The existing broad admin endpoints and screens still use existing authentication and have not been converted to staff scope.

Customers and drivers see only cases they reported. Support and platform admins can list all cases; safety staff can list safety cases only. Support or safety staff and platform admins can mutate cases, but safety cases can only be mutated by safety or platform staff, and safety staff cannot mutate other cases. Case changes require a named purpose and produce both a case event and a staff action in the same transaction. Assignment requires a suitable admin owner; escalation requires a reason. Finance and platform admins can request or decide approvals; a different person must decide each pending approval. An approval is a record only and does not authorize or execute a refund automatically. Staff audit access is platform-admin only.

SQLite and PostgreSQL databases without migration 18 return `409 ops_unavailable` for authenticated WP15 routes. No WP15 SQLite tables are created. Snapshot import ignores these PostgreSQL-only tables; `users.staff_role` defaults to null because the snapshot's explicit legacy column list does not include it, and reconciliation compares those same legacy columns.

## Owner activation gates and limitations

G3: signed staffing rota and a timed operational drill are required before claiming staffed safety coverage. G4: emergency and support numbers require operator validation and configuration. G6: workforce MFA/SSO and revocation remain an owner gate; `staff_role` is not MFA or SSO. Existing admin screens remain behind the existing authentication boundary, not the new staff scopes. Activating operations requires owner approval of these gates; the code does not claim police dispatch, a callback time or 24/7 service. Masked calling remains off until a tested local relay exists, and AI assistance remains disabled for launch. Deferred UI states and policy versions are not implemented.
