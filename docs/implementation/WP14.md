# WP14 backend: payment adapter and merchant COD

Migration 17 adds PostgreSQL-only payment intents, attempts, provider event inbox, refunds, merchant COD and append-only COD events. Provider events are append-only and deduplicated by provider and event ID. An intent snapshots the order amount and quote reference where present; its order business reference prevents another create for the same order. Captures and operational completion are independent. Out-of-order inbox events are retained without reversing an invalid state transition. Unknown create outcomes stay pending; the injected provider's query can reconcile them without another create.

Refunds never call the provider inside a database transaction: the intent row is locked, the cap (counting `requested`/`approved`/`completed` rows) is checked and a `requested` row is inserted and committed, the provider is called, and a second short transaction settles the row (`completed`, or `rejected` when the provider does not capture, including a provider throw). The two payment provider routes bypass the request-long atomic envelope in `server/main.ts` for this, following the phone-route precedent; a refund invoked from inside an open transaction fails `409 refund_in_transaction`. A crash can leave a `requested` row holding its cap amount (fail-closed: no double refund); re-driving it requires the activation reconciliation below. The provider interface still takes no refund idempotency key, so a lost response followed by a fresh-`requestId` retry can double-refund at a real provider; idempotent provider refund requests remain an activation requirement, not implemented against the fake.

COD goods value is recorded separately from fare, commission and ledger journals. A customer owner or admin creates a record; the assigned driver or admin records collection up to the goods value and 1,000,000 minor-unit limit. A finance-scoped admin (WP15 `needStaff('finance')`; legacy unscoped admins count as platform admin) records a payout reference once fully collected. Refunds are finance-scoped too: a refund the provider does not capture is marked `rejected` and does not consume the capture cap, an optional client `requestId` makes refund submission replay-safe, and webhook events never set refund states — only `refund()` does, keeping cumulative refund rows authoritative. These records do not themselves transfer or hold money. SQLite has no WP14 tables: authenticated payment and COD endpoints fail with `409 payments_unavailable`; the public webhook rejects an invalid signature with `401 invalid_signature` before checking availability.

## Capability matrix

| Capability | Current implementation |
| --- | --- |
| Create, query, capture, void, refund | Interface and deterministic injectable fake only; no Bank of Palestine transport. |
| Webhook | Test signature verifier only. Real raw-body signature verification and bank event format are not implemented. |
| Timeout reconciliation | Fake query can reconcile a pending intent; no live bank query exists. |
| COD | Separate collection and manual remittance evidence records; no wallet or escrow. |
| Preauthorization, marketplace split payout, native SDK | Not claimed or implemented. |
| Hosted/tokenized checkout and approved return link | Not implemented; no raw card data is collected by this adapter. |

The fake is constructed only with `NODE_ENV=test` and `WIND_PAYMENTS_TEST_ONLY=1`. `WIND_BOP_ENABLED=1`, `WIND_BOP_MERCHANT_ID` and `WIND_BOP_SECRET` identify a configured environment but do not activate a real provider; live provider operations remain unavailable. Activation requires a signed merchant agreement and confirmed capability matrix, sandbox access, approved holding and settlement arrangements, finance ownership, and an authorized test budget. Integration also requires raw request bytes, a bank-approved signature verifier, idempotent refund/provider requests, reconciliation and settlement tests, and actual transport implementation. No real payment, settlement, chargeback handling or payout reconciliation is claimed.

## API contract

`POST/GET /api/orders/:id/payments`, `POST /api/orders/:id/payments/refund`, public `POST /api/payments/webhook`, `POST/GET /api/orders/:id/cod`, and `POST /api/orders/:id/cod/collect` and `/remit`. Customer owners and admins manage payment intents; only finance-scoped admins refund and remit COD. Order participants can view COD, and only the assigned driver or admin can collect it. Provider calls are disabled outside the explicitly configured test fake.

## Verification

`node scripts/run-tests.mjs --filter=payments-sqlite`: seven authenticated 409 gates, anonymous signature rejection, absent SQLite tables, and legacy parcel/freight flow passed. `node scripts/check-persistence.mjs --filter=payments`: migration 17, idempotent intent creation, signature rejection, duplicate and reordered inbox events, fake timeout/query reconciliation, partial and excessive refunds, and COD collection/remittance with unchanged fare and ledger passed. `node scripts/check-contracts.mjs`: 90 installed and 59 additive boundaries, 174 exchanges passed. `npx tsc --noEmit` and `npx expo lint` passed.

Refund-transaction slice (this session): `tests/payments.mjs` now also proves the provider refund runs with no open transaction, that concurrent same-`requestId` refunds racing inside reservation make one provider call and one row, that an in-flight replay returns the `requested` row without a second provider call, and — through a real HTTP fixture with the test fake enabled — that create/query/refund reach the provider instead of failing inside the request envelope. Mutation-proven both ways: wrapping the provider call back in a transaction fails the suite (exit 1), and disabling the envelope bypass fails the HTTP refund with `409 refund_in_transaction` (exit 1). Independent review (fresh Wonder critic; DeepSeek/MiniMax/GLM pools unavailable) found the envelope defect, since fixed; its provider-idempotency-key and stuck-`requested` findings are the activation backlog recorded above.
