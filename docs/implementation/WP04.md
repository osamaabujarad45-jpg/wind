## Atomicity and privacy

PG order INSERT/UPDATE, proof attempts, security audit insertion and cash INSERT/UPDATE have database journal triggers. Every such committed mutation has a durable event plus timeline outbox row, including direct SQL writers. Transactional sequence allocation is unique per order. Event sequence is a cursor, distinct from aggregate version: multiple safe events can describe a version. Pre-migration historical state remains authoritative through snapshots; migration4 does not invent historical events.

The actual HTTP transaction commits only after state, awaited notification destinations and new command result are written. Notification persistence failure rolls back even work after a legacy handler's COMMIT. Intentional HTTP errors retain existing savepoint semantics: wrong proof commits its attempt, journal and saved error; replay cannot increment attempts again. Proof failures advance aggregate version without changing lifecycle status. Cash retains append-only/decision guards and locks the driver account before checking remaining obligations.

Actors derive from authentication. Public/partner/cron/direct maintenance writes have named purposes, never a global mutable actor. HTTP events share a generated correlation UUID. Events contain IDs, public statuses, versions/epochs, minor-unit money and action identifiers. They omit phones, addresses, precise locations, password/hash, bearer/share token, handover/return codes and free-form security notes. Destinations contain user ID and SHA256 subscription endpoint key, not endpoint/encryption credentials. Existing private subscription storage supplies delivery material.

Command results store the original **authorized private response**, including fields the authorized installed client already receives. These rows require private order-equivalent access/retention; they are never public events. Only authenticated current participants/admin can request the order timeline.

## Exact additive contract for root integration

No registered route was added. Default paths, statuses, numeric IDs and response shapes remain unchanged: the unmodified corpus remains90 route boundaries/21 transitions/174 exchanges.

1. `GET /api/health?protocol=1` adds `protocol: {version:1,durableCommands,durableEvents,pushDelivery,snapshotAuthority:true}`. PG advertises durability only with migration4 and its tables. SQLite advertises false and `legacy_best_effort`. Durable protocol requests on SQLite return409 `durable_protocol_unavailable`. Critical PG writes without migration4 return503 `durable_schema_required`.
2. `GET /api/orders/:id?protocol=1&after=<nonnegative sequence>` adds `protocol: {version,assignmentEpoch,events,nextCursor,snapshotRequired:true}` to the normal snapshot. Repeatable-read/read-only transaction makes snapshot and page consistent. Events are ascending, at most100/page. Only current customer/current assigned driver/admin can request it; marketplace drivers and public tracking viewers cannot. Default GET is unchanged.
3. Event shape: `{eventId,aggregateId,sequence,aggregateVersion,assignmentEpoch,type,occurredAt,correlationId,schemaVersion:1,payload}`. Order-scoped versions/epochs come from current state. Payload has nullable `systemPurpose`. Consumers dedupe IDs, reject older versions/epochs and fetch snapshots on sequence gaps/reconnect. Events/push grant no action authority. No PubSub/WebSocket provider is claimed.
4. Authenticated order/job/admin-order/admin-cash/driver-cash mutations accept flat `{commandId,expectedVersion,...existingFields}` or `{commandId,expectedVersion,clientRecordedAt,payload:{...existingFields}}`. commandId is a UUID. clientRecordedAt is metadata, excluded from fingerprint. Explicit top-level fields override payload. Path/method/business fields, including expectedVersion, are hashed; changed input under an actor's existing ID returns409 `idempotency_conflict`.
5. Order-targeted commands require positive safe-integer expectedVersion. Creation has no existing aggregate to compare. The adapter uses existing handlers, supplies requestId from commandId when absent and derives expectedStatus from the locked order when absent. Existing requestId/expectedStatus adapters keep installed semantics. New stored success/error replay follows authentication but precedes current version, price, quote/offer and assignment checks. A changed attempt needs a new commandId, including after saved proof/VERSION_CONFLICT errors. Error body remains `{error}`; stale new versions use409 `VERSION_CONFLICT`.
6. New money commands require `currency:'ILS'` and exact amountCents. Cash confirmation also requires expectedVersion and stored amountCents; altered amount returns409 `cash_amount_changed`. `GET /api/driver/cash?protocol=1` adds currency and up to100 pending `{id,version,amountCents}` entries. Default cash output is unchanged. New cash-entry creation has no existing entry version. Old cash requests gain no required fields.

Existing negotiated-offer lifetime stays ten minutes; this is not WP07's future sequential15-second dispatch lease. Quote/route/itinerary/restriction revisions belong to later packets when those aggregates exist. D30's WP04 contribution is replay/version/state ordering and recoverable hints that cannot assign, collect or undo custody; no dispatch engine is fabricated.

## Worker and review queue

Entrypoint: `node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --disable-warning=ExperimentalWarning server/worker.ts`. It requires the same explicit test-only loopback PG environment/schema as API, plus installed migration4. It rejects SQLite and cannot enable production PG access.

Claims use `FOR UPDATE OF outbox SKIP LOCKED`, ordered by due time/event occurrence, with a fresh per-row UUID lease token. Default lease30seconds; actual Web Push timeout10seconds. States: pending/processing/delivered/obsolete/review. Claims increment attempts; expired leases recover after restart; stale owners cannot acknowledge replacement work. Default maximum8 attempts; backoff starts1second, doubles to at most1hour plus up to25% jitter. Exhaustion/poison enters review. Only safe provider status is stored; raw error/body is excluded.

Timeline projection, inbox and acknowledgment commit together. Projection advances only by sequence. Web Push resolves current subscription/role/access, epoch, lifecycle and remaining TTL before send. Logout/account switch/revocation, stale epochs, cancelled/finished job or offer hints, obsolete state hints and expired TTLs are suppressed. Retry never restarts TTL. Worker never changes assignment, custody or cash.

Existing encryption/VAPID is retained. HTTP404/410 disables invalid subscription and records obsolete/provider status, never delivered. Other non2xx/timeouts/encryption/network failures retry/review. A2xx is acknowledged in DB after provider return. Crash between publication and acknowledgment can duplicate provider delivery: **at least once, never exactly-once provider delivery**. Inbox skips already acknowledged destinations. SIGTERM/SIGINT stops claims and drains the current bounded call before pool close.

Review uses safe `outbox WHERE status='review'` fields joined to minimized events. Investigate provider/configuration before explicitly requeuing reviewed work; retain inbox keys and evidence. Do not retry indefinitely. Operator UI, native Expo/APNs/FCM, PubSub, consented SMS fallback and urgent staffing remain WP09/operator gates.
