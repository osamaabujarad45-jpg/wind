# WP11 backend: ride lifecycle — arrival evidence, grace clock and boarding challenge, activation off

Migration 14 (`server/db/postgres-ride-lifecycle.sql`, registered in `server/db/postgres-schema.ts` after verifying 13 was the maximum) adds two PostgreSQL-only tables, allowlisted for legacy import in `server/migrate.ts` (`NON_LEGACY_TABLES` plus the auxiliary table list). `ride_lifecycle` holds at most one current-assignment row per order: the matched `driver_id`, the `assignment_epoch` it belongs to, `arrived_at`/`arrival_source` (`gps` or `operator_override`)/`arrival_actor_id`, the 4-digit `boarding_code`, and `boarding_required`. `ride_boarding_attempts` is a separate counter (`order_id`, `assignment_epoch`, `failures`) so boarding misses never touch `proof_attempts`, the parcel handover code or the sender return code; neither legacy code field is reused for boarding. SQLite gains no tables or columns and the frozen SQLite schema is unchanged.

`server/domain/ride-lifecycle.ts` implements arrival, grace and the boarding guard. Arrival (`POST /api/orders/:id/arrive`, matched driver only) is server-confirmed from the newest stored driver fix — the legacy `driver_locations` or presence `driver_latest_locations` good-fix reference, both of which already passed the 70 m/s plausibility rejection at ingestion — and requires that fix to be at most `RIDE_ARRIVAL_FIX_MAX_AGE_MS = 120_000` old (the freshness order serialization already uses for a live fix) and within the named `RIDE_ARRIVAL_RADIUS_METERS = 300` of the pickup pin (room for the 50 m effective accuracy of an unreported fix plus pin error, without accepting a driver blocks away). Arrival is recorded with server time while the legacy status stays `assigned`; the five-minute grace clock (`RIDE_GRACE_MS = 300_000`) therefore starts only after a valid arrival, and no waiting or cancellation fee is introduced anywhere (`newWaitingFeeMinor`/`newCancellationFeeMinor` remain 0). A repeated arrival replays the original timestamp. A client-supplied override flag is rejected as invalid input and never authorizes arrival: the only no-GPS path is the named operator override (`POST /api/admin/orders/:id/arrival/override`), an admin action requiring a reason of at least five characters, recorded in `security_events` as `RIDE_ARRIVAL_OVERRIDE` with actor, driver, assignment epoch and the reason in the detail. GPS arrivals record `RIDE_ARRIVED` with the measured distance and fix age.

The supported boarding cohort is precise: a PostgreSQL ride order assigned (a) through WP10 dispatch acceptance, or (b) through any existing assignment path (legacy accept, dispatch accept closure, or customer acceptance of a negotiated offer) while the boarding test gate is on — `eligibilityDefaults.futureBoardingChallengeActivated` remains `false`, and the gate is only `NODE_ENV=test` plus `WIND_BOARDING_TEST_ONLY=1`, following WP10's test-only pattern. At such an assignment `RideLifecycle.ensureAssignment` generates the 4-digit code server-side for the new `assignment_epoch` and resets arrival and attempts; a release (`clearAssignment`, inside the release transaction) deletes both lifecycle rows, so WP10's re-dispatch to a new epoch excluding the releaser starts with no arrival, code or attempts from the previous driver. Orders outside the cohort — every SQLite order and every legacy PostgreSQL assignment outside the gate — get no lifecycle row and advance, release and cancel exactly as before.

Order serialization gains the additive `ride` object only when a lifecycle row exists: `{arrivedAt, graceUntil, arrivalSource, boardingRequired, boardingLocked}`, with `boardingCode` included only for the customer owner and the currently matched driver at the current epoch — never for pre-assignment drivers, other drivers, admins, or the public tracking view (an explicit allowlist that never read the code).

## Start and completion guards

`advanceOrder` keeps every legacy check (matched driver, `expectedStatus`, safety hold, proof codes) and, for cohort rides, additionally calls `RideLifecycle.guardAdvance` after `safetyFree`: moving to `at_pickup` or `in_transit` requires a recorded arrival at the current driver and `assignment_epoch` (`409 arrival_required`, `409 assignment_changed`); starting (`in_transit`) with `boardingRequired` requires `boardingCode` (the existing advance `code` field is accepted as its spelling) — a miss increments only `ride_boarding_attempts`, writes `BOARDING_FAILED`, and fails `400 wrong_boarding_code`; the fifth miss writes `BOARDING_LOCKED`, pages admins like the proof lockout, and locks boarding (`409 boarding_locked`, correct code included) until an admin calls `POST /api/admin/orders/:id/boarding-reset` with a reason (audited as `BOARDING_RESET`). Completing or returning a cohort ride checks the current assignment only; rides keep their existing `in_transit -> completed` movement and payment outcome, no started ride is ever reset to `searching`, and release stays pre-pickup only. The existing exception, safety-hold, `on_hold`/`returning`/`returned`, return-code and cash flows are untouched: duplicate return confirmation replays or is refused with order and cash totals unchanged, and cancellation in custody remains impossible under the existing `cancellable` list.

## API contract

New additive routes, registered only through `docs/implementation/contracts/additive-endpoints.json`: `POST /api/orders/:id/arrive` (matched driver; `400 invalid_input`, `404 not_found`, `409 ride_lifecycle_unavailable` on SQLite/pre-migration, `409 not_a_ride`, `409 cannot_arrive`, `409 safety_hold`, `409 arrival_fix_missing`, `409 arrival_fix_stale`, `409 arrival_too_far`), `POST /api/admin/orders/:id/arrival/override` (admin, reason required; `400 invalid_input`/`400 reason_required`, `403 forbidden`, plus the arrival failures above), and `POST /api/admin/orders/:id/boarding-reset` (admin, reason required; `409 boarding_not_required` when no cohort row exists). Existing `POST /api/orders/:id/advance` is unchanged outside the cohort and gains `409 arrival_required`, `409 assignment_changed`, `409 boarding_locked` and `400 wrong_boarding_code` only for cohort rides. No existing field changes shape; on SQLite all three WP11 routes return `409 ride_lifecycle_unavailable` while the legacy advance flow is untouched.

## Verification

New suites: `tests/ride-lifecycle.mjs` (migration 14 and import allowlist, GPS arrival and grace clock, pre-assignment/admin code redaction, arrival-before-pickup, boarding attempts 1–4 then success with `proof_attempts` untouched, duplicate advance/completion replay, far/stale/missing fix rejection, wrong driver, client-flag refusal, audited operator override, five-miss lock and audited reset, release/reassignment with stale-epoch start rejection, legacy PG flow unchanged without the gate), `tests/ride-lifecycle-races.mjs` (start-vs-release and complete-vs-safety-hold single winners across both API processes, duplicate return confirmation with unchanged order/cash totals, cancellation in custody refused), and `tests/ride-lifecycle-sqlite.mjs` (409 WP11 gates, legacy accept/advance unchanged, no SQLite tables). The PG suites are registered in `scripts/check-persistence.mjs`; the SQLite suite is registered in `scripts/run-tests.mjs`. Real results in this session: `node scripts/check-contracts.mjs` passes (174 frozen exchanges unchanged, 90 installed + 36 additive endpoint boundaries); the `ride-lifecycle`, `dispatch`, `quotes`, `events`, `eligibility`, `presence`, `capacity`, `coverage`, `commands`, `outbox`, `pg-cash`, `offers`, `claims`, `realtime`, `active-gps`, `native-push`, `phone`, `review-security`, `database-logging`, `pg-live`, `pg-contracts`, `pg-dialect`, `pg-customer-rating`, `db-persistence`, `db-api`, `pg-claims`, `pg-email`, `presence-migration`, `driver-presence-api`, `pg-live-commit`, `eligibility-legacy` and `pg-memo` persistence subsets pass serially; `tests/pg-import.mjs` passes standalone (29 legacy tables, 135 rows, pg_dump/pg_restore + HTTP parity); `npm test` passes 61 suites (60 before, plus the new SQLite suite); `npm run lint` and `npm run typecheck` exit 0. The unfiltered `check-persistence` run (which also runs the legacy-import check) was not used as a gate in this session — every suite in its list was exercised individually through its filter, serially, so the known parallel-load `pg_dump` timeout flake did not arise and no result is hidden behind it.

Open gates, recorded as not met: boarding activation stays off outside the test cohort (`futureBoardingChallengeActivated: false`; dispatch itself remains test-only under WP10's gate, so no real ride is boarding- or auto-dispatch-ready), arrival enforcement applies only where a lifecycle row exists (legacy assignments outside the cohort keep the legacy flow by design until activation is separately approved), photo/signature proof remains disabled until WP12's private-object release, and no waiting or cancellation fee is introduced. Production PostgreSQL cutover remains gated by the earlier packets.
