# WP10 backend: deterministic passenger dispatch and atomic acceptance, activation off

Migration 13 (`server/db/postgres-dispatch.sql`, registered in `server/db/postgres-schema.ts` after verifying 12 was the maximum) adds three PostgreSQL-only operational tables, allowlisted for legacy import in `server/migrate.ts` (`NON_LEGACY_TABLES` plus the auxiliary table list). `dispatch_rounds` holds one open round per order through a partial unique index, with `deadline_at = started_at + 90s` written once at insertion and never extended; states are `open`/`matched`/`exhausted`/`cancelled` with a `close_reason`. `dispatch_offers` stores a UUID id, the 15-second lease (`expires_at = min(issued_at + 15s, round deadline)`), only the SHA-256 `nonce_hash` (no raw-nonce column exists), partial unique indexes for one open offer per round and per driver, and every bound revision — order (`orders.version` as `order_revision`), `assignment_epoch`, presence session id, vehicle, driver/vehicle/policy/requirements/run revisions — plus the persisted rank inputs `pickup_eta_seconds`, `idle_seconds`, `idle_credit_seconds`, `rank_score` and the `eta_estimated` flag. `assignment_history` is append-only under the existing `wp05_append_only` trigger. A trigger on order cancellation revokes the open offer and cancels its round inside the cancelling transaction, so every cancel path (customer, partner, support, failed pickup) has the same behaviour. SQLite gains no tables and the frozen SQLite schema is unchanged.

`server/domain/dispatch.ts` implements filter → shortlist → rank → issue-one-at-a-time. The filter accepts only `service='ride'` orders: presence session online with a valid lease and a fix at most 30 seconds old bound to that session (`driver_latest_locations`), eligibility evidence mirrored from `Presence.status`/the presence sweep in SQL (enrolled/approved driver and vehicle, activated policy, presence-bound revisions, current license/registration/inspection checks, no unknown legacy load), a required `order_requirements` row (prep A8: an unmeasured ride is never dispatched), vehicle seats and equipment (`equipment @>`), no active work of any service for the driver and no active work on the vehicle, exclusion of drivers in `order_releases` for the order, and exclusion of drivers already offered in the round or holding another open offer. The shortlist is the PostGIS KNN over `driver_latest_locations.position` bounded by the named constant `DISPATCH_SHORTLIST_LIMIT = 10`. Road ETA is evaluated only on that bounded set through an injected provider: `server/main.ts` wires the retained `osrmRoutes` adapter when `OSRM_URL` is configured, and any provider failure or absence falls back to a straight-line 30 km/h estimate persisted with `eta_estimated = 1` — a road ETA is never fabricated. Ranking is the binding formula `pickupETAsec - min(60, floor(idleAvailableSec / 10))` with a stable driver-id tiebreak; idle is measured from the presence session `started_at`; rating is never read. Before each issue the candidate is re-checked through `Eligibility.base` and `Eligibility.coverage` (plus current approach evidence), and acceptance re-runs `Eligibility.guard` under the offer locks — eligibility is never weakened by dispatch. Offers are issued one at a time; decline or expiry issues the next ranked driver; three offers or the 90-second deadline exhausts the round with `close_reason` `no_driver` or `deadline`. A driver release before pickup records `assignment_history` and starts a new round that excludes the releaser through `order_releases`; retry creates the next round on the same order at the same committed price.

The lease nonce is never stored: it is deterministically re-derived by the server from the bound presence session's credential hash (`leaseNonceFor`) and disclosed only to the offered driver through the order's `dispatch.myOffer`; acceptance compares `SHA-256(supplied nonce)` against the stored hash. Acceptance keeps `POST /api/jobs/:id/accept` working exactly as today when the body carries no offer (and a new guard returns `409 dispatch_offer_required` only while a dispatch offer for that order is open, so the legacy path cannot bypass a live offer). With `{offerId, leaseNonce}` — and `commandId`/`expectedVersion` through the existing `versionedCommand` envelope when supplied — the transaction locks in the order orders → advisory → driver → presence → vehicle/run → offer (the dispatcher's installed pre-lock already takes the order row first, so this unifies on order-first and changes direct accept's previous users → orders order), validates offer openness, nonce hash, server-time expiry, `searching` state at the same `orders.version`/`assignment_epoch`, the bound presence session and every bound revision, and the cross-mode locks (a driver with active parcel custody cannot accept the ride; vehicle-level active work blocks a second driver on the same vehicle), then atomically assigns, marks the offer accepted, revokes competitors, closes the round `matched`, appends `assignment_history`, emits the `dispatch.matched` domain event/outbox row, and stores the command result. A replayed command returns the stored result before any expiry or version check. `DurableWorker.processDispatchExpiries` (also run at the head of `runOnce`) expires offers under the identical `order_revision = orders.version` predicate, so accept-versus-expiry has exactly one winner and a restart simply reprocesses nothing twice.

Activation stays honestly off: `eligibilityDefaults.futureDispatchActivated` remains `false`, and dispatch is reachable only with `NODE_ENV=test` plus `WIND_DISPATCH_TEST_ONLY=1` (`dispatchEnabled` in `server/domain/eligibility.ts`). In that test-only mode `Presence.status` returns `eligibleForMatching: true` for a fully eligible idle driver with a fresh fix; busy drivers keep `eligibleForMatching: false` with the previous reason, and every other mode keeps `dispatch_not_enabled` exactly. Ride creation (immediate or at scheduled release) starts a dispatch round only when dispatch is enabled; otherwise the legacy `newJobPush` broadcast is unchanged, as are parcel and freight. WP08's 100-case corpus and operator sign-off are not met, so no real ride may be described as auto-dispatch ready.

## API contract

`POST /api/jobs/:id/accept` is unchanged without offer fields. With `{offerId, leaseNonce, commandId?, expectedVersion?}` it returns the assigned order (with `dispatch.state: 'matched'`) or `400 invalid_input`, `404 not_found`, `409 dispatch_unavailable` (SQLite or missing migration), `409 dispatch_offer_closed`, `409 offer_expired`, `409 invalid_lease_nonce`, `409 dispatch_order_changed`, `409 presence_session_changed`, `409 eligibility_changed`, `409 vehicle_busy`, `409 shared_vehicle_busy`, `409 already_taken`, or the existing eligibility guard failures. New additive routes, registered only through `docs/implementation/contracts/additive-endpoints.json`: `POST /api/offers/:id/decline` (the owning driver only, idempotent — a repeat returns the declined state; another driver gets `404`) and `POST /api/orders/:id/dispatch/retry` (the customer owner of a searching ride only; an already-open round is returned unchanged). Order serialization gains the additive `dispatch` object `{roundId, state, closeReason, offersIssued, deadlineAt, startedAt, myOffer?}` only when a dispatch round exists for the order; `myOffer` (with `leaseNonce`, ETA, idle credit and rank score) is present only for the offered driver's view. No existing field changes shape, and on SQLite all three dispatch paths return `409 dispatch_unavailable` while the legacy accept is untouched.

Ambiguity defaults (prep A1–A11), all fail-closed and none invented beyond this list: A1 shortlist bound 10 (`DISPATCH_SHORTLIST_LIMIT`); A2 idle origin is the presence session `started_at`; A3 no decline cooldown was invented — a declining driver is excluded only from that round (an existing offer row in the round); A4 no safety pair-block table exists anywhere in the tree (searched), so no pair-block filter or table was created; A5 rounds are numbered per order, one open at a time, each with its own unextended 90-second deadline; A6 the ETA fallback is the marked straight-line estimate above; A7 server `Date.now()` is the only clock authority for leases and deadlines; A8 unmeasured rides get no dispatch; A9 retry is the customer owner's idempotent new round, no command id required; A10 lock order is unified order-first as described above; A11 legacy no-quote ride orders dispatch on their committed order price exactly like quote-bound ones, and retry never re-prices.

## Verification

New suites: `tests/dispatch-migration.mjs` (migration 13, tables, partial unique indexes, rank-input columns, nonce-hash-only, append-only trigger, import allowlist), `tests/dispatch-ranking.test.mjs` (formula, 60-second cap, tiebreak, rating exclusion; registered in `scripts/run-tests.mjs`), `tests/dispatch.mjs` (fail-closed creation, retry, ranked sequential issue, decline → next, atomic accept with history/event, decline exhaustion, no-supply, release re-dispatch excluding the releaser, cancel revocation), `tests/dispatch-races.mjs` (120 concurrent attempts across both API processes with exactly one winner, command replay, vehicle-edit fencing, parcel-custody cross-mode block, two drivers sharing one vehicle with one winner, expiry-versus-accept and cancel-versus-accept single winners, worker-restart idempotence, deadline exhaustion), and `tests/dispatch-sqlite.mjs` (409 gates, presence off, legacy accept unchanged; registered in `scripts/run-tests.mjs`). The PG suites are registered in `scripts/check-persistence.mjs`. Real results in this session: `node scripts/check-contracts.mjs` passes (174 frozen exchanges unchanged, 90 installed + 33 additive endpoint boundaries); `node scripts/check-persistence.mjs --filter=dispatch` passes all three PG suites; the `quotes`, `events`, `eligibility`, `presence`, `capacity`, `coverage`, `commands`, `outbox`, `native-push`, `realtime`, `claims`, `offers`, `pg-cash`, `pg-live`, `phone`, `review-security`, `active-gps` and `database-logging` persistence subsets pass; `npm test` passes 60 suites (58 before, plus the two new SQLite/pure suites); `npm run lint` and `npm run typecheck` exit 0. One environmental note: a single full `check-persistence` run stopped in `tests/pg-import.mjs` at a 30-second `pg_dump` spawn timeout; that suite passes standalone (29 legacy tables, 135 rows, pg_dump/pg_restore + HTTP parity), and no WP10 code participates in the dump path.

Open gates, recorded as not met: WP08's adjudicated routing corpus (≥100 cases per launch area) and operator sign-off do not exist, quote feasibility stays `uncertain`, and `futureDispatchActivated` stays `false` — dispatch is test-only engineering, not real-ride readiness. The cash cap remains unenforced until WP13, WP09's 8-second jobs poll still makes a 15-second lease barely reachable for real clients (acceptance always revalidates server-side, so late delivery degrades to missed offers, never wrong ones), and production PostgreSQL cutover remains gated by the earlier packets.
