## Evidence, coverage and policy

`service_areas` and directed `route_permissions` are append-only versions by operator-provided key. Each records service and vehicle classes, required permit keys, validity, reviewer, reason and an opaque provenance reference. Areas use valid nonempty SRID4326 multipolygons; corridors use the same type. SQL GiST indexes are present. API coordinates are explicitly **longitude,latitude**; only2D bounded geometries are accepted.

The latest version of a key is authoritative, including suspension. Old approved geometry cannot become an implicit fallback. Pickup/destination must be covered by their respective approved areas, and **every point** of the operator-assessed route must be covered by the approved directed corridor. `ST_Covers` includes boundary points. Route endpoints must equal confirmed order coordinates; neither geocoding nor a city circle can move a booking into eligibility. From/to area IDs are directed and version-specific. Coverage validity must extend through the conservative planned finish. This interval can represent the operator-approved operating shift; recurring weekly hours are not inferred.

Any area/corridor revision increments the policy revision and disables activation. An admin must explicitly sign the revised matrix with provenance/reason before measured work resumes. There is no seeded legal interpretation of Gaza, East Jerusalem, cross-border travel, city boundaries or permits. A routing response and the synthetic test polygons grant no authority. Operator-reviewed route evidence is manually entered here; road-provider integration and restriction revisions remain WP08. Public legal verification is an operational responsibility.

Driver approval, vehicle approval, document checks and coverage are separate records. Driver/vehicle lifecycle supports draft, submitted, under_review, approved, changes_required, rejected, suspended and expired. `verification_checks` retains reviewer, issuer, outcome, method, validity and provenance. Manual in-person and operator-registry checks are supported; there is no upload/identity scan field. Extra fields such as `identityScan` are rejected. Use opaque case references; private scans/storage integrations are not created. Audit/free-text provenance is restricted to authenticated operator/self evidence responses and excluded from public events.

Newest applicable check wins; a newer invalid/rejected/suspended check cannot revive an older approval on that subject. Driver-license, vehicle-registration and vehicle-inspection checks are required. Vehicle checks bind the measured vehicle revision. For each required permit, the latest applicable negative on either driver or matching-revision vehicle blocks; otherwise current approved driver or matching-revision vehicle evidence must be valid through finish. No permit evidence is invented. Legacy account approval never creates measured approval. Legacy phone/email/role/vehicle/status edits invalidate measured driver revisions and put identity/vehicle changes back under review; blocking marks measured approval suspended.

`eligibility_audit`, verification checks, area versions and corridor versions reject row edits/deletes. Operator actions store actor/reason/provenance/time and append a minimized WP04 `eligibility.changed` event with IDs/actions only, with transactional outbox intent. No proof, phone, exact geometry or free-form operator text is put in those events. Existing private security events retain the authorized custody recovery reason.

## Measured reservations and retained work

Vehicles have real plate/class, passenger seats, usable grams and cubic centimetres, length/width/height in millimetres, piece bound and equipment. These integer units avoid floating capacity rounding; kg = grams/1000 and m³ = cm³/1000000 for display. Values are operator measurements, not class-based invented capacities. The legacy user's class must agree with the selected vehicle.

Each enrolled driver selects a reviewed vehicle. Multiple drivers may reference the same vehicle. New work locks current policy, driver approval, vehicle and vehicle-run revisions, then checks both drivers' commitments. Ride/freight exclusivity covers the shared physical vehicle as well as the installed driver guard. The existing200-count guard is retained, with an additional measured piece ceiling of at most200. It never establishes physical feasibility by itself.

Every accepted planned pickup reserves its entire measured weight/volume/pieces until the order finishes or is returned, even before collection and even after an earlier planned dropoff. All accepted orders on that vehicle contribute. The conservative policy intentionally gives no capacity reuse credit between stops. Pickup/dropoff rows retain pickup-before-dropoff positions, service times, windows and resource deltas. New stops append after the latest reserved planned finish plus a fresh, revision-bound operator-attested approach leg. Overdue unfinished work rejects new insertion with prior_run_overdue; planned time is never automatically renewed. Driver/vehicle/check/coverage validity must span that finish. Missed windows, seats and missing equipment reject new work.

Packing policy is explicitly `fixed_axes_no_stacking`: orientation is fixed; width/height must each fit; each piece has its own longitudinal slice; summed slice lengths must fit. This conservative sufficient condition rejects many otherwise packable arrangements. Volume, dimension sorting or rotation heuristics are never treated as packing proof. Automatic insertion, optimized packing, road-time prediction, stop resequencing and shared passenger rides remain disabled. Operator route/service estimates and physical measurement need field validation; these tests do not prove real-world timing or legal coverage.

Negotiated measured offers snapshot driver/vehicle/policy/requirements/run revisions. Changes invalidate their acceptance, including changes made through legacy account editing. Invalid-price attempts cannot refresh an old snapshot. Existing negotiated offers retain their **ten-minute** lifetime; WP07's future15-second dispatch lease is not applied to them. Direct measured acceptance re-evaluates and locks current evidence/resources rather than trusting client cached eligibility. Protocol1 direct acceptance/offers require expectedRequirementsRevision; a supplied stale revision always rejects before assignment/reservation. Opt-in jobs/detail reads expose only the safe immutable measuredScope for that revision. Existing WP04 `expectedVersion` still fences order versions when using command IDs.

Protocol opt-in is `capacityProtocol:1` on installed offer/accept actions, with `expectedRequirementsRevision` echoed from opt-in job/detail measuredScope. Once enrolled, the server always enforces measured eligibility even if that field is omitted; an installed request cannot downgrade it. Orders with operator-measured requirements require enrollment. Nonenrolled, unmeasured installed flows remain an explicit compatibility cohort until approved policy/client rollout. That cohort is **not claimed capacity-safe**. Linking its vehicle prevents incompatible shared-vehicle or unknown-to-measured mixing.

Unknown active legacy loads raise an inspection marker/audit and block adding measured work. They keep the same custody, IDs, proofs/attempts, sender-only return code, commissions and cash records. The operator may measure an already accepted legacy order in place; it becomes a `legacy_inspection` reservation without legal reapproval or reassignment. Even an inspected overload is retained in full and blocks insertion. After every unknown item is accounted for, a separate approved physical-inspection check may clear the marker; the resource and packing guards still apply. Existing accepted requirements cannot be edited into a smaller load.

Expiry/suspension closes new work while retained custody remains actionable through existing proof flows and the audited admin recovery endpoint. Recovery supports hold, return, and confirmed sender return under expected order version. Returns keep the same order/driver/financial fields, use a separate sender-only return code and reset proof attempts only when entering a new return as the installed behavior requires. Neither reservations nor cash are silently deleted. Driver switching to another vehicle with active custody is denied. Historical reservations/stops remain for audit; active order lifecycle determines occupied resources.

| Method/path | Required body / result |
|---|---|
| GET `/driver/eligibility` | Driver only. `{available,policy:{revision,activated},driver,vehicle,defaults}`; SQLite has `{available:false,activated:false,reason,defaults}`. Null driver/vehicle means evidence absent. Read does not assert eligibility. |
| POST `/driver/eligibility/activate` | Driver only; `{vehicleId,expectedRevision}`. Requires currently eligible reviewed evidence and active policy; persists enrollment and returns `{activated:true,driver}`. Enrollment cannot be removed through a legacy request. |

| POST `/admin/eligibility/areas` | `{key,state,services,vehicleClasses,requiredPermits,validFrom,validUntil,geometry,reason,evidenceRef}`. State approved/suspended; GeoJSON Polygon/MultiPolygon. Appends `{id,version}`. |
| POST `/admin/eligibility/routes` | Same shared fields; replaces geometry with `{fromAreaId,toAreaId,corridor}`. Appends directed `{id,version}`; reverse permission requires its own approved record. |
| POST `/admin/eligibility/vehicles` | `{plate,class,state,seats,usableGrams,usableCm3,lengthMm,widthMm,heightMm,maxPieces,equipment,validUntil,reason,evidenceRef}`. Returns private reviewed row. Classes bicycle/motorcycle/car/van/truck. |
| PATCH `/admin/eligibility/vehicles/:id` | Full vehicle body plus `{expectedRevision}`. Increments revision, invalidates previous vehicle documents/offers, preserves reservations. It cannot clear unknown-load inspection by itself. |
| POST `/admin/eligibility/drivers/:id` | `{vehicleId,state,validUntil,expectedRevision,reason,evidenceRef}`. First review expects0. Later reviews require the current revision. Records relationship; never changes legacy user approval or silently unenrolls a driver. |
| POST `/admin/eligibility/checks` | Exactly one of driverId/vehicleId; `{kind,permitKey?,outcome,validFrom,validUntil,method,issuer,reason,evidenceRef}`. Kinds driver_license/vehicle_registration/vehicle_inspection/permit. Outcome approved/rejected/invalid/suspended. Method manual_in_person/operator_registry. permitKey only for permit. Reviewer derives from auth. |
| POST `/admin/eligibility/orders/:id` | `{expectedRevision,items,seats,equipment,rotationPolicy,route,routeSeconds,serviceSeconds,pickupAfter,pickupBefore,dropoffBefore,reason,evidenceRef}`. Searching orders can be revised; unknown active legacy orders can be inspected once in place. |
| POST `/admin/eligibility/orders/:id/recovery` | `{action:'hold'|'return'|'confirm_return',expectedVersion,reason,evidenceRef}`. Active custody only; returns `{id,status,driver_id,version}`. All actions audited and retain financial/custody identity. |
