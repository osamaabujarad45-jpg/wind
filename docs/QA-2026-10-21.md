# Wind review — 21 October 2026

## Live-tracking pass — 22 October 2026

A review of the live map, the live push and the GPS pipeline against Uber's
behaviour found and fixed real defects. Everything below is verified by the test
suite and the browser journeys; the device matrix in the workflow document is
unchanged (a rebuilt native APK still has to be exercised on the A53).

| Defect | Change | Verification |
|---|---|---|
| One wild fix that won on accuracy became the yardstick: the next real fixes were rejected and the marker froze kilometres away for minutes | `driver_locations` keeps the last *plausible* fix (`good_lat/good_lng/good_at/good_acc`); a fix is measured against it and against the fix on screen, and only a plausible one advances it | `tests/map.test.mjs` posts a 50 km outlier and then the real fix, which must be accepted and must put the marker back |
| A reassignment left the held live request asleep on the old driver, and the answer carried no driver identity | Waiters are keyed by order, the driver's next fix wakes them, and every answer names the driver (`driverKey`); a request for another driver gets no coordinates and a `driverChanged` flag | `tests/map.test.mjs` and `tests/share.test.mjs` (the public long-poll had no test at all before) |
| The public and authenticated live endpoints had no rate limit and no global socket budget | Per-user and per-link limits, 20 watchers per order, 200 in total, `server.maxConnections` | `tests/map.test.mjs` keeps the 20-watcher rule; the load test shows the limits biting under a synthetic hammer |
| A contended write blocked the whole event loop for five seconds (one health request took 5.2 s behind a writer lock) | The busy wait is a quarter of a second and a contended write answers with a retryable 503 | Load test: "Long external writer lock returns retryable503 in 299ms; unrelated health request takes 197ms" |
| The route cache counted entries, not geometry (2000 full routes would be ~500 MB) | The cache keeps a point budget (200k points) and evicts the least recently used route | `tests/route.test.mjs` still caches and re-routes on a moved checkpoint |
| The map zoomed and jumped on every fix; the camera never followed the car at street level | Web, Android and iOS ease the camera with the car at a fixed zoom; a user gesture still wins, with a recenter button | Browser scenarios (15 groups) and the Android map bridge |
| A working map was replaced by the diagram when the tiles were slow | The page reports "drawing" as soon as the style is parsed; the app keeps the map and waits for the tiles | Android map scenario |
| The accuracy halo jumped ahead of the marker, and a stale fix kept a bright route line | Halo and approach line follow the interpolated position; a stale fix loses the approach line and the halo fades | Browser scenarios |
| One dropped poll marked a fresh fix stale and hid the ETA | Staleness follows the fix's age only; a middle band (15 s) says the signal is weak; the ETA stays | `tests/presentation.test.mjs` covers the three states |
| The public page blanked on a transient error and lost the driver after 120 s | The last answer stays with an "updates paused" note, the last known fix is kept faded, and the leg follows the real status | Browser scenario (recipient tracking) |
| Polling and the long-poll ran in the background, retried forever on 401/404 and hammered the server | Polls pause while the app is backgrounded, back off after a failure and stop on a refusal polling cannot fix | `npm run test:load` (throttles and live push under load) |
| iOS ignored the route, treated a tap as a pan, had no map failure path and no heading without a device bearing | The iOS map follows the car, shows the diagram with Retry when it never loads, derives the direction of travel from two fixes, and reports a failed pin map | Typecheck, lint; an iPhone run is still listed as outstanding |
| A customer could set a 6-character password the server refuses (12 required) | The profile form requires 12 to 100 characters, like sign-up | `tests/api.test.mjs` (server rule) |
| The admin settings offered a shared-delivery discount that no booking can use | The control is gone (pooling is disabled) | Admin settings screen |
| 23 API refusals had no translation and showed "something went wrong" | Every reachable refusal has its own Arabic and English words | `src/copy.ts` |

### Email status

The server talks to `POST /accounts/{id}/email/sending/send`. A probe with the
account's token returned `email.sending.error.email.sender_not_configured`: the
token and account work, but **the Cloudflare account has no domain on Cloudflare
DNS**, and Email Service only sends from an onboarded domain. Until the owner adds
a domain and onboards it (Email Service → Email Sending), the app hides every
email flow and behaves as before. Then set `WIND_EMAIL_FROM`, `CLOUDFLARE_ACCOUNT_ID`
and `CLOUDFLARE_EMAIL_TOKEN` (Email Sending: Edit) on the API.

# First pass: Wind scenario review — 21 October 2026

## Result and scope

The local customer, driver, recipient and administrator journeys passed against
isolated SQLite databases. The review includes real browser interactions, the
actual API, map downloads and the connected Samsung A53's Chrome. It does not
certify a new native APK, iOS device build, production deployment or real payment.

Workspace: Expo SDK 57, Android version 1.0.12 / code 13. The attached A53 had
1.0.11 / code 12 installed; physical checks used the latest local web export in
Chrome. No production orders, external messages, payments or deployments were made.

The desktop scenarios use controlled GPS samples and a local OSRM fixture. MapLibre,
its worker, styles, fonts and OpenFreeMap tiles load from their actual URLs. Route
fixture success establishes application behavior, not real-road travel accuracy.

## Fixes

| Issue | Change | Verification |
|---|---|---|
| Fresh driver GPS could be discarded while an older upload was pending | Keep the newest pending browser fix and upload it after the in-flight request | Browser regression delays the first, rejected pre-assignment fix, injects a fresh point, then verifies the customer receives it |
| An HTTP 200 for an ignored GPS sample incorrectly counted as successful sharing | API returns an additive `accepted` flag; web and native clients acknowledge only accepted samples; native malformed receipts remain retryable | API, background delivery and registered native-task tests cover old, reordered and accepted fixes |
| Native pickup permission could leave the location request waiting indefinitely | Include permission acquisition in the pickup deadline and cancellation; late permission cannot start a watch | Pickup tests cover permission timeout, late grant, denial, successful grant and watch cleanup |
| Android map said ready while tiles were still loading | Send the WebView `ready` signal after MapLibre's load event; retain the failure deadline through tile loading | Delayed tile downloads reproduced the old failure; the scenario now requires no premature ready signal |
| Ride boarding used parcel pickup wording | Add English and Arabic passenger-boarding text to the ride action | Browser ride journey boards and completes without a parcel handover code; typecheck/lint |
| Missing Router linking dependency and SDK patch mismatches | Install the SDK-compatible `expo-linking` dependency and update Expo/location/router/splash packages with Expo install | Expo Doctor 21/21; web export and Android/iOS Hermes exports; typecheck/lint |
| Repeatable cross-role checks were missing and backlog/docs were stale | Add browser and physical Android test commands; distinguish historical plans from verified behavior and unfinished work | Scenario outputs below; README commands run against isolated local data |

Existing in-progress map and pickup-selection changes were retained and exercised,
including chosen-city gating, city selection from a GPS fix, removal of an old
landmark when the city changes, accuracy handling, map framing and retry behavior.
