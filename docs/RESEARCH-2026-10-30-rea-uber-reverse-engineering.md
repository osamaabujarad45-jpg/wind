## 1. Answers first

1. **REA is real, active, and not Uber-specific.** "REA: Reverse Engineer Anything" — "Reverse engineer anything with agents, from app behavior down to native binaries" — is an MIT-licensed TypeScript project: one MCP server + one CLI (`rea`) + agent workflow files (a "skill"), created 2026-04-14, last pushed 30 Oct 2026, ~411k stars / ~103k forks [W github.com/morluto/rea, rea.tools]. Its showcases are Aegis (Android authenticator), Notion (Electron), DX-Ball (native), Windows Calculator, Chrome's dinosaur game — no Uber case study exists on the site or repo [W; absence noted, not proof of absence].
2. **Against an Android APK, REA is a static-decompilation harness with a dynamic side.** The APK workflow wraps headless JADX (pinned `jadx-headless-mcp 0.7.1` JAR, JDK 17+ required): manifest projection (activities, services, receivers, providers, intent filters, exported/enabled flags, permissions), class search, member inventories, decompiled Java or smali per method, incoming-reference tracing, JNI-binding attribution to bundled ELF libraries, and a component/native-bridge graph [W docs/android-analysis.md]. The dynamic side is caller-supplied `adb` device inspection (packages, processes, logs, screen captures, file transfers) and a Frida harness that loads **caller-authored** scripts into a running process — REA does not provision frida-server and does not ship hooks [W docs/frida-instrumentation.md, docs/adb-device-analysis.md].
3. **REA handles R8/ProGuard obfuscation only if you hold the build's `mapping.txt`.** You pass `mapping_path` and REA reports per-symbol `mapped / ambiguous / unmapped` plus the map's `pg_map_id` — which it "reports, not compares" [W docs/android-analysis.md]. Uber does not publish mappings, so on the real Uber APK most app-code symbols should be expected `unmapped` [X — expected for any R8-obfuscated release, not verified against a real Uber APK, and we did not obtain one].
4. **The Uber consumer app is a hard target, and most of what matters is not in the APK.** Public, Uber-sourced knowledge says the mobile architecture is RIBs (Router/Interactor/Builder, business-logic-driven trees, hierarchical DI, Rx state flow — Apache-2.0, with Kotlin/Compose/Coroutines extensions) [W github.com/uber/RIBs], and Uber's own React Native use was the UberEATS **Restaurant Dashboard** (merchant side), not the consumer apps [W uber.com blog, 28 Mar 2017]. Pricing, matching, dispatch and fraud logic are server-side and invisible to any static APK analysis. Protections expected on a ride-hailing app of this class (R8 obfuscation, native libraries, TLS pinning, Play Integrity) are listed in §4.3 as [X] — plausible but unverified, because verifying them on Uber's app is itself the activity that needs authorization (§5).
5. **The lawful lanes, in order of usefulness to this repo:** (a) run REA on **our own** Fastship release APKs as a pre-release self-audit (permissions, exported components, secrets in resources/strings); (b) study Uber's **public** engineering artifacts — RIBs, the Android-monorepo blog posts — for architecture lessons (§6); (c) practice on apps we are authorized to examine (open-source like Aegis, per REA's own showcase); (d) if the owner ever wants security research on Uber itself, the only sanctioned lane is Uber's HackerOne bug-bounty program and its safe-harbor terms [W hackerone.com/uber]. Anything else is out of scope for this repo's work.
6. **Practical gate before any run:** REA needs Node `22.x (≥22.23.4) / 24.x (≥24.22.1) / 26.12.1+` plus npm [W README], a **full JDK 17+** (with `jdk.compiler`; a JRE is not enough) for the APK bridge, and on Linux a procps-compatible `ps` [W docs/android-analysis.md]. Static decompilation of a ride-hailing-sized APK is heavy work → K5 per owner policy, and K5 is currently unreachable [R AGENTS.md]. Nothing blocks reading this research or the self-audit planning in §6/§7 today.

## 2. What REA is (the repo and package)

- **Repo:** [github.com/morluto/rea](https://github.com/morluto/rea) — description above; MIT; TypeScript; default branch `main`; homepage [rea.tools](https://rea.tools); topics include `mcp`, `model-context-protocol`, `reverse-engineering`, `ghidra`, `hopper`, `static-analysis`, `claude-code`, `codex` [W GitHub API, retrieved 30 Oct 2026].
- **Distribution:** npm package [`rea-agents`](https://www.npmjs.com/package/rea-agents), latest **6.8.0**, MIT [W registry.npmjs.org, retrieved 30 Oct 2026]. Two binaries: `rea` and (from 2.1.0) `rea-agents`, both `scripts/rea.mjs`; the MCP server runs as `node scripts/rea.mjs mcp` [W npm metadata]. Dependencies include `@modelcontextprotocol/server` 2.0.0-beta.x, `ws`, `zod`, `pino`, `isomorphic-git`, `@electron/asar`, `playwright-core`; a `postinstall` step builds `node-pty` (native module) [W npm metadata].
- **Setup into an agent:** `npx rea-agents setup` — choose agents, review, approve; it "adds REA's MCP server and matching workflow instructions, with backups of existing configuration"; restart the agent afterwards. Named supported agents: Claude Code, Codex, Cursor, Gemini CLI, Grok Build "and other agents" [W README]. Global install alternative: `npm install --global rea-agents` then `rea --help`; update via `rea update` [W README].
- **Engine requirements:** Node `22.x (>=22.23.4)`, `24.x (>=24.22.1)`, or `26.12.1+`, plus npm; Linux needs a procps-compatible `ps` on PATH [W README]. Engine history in npm metadata: earliest versions required Node ≥24 only; relaxed to `^22.19.0 || >=24.11.0` by 3.0.0 [W npm].
- **What the "one MCP" connects to:** REA drives inspection engines rather than reimplementing them — Hopper, Ghidra, IDA, or Kuna for native binaries; headless JADX for APKs; caller-supplied Apktool for Android resources; caller-supplied `adb` for devices; tshark/capinfos for pcaps; JEB via a caller-started JEB MCP client (`REA_JEB_MCP_URL`) [W README]. Commercial analyzers must be legally licensed; setup can optionally install Hopper with approval [W README]. Download REA only from the official repo / rea.tools / npm — the README warns against impersonating copies [W README].
- **Evidence model:** every workflow returns "findings with their evidence," artifact-bound; MCP helpers include `inspect_analysis_view`, `export_evidence_bundle`, `update_analysis_settings` [W README, docs/android-analysis.md].

## 3. REA's Android capabilities in detail (what an agent gets)

### 3.1 Static APK analysis (`docs/android-analysis.md`) [W throughout]

- **Engine:** headless JADX kept as "an unmodified, commit-pinned Git submodule", bridged from `src/android/`; `jadx-headless-mcp 0.7.1` JAR pinned by SHA-256 (`6e5eacf5…775`), configured via `REA_JADX_MCP_JAR` and optional `JAVA_HOME`. Full JDK 17+ including `jdk.compiler` is required to build the bridge.
- **Static only:** "the APK is never executed"; signature verification is "explicitly `not_performed`".
- **MCP tools / CLI verbs** (exact names): `inspect_android_package` / `rea inspect-android-package` — decoded manifest, SDK levels, permissions, class/resource counts, and a **manifest component projection** (activities, services, receivers, providers, `intent_filters`, `exported`/`enabled`/`process`); `search_android_classes`; `inspect_android_class` (member inventory, `dex_static_value` for `static final` fields); `inspect_android_method` (decompiled Java **or smali**, overload index, explicit fallback markers such as `native_method`, `abstract_method`, `java_body_unavailable`); `trace_android_references` (incoming static references, `direct_invokes`); `inspect_android_jni_bindings` (links `ACC_NATIVE` declarations to bundled ELF libraries, with `JNINativeMethod` table attribution); `project_android_application_graph` (component/native-bridge hypothesis graph).
- **Obfuscation support:** pass an absolute `mapping_path`; response carries a `mapping` block (path, SHA-256, header fields like `pg_map_id`, counts, malformed samples) and per-symbol status `mapped / ambiguous / unmapped / unknown(reason=projection-budget)`. Lookups use raw DEX names; the map's identity is "reported, not compared".
- **Budgets and limits (why big APKs are heavy work):** 120 s default operation deadline (`REA_JADX_OPERATION_TIMEOUT_MS`), 30 s bridge handshake, 90 s decompilation cap, 1 MiB manifest/method-text budgets, 4,096-name class pages, 64 MiB mapping cap with 128 MiB index estimate, heap tunable via `REA_JADX_HEAP_MIB`. Explicitly **not** supported: split APKs / `.aab`, signature validation, resource-table semantics, native-library deep analysis, runtime capture.

### 3.2 APK signatures and resources [W README + docs listing]

- `inspect_apk_signature`: v1/v2/v3/v3.1 signers, certificate fingerprints, key rotation lineage — static only.
- Resources via caller-supplied Apktool: decoded manifest, string tables, locales (`docs/apktool-resource-analysis.md`).

### 3.3 Dynamic side [W README + docs]

- **adb device analysis** (`docs/adb-device-analysis.md`): packages, processes, logs, dumps, screen captures, APK/file transfers — "caller-supplied adb (emulator or hardware)". For this repo that maps directly to the physical test phone (`SM-A5360`) policy in AGENTS.md.
- **Frida harness** (`docs/frida-instrumentation.md`): tools `list_frida_devices`, `list_frida_processes`, `start_frida_session`, `load_frida_script`, `resume_frida_session`, `unload_frida_script`, `frida_session_status`, `close_frida_session`; CLI one-shot `instrument-with-frida`. Node bindings are an optional dependency loaded only when a Frida operation runs; **REA does not install frida-server on any target** and scripts are caller-authored, executing "inside the selected target with that process's … authority". Evidence records exclude authentication values and store script digests, not sources. This is an instrumentation *harness* — any specific hooking technique for a specific app is outside this document's boundary (§5).
- **Captures:** HAR/SAZ (`docs/web-network-captures.md`), pcaps via tshark/capinfos (`docs/pcap-analysis.md`), plus an RL-environment builder (`rea environment-build ./session.har ./my-env`) that turns recorded request/response sessions into local test environments [W README]. For Fastship QA this is attractive against **our own** sandbox backend traffic (the `adb reverse` QA setup), not against third-party services.

## 4. The Uber Android app as a target — public knowledge only

### 4.1 What Uber has said publicly [W]

- **RIBs** — "Uber's cross-platform mobile architecture framework": Router, Interactor, Builder; business logic drives the app (a RIB need not have a view); deep logic tree / shallow view tree; hierarchical DI scoping; Rx for parent/child state. Android repo [github.com/uber/RIBs](https://github.com/uber/RIBs) (Apache-2.0, 2017; `com.uber.rib:rib-android:0.17.0`; iOS moved to `uber/ribs-ios`; extension packages for Kotlin, Jetpack Compose, Coroutines). Open-sourced with the Uber Engineering post "Introducing RIBs" (late 2017).
- **React Native precedent:** "Powering UberEATS with React Native and Uber's Mobile Platform" (Uber Engineering blog, 28 Mar 2017) — the UberEATS **Restaurant Dashboard** (merchant-facing) is React Native; RN was a small share of the codebase; the consumer apps are not RN-first [W uber.com/us/en/blog/ubereats-react-native].
- **Android engineering content hub:** uber.com blog Android/monorepo articles (e.g. "android-engineering-code-monorepo") [W search result; individual posts not read this session].

### 4.2 What that predicts a decompiler would see on the consumer APK [W→X chain]

If an authorized static analysis were ever performed, REA's manifest projection and class inventory would legitimately answer: component structure (activities/services/receivers and which are `exported` — always the most interesting attack surface), permission requests, third-party SDK package inventory, RIB framework fingerprints (`com.uber.rib.*` namespaces are open-source and often survive obfuscation of *app* code [X — plausible, unverified]), native library inventory via `inspect_android_jni_bindings`, signature/certificate lineage, and localized string resources. It would **not** answer: business logic (obfuscated without a public mapping), server API semantics (payloads are data, not code), pricing/matching/fraud internals (server-side), and anything gated behind TLS pinning at runtime.

### 4.3 Expected protections [X — none verified this session, by design]

For a ride-hailing app of Uber's class, industry-standard expectations are R8/ProGuard obfuscation of app code, native `.so` components, certificate pinning on API traffic, and Play Integrity attestation. No public primary source for these specifics on the current Uber APK was verified in this session, and we deliberately did not obtain the APK to check. Treat every item here as unverified; §5 explains why empirically verifying them on Uber's app requires authorization.

## 5. Legal and authorized channels (governing section)

- **Uber's U.S. Terms of Use** (last modified 10/12/2026, retrieved 30 Oct 2026) [W uber.com/legal]: users may not "decompile, reverse engineer or disassemble the Services **except as may be permitted by applicable law**"; no derivative works; no "programs or scripts" that unduly burden the Services; no unauthorized access; and — notable for AI-era research — no using the Services "for developing software, including training machine-learning or AI systems, without Uber's prior written permission". The ToS carve-out ("except as permitted by applicable law") is where statutory reverse-engineering rights (e.g., security-research and interoperability exceptions) would live; the precise scope of those exceptions was **not** verified against primary law in this session [X] and counsel should be consulted before relying on them for anything beyond personal study.
- **Authorized security research:** Uber runs a public bug-bounty program on [hackerone.com/uber](https://hackerone.com/uber) — scope "focused on securing user data and company assets", with updates published at hackerone.com/uber/updates; reported bounty ranges are secondary-sourced [W program page; bounty figures secondary]. Any Uber-facing testing from this repo would be under that program's rules, on the physical test phone, with safe-harbor terms read first.
- **REA's own terms** [W README]: use is for "lawful research, education, interoperability, software preservation, and analysis of software you own or are authorized to examine"; commercial analyzers (IDA, Hopper, JEB) must be legally licensed; vulnerabilities in REA go through its SECURITY.md and a DISCLAIMER.md exists in the repo.
- **Concrete no-go list for this repo** (restating the boundary): no pinning-bypass or anti-tamper-defeat writeups; no harvesting of endpoints, keys or credentials from any app we are not authorized to examine; no scripted traffic against Uber production; no redistribution of decompiled third-party code into Fastship (license + copyright; a capability learned from an app is fine, its code is not).

## 6. What Fastship can actually take from this

1. **Self-audit our own APKs with REA before each release.** `rea inspect-android-package` on a Fastship build answers, in minutes: which components are `exported`, what permissions we really declare, what third-party SDKs ship, whether strings/resources leak secrets or internal URLs, and whether the signing lineage is what we think it is. That is a checklist item that fits the existing release-readiness work (the 29 Oct report) and needs no external authorization because the APK is ours.
2. **Adopt RIB-shaped thinking where it maps to Expo Router.** RIBs' core lesson — a deep tree of testable business-logic scopes with a shallow view tree, DI-scoped per feature [W] — translates to RN as: keep feature logic in hooks/stores independent of `src/app` route components, and scope dependencies per route tree. Our structure already leans this way (`src/app` routes thin, logic in `src/`); RIBs is a vocabulary for pushing further, not a port.
3. **The RN precedent de-risks our stack choice.** Uber shipped a production merchant app in React Native in 2017 and grew microservices around it [W]; Fastship's Expo/RN consumer+driver apps on a Node backend are consistent with proven industry practice, not a gamble.
4. **Use the HAR → agent-environment builder against our own QA sandbox.** `rea environment-build` turns recorded request/response sessions into local environments for AI-agent testing [W]. Recorded Fastship QA traffic (our server, `adb reverse` per AGENTS.md) could give deterministic test fixtures for rider/driver flows — an alternative or complement to hand-written mocks.
5. **Practice target:** REA's own showcase (Aegis authenticator APK — tracing the six-digit-code generation and 30-second rotation [W rea.tools]) is the right first exercise to validate the K5 toolchain before any bigger analysis.
