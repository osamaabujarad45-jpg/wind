## Which public Uber behaviors should inform Fastship?

### Takeaway

Public Uber documentation supports efficient network matching, explicit trip state, route-aware ETA, price policies, delivery verification and recovery behavior. It does not disclose enough to reconstruct every internal algorithm. The behaviors below should become independently implemented and measured Fastship contracts.

### Cited Findings

- **PUBLIC:** Uber describes batching nearby rider requests and driver availability for several seconds to reduce collective waiting, rather than simply choosing the physically nearest driver. Road connectivity matters. It also describes avoiding repeat one-star matches, with market availability caveats. [Marketplace matching](https://www.uber.com/ug/en/marketplace/matching/).
- **PUBLIC, historical engineering disclosure:** Uber's 2022 DeepETA description combines road-network/traffic ETA with a learned residual using spatial, temporal and trip-context features. This explains a modeling approach, not current model parameters. [DeepETA](https://www.uber.com/br/en/blog/deepeta-how-uber-predicts-arrival-times/).
- **PUBLIC, historical engineering disclosure:** Uber developed H3 for fine spatial aggregation supporting dispatch/pricing analysis. H3 is an index, not a routing engine or proof a road is traversable. [H3](https://www.uber.com/us/en/blog/h3/).
- **PUBLIC:** Guest Rides documentation exposes processing, accepted, arriving, in-progress and completed states; driver cancellation may cause redispatch or a terminal no-driver result. Its numeric cancellation policies are product/market-specific examples, not Palestine rules. [Dispatch and cancellation](https://developer.uber.com/docs/guest-rides/guest-ride-api-build-guide/dispatch-and-cancellation).
- **PUBLIC:** upfront fare documentation explains a confirmed quote with possible adjustment after substantial changes or material delay. Fastship must publish its own explicit adjustment policy rather than silently copying examples. [Upfront fares](https://help.uber.com/riders/article/how-do-upfront-fares-work?nodeId=5073140f-3d5f-4046-80da-2db9ed7b11b3).
- **PUBLIC:** Uber's optional trip verification uses a four-digit PIN entered by the matched driver before starting. This is a benchmark feature; Fastship should choose its own secure implementation and retry limits. [Verify your trip](https://help.uber.com/en/riders/article/was-bedeutet-%E2%80%9Everifiziere-deine-fahrt%E2%80%9C?nodeId=9a2a4bc6-002b-4461-8e9e-8ea29974795d).
- **PUBLIC:** Uber Direct supports configurable signature, barcode, picture, identification and PIN verification at relevant handoffs. Restricted-item rules vary and should not be inferred for Palestine. [Proof of delivery](https://developer.uber.com/docs/deliveries/guides/proof-of-delivery).
- **PUBLIC:** Uber Direct documents return relationships and delivery state updates; its delivery webhook explicitly includes original/return jobs and verification evidence. [Delivery status webhook](https://developer.uber.com/docs/deliveries/daas/references/api/webhooks/delivery-status-webhook).
- **PUBLIC:** Uber Health webhook guide warns events may arrive more than once and out of order; consumers can refresh the authoritative resource. [Webhooks](https://developer.uber.com/docs/health/guides/webhooks).
- **PUBLIC, historical architecture disclosure:** Uber's fulfillment architecture uses modeled entity lifecycles and coordinated business transactions. Its scale does not imply Fastship needs hundreds of microservices. [Fulfillment architecture](https://www.uber.com/au/en/blog/fulfillment-platform-rearchitecture/).
- **PUBLIC:** Reserve documents prebooking, driver confirmation, arrival and waiting behavior, with rules varying by product/city. [Reserve](https://help.uber.com/en/riders/article/%CF%87%CF%81%CE%AE%CF%83%CE%B7-%CF%84%CE%BF%CF%85-uber-reserve?nodeId=71708d67-bbac-4dda-9d32-53c2509bdd1b).
- **PUBLIC:** Uber Eats documents batched orders from one restaurant serving distinct dropoffs. This is evidence of batching behavior, not disclosure of insertion optimization coefficients. [Batched orders](https://help.uber.com/en/merchants-and-restaurants/article/how-do-multiple-batched-orders-work?nodeId=ad7637cb-1fc0-4902-b097-43105c557ce3).

### Inferences

The remainder is a **DESIGN** specification for Fastship. All formulas, schemas, initial numbers, thresholds, goals and business rules are proposals to validate with Palestine operations and pilot telemetry. They do not claim to be Uber's algorithms. Existing implementation coverage and exact file locations belong to `app_audit.md`.

These are **preserve and extend**, not missing. SDK 57 and existing API paths must remain the baseline. Native push is missing (current push is web-only); durable outbox/event replay, server presence/automatic proximity dispatch, measured vehicle capacity, separate verified vehicles/doc expiry, immutable stored quotes, integer fare records, payment/COD double-entry and local provider integration are material additions. See [local app audit](app_audit.md) for source lines and checks. ## What should Claude implement and how should correctness be proved?

### Takeaway

Build server authority and reliable money/state handling first, then route-aware dispatch and measured operational improvement. Keep passenger transport, delivery and freight as separate product policies sharing identity, location, fulfillment, money and support infrastructure.

### Cited Findings

The proposed contracts below are independent engineering designs informed by the public evidence above; they are not copied vendor internals. Local coverage must be cross-checked against the app audit before coding to preserve working features.

### Inferences

#### D01 — Core domain and ownership

Model `User`, `Session`, `DriverProfile`, `Vehicle`, `DriverSession`, `ServiceRegion`, `Product`, `Quote`, `Booking`, `Offer`, `Assignment`, `Itinerary`, `Stop`, `FulfillmentEvent`, `PaymentIntent`, `LedgerJournal`, `Payout`, `Evidence`, `SupportCase` and `PolicyVersion`. Shared identifiers are opaque server IDs. Booking stores product (`ride`, `parcel`, `freight`), customer, immutable quote/policy snapshot, locations and revision. Driver sessions distinguish offline/available/offered/assigned/occupied/paused; driver and vehicle approval are separate conditions. Keep product-specific fields typed: rides require seats/accessibility, parcels require pieces/weight/handoff/declared value/COD beneficiary, freight requires dimensions/load class/crew/vehicle capacity/handling/windows. Do not turn one parcel boolean into all product logic. Invariants: one active exclusive assignment per driver; one active assignment per booking; no cross-city accidental allocation; all monetary records carry currency and integer minor units with checked overflow.

#### D02 — Authentication and account lifecycle

Normalize phone to E.164 with explicit country context; preserve display form. Make OTP issuance server-only, cryptographically random, short-lived and single-use. Store an HMAC of OTP + challenge ID with secret held outside client code, attempt count, expiration, resend time and audit reason; return generic account responses. Rate-limit by phone, IP and device using conservative shared limits and abuse escalation. A verified OTP proves phone control, not driver identity. Use short-lived access tokens with rotating refresh families; detect refresh reuse, revoke device or all sessions, and support logout/recovery, phone change with re-verification, role change and account deletion workflow. Admin accounts need stronger authentication and server permissions. Initial pilot hypothesis: 5-minute OTP validity, 5 attempts, 30–60-second resend cooldown; test real SMS delivery and false blocks before release. All endpoints reject expired/replayed challenge, revoked role and user-supplied role escalation. Keep development/test OTP isolated by environment; production startup must reject a bypass flag.

Migration delta: preserve existing scrypt passwords, hashed tokens, verification/reset flows and SecureStore behavior. OTP is an optional phone-verification/login extension after selecting a real local provider. Do not force existing users to re-register or replace working identity with mock SMS. Shorter/rotating sessions require a compatible migration, active-device revocation and explicit recovery path.

#### D03 — Driver and vehicle eligibility

Onboarding lifecycle: draft -> submitted -> under_review -> approved OR changes_required/rejected -> suspended/expired. Documents have type, issuer, expiry, review history and restricted storage; vehicle inspection/capacity and legal operator permissions are recorded independently. Availability eligibility is computed server-side from current approval, document expiry, vehicle match, service zone, settlement/debt policy and active duty restrictions. Suspend future matching immediately on expiry; define an operations workflow for an already active trip instead of abandoning the passenger. Every approval/override has named operator, reason and audit timestamp. Avoid automatic biometric or criminal-background claims until a lawful supported vendor/process exists.

#### D04 — Location ingest and battery/network behavior

Location sample envelope: `{deviceSessionId, seq, recordedAt, lat, lng, horizontalAccuracyM, speedMps?, headingDeg?, source}`. Server adds `receivedAt`; validates coordinate bounds, sample age, monotonic sequence per session, impossible jumps and plausible accuracy without treating GPS noise as conclusive fraud. Persist latest accepted position and enough raw evidence for reconciliation; map presentation may interpolate but must never create payable distance. Offline device queues bounded signed-in session samples and commands with stable IDs; on reconnect upload by sequence, discard expired location for current matching while retaining permitted historical context. Server acknowledgments distinguish accepted/deduplicated/rejected. Show location freshness, retain a separate last-known marker and stop claiming live tracking when stale.

Pilot hypotheses: active movement every 3–5 seconds or meaningful displacement, waiting every 10–15 seconds, no idle customer continuous tracking; available driver matching requires sample <=20–30 seconds old. Tune using real Android/iOS battery and weak-network tests. Sending more frequently than device/background execution allows is not a guarantee. After missed heartbeat, unavailable for new assignments; an active job remains recoverable and support receives a stale-tracking signal. Test app kill/relaunch, foreground/background, permission revoked mid-job, clock skew, out-of-order batch, loss of connectivity and low-power mode on physical devices.

#### D05 — Geocoding, addresses and serviceability

Store structured address plus Arabic/English free text, landmark, building/floor/unit, contact instructions, coordinates, provenance, precision/confidence and chosen entrance/pickup point. Geocoding disagreement requires user confirmation; do not move a known building to a nearby city to satisfy routing. Serviceability = pickup polygon AND destination corridor permissions AND product/vehicle eligibility AND operational hours/capacity. Boundary rules use one deterministic geometry policy with versioned zones and an exception workflow. H3/PostGIS coarse candidate selection may accelerate lookups; exact polygon/corridor checks remain authoritative. Test duplicate names, transliteration, rural landmarks, apartment access, boundary points and addresses without street numbers.

#### D06 — Palestine checkpoint and closure policy

Maintain versioned road restrictions with directed geometry/edge IDs, affected vehicle/products, validity interval, source, last confirmation, confidence, status (`open`, `closed`, `restricted`, `unknown`) and operator review. `unknown` or stale is not equal to open. Route result records provider version, restriction version, timestamp and feasibility decision. If a corridor closes after quote, re-route and estimate delay; if no verified feasible route remains, pause assignment/request reconfirmation or cancel through an explicit no-fee/exception policy. Passenger/driver support must be able to stop/replan an active job. Never market a route as safe or promise that an app knows live checkpoint conditions. Crowd reports need corroboration, expiry and moderation; do not automatically publish identifiable movement reports. Route uncertainty should widen ETA intervals or prevent a guaranteed booking. Test conflicting reports, no data, stale update, reverse-direction restriction and closure during pickup/in-progress.

#### D07 — Routing, travel distance and ETA

Use road-network routing and a duration matrix for the small shortlisted candidate set; Euclidean distance is only a coarse search bound. Cache only where map-provider terms permit, with time bucket/product/vehicle and restriction-version keys. Pickup ETA = dispatch latency estimate + driver road travel + pickup-access allowance. Delivery ETD = remaining drive + known stop service times + handoff allowance + delay adjustment; freight adds loading/unloading. At first use provider baseline plus empirical zone/time median bias and quantile intervals. Later train residual model `ETA = max(0, baselineETA + f(originZone,destinationZone,hour,weekday,vehicle,jobStage,traffic,checkpointState))`; never train on future information or leak one job across train/test sets. Monitor MAE, median/p90 absolute error, promised-window coverage and error by geography/network/product; a model ships only if temporal holdout and shadow mode improve over baseline. Recompute on material route/stage changes, not each animation frame. Provider outage uses a clearly degraded last route or blocks fresh precise quotes; straight-line distance must not become a normal billable road price.

#### D08 — Immutable quotes and pricing

Represent each quote as `{quoteId, expiresAt, currency, lineItems, routeSnapshot, routeVersion, policyVersion, product, scope, limits, cancellationPolicy, adjustmentPolicy}`. Sample recommended equation in integer-money-safe arithmetic: `subtotal = max(minimumFare, baseFare + distanceRate*billableKm + timeRate*billableMinutes + productSurcharges)`; `total = subtotal + reservation/handling/waiting/tolls + tax - fundedDiscount`. Clearly define whether surge multiplies only base transportation or selected components; never multiply tax or tip accidentally. Currency rounding happens once per policy-defined line, and line sum must equal total. Rides can use an upfront guaranteed-scope price; parcels use size/weight tiers and returns; freight can use negotiated accepted offers with expiry and scope. Destination/stop change obtains a new quote revision and explicit customer acceptance; preserve the previous price history. Idempotent booking creation consumes a valid quote without generating different totals on retries.

Do not introduce opaque surge before demand telemetry and local pricing policy exist. Initial fixed rates with operator-managed versioned zones are sufficient. Future proposed smoothed surge: `ratio = weightedUnservedDemand / max(eligibleIdleSupply, supplyFloor)`; `target = clamp(1 + alpha*max(0, ratio-targetRatio), 1, cap)`; smooth over time and neighboring cells, apply hysteresis, movement rate limit and minimum sample size, and freeze multiplier in the quote. Prevent duplicated requests/artificial location signals from inflating demand. Log explainable factors; disaster/emergency controls can freeze surge. No model based on protected traits, battery level, desperation or guessed willingness to pay. Simulate oversupply/undersupply/no supply, boundary oscillation and attacks; confirm quoted prices do not change while waiting.

#### D09 — Dispatch candidate generation

Candidate pool = approved eligible drivers whose fresh location lies within the permitted road-service region; product vehicle/seats/cargo limits match; driver is not paused, already exclusively assigned, blocked by safety pair or outside financial policy. Use spatial index to retrieve coarse nearest candidates, then route-time matrix and restriction feasibility. Expand search gradually only within published pickup-time ceiling, never across inaccessible corridors. Exclude recently declined/timed-out same request for a cooldown; driver refusal is not a reason to silently lower safety checks. Distinguish automatic dispatch from negotiated marketplace bidding: passenger standard rides can auto-dispatch, while freight/selected parcels can use explicit quote/offer competition and customer choice. Policy is per product and shown consistently in booking semantics.

#### D10 — Dispatch ranking and assignment optimization

Start with deterministic ranked sequential offers, measurable and debuggable. Proposed cost in seconds: `C(driver,request) = pickupETAsec + lateRiskPenaltySec + deadheadPenaltySec + compatibilityPenaltySec - cappedIdleCreditSec`. All weights are documented versioned tunables; infeasible pairs are removed, not merely penalized. Do not rank solely by map distance or star rating. Pilot with fairness cap so idle credit cannot create a long/infeasible pickup. At higher concurrent demand introduce 1–3-second microbatches as an experiment, minimizing `sum(Cdr*xdr) + unservedPenalty` with `sum_d xdr<=1`, `sum_r xdr<=driverCapacity`, binary assignments and wait-age/service constraints. Use min-cost bipartite matching or bounded min-cost flow; benchmark solve deadline and fallback to deterministic ordering. Publish fairness/earnings and cancellation metrics to detect concentration. Uber's public material does not disclose this exact cost function or interval.

#### D11 — Offer lease, race safety and retries

Offer states `issued -> accepted | declined | expired | revoked`; includes offer ID, booking revision, driver session, lease expiry and opaque nonce. A notification is only a hint. Acceptance transaction locks/checks booking, driver and live offer, compares expected revisions, checks server-time expiry, claims both resources, writes assignment and outbox event, commits; uniqueness constraints enforce both invariants even across processes. Return conflict for late/double acceptance. Initial hypothesis: 15-second offer TTL, at most 3 sequential rounds within 60–90-second customer search ceiling; tune with drivers. Expiry/retry is a durable worker action, not a phone timer. Retry only while booking remains searchable, scope unchanged and no live assignment exists. Worker restart reconstructs unfinished leases; duplicate expiry messages cannot cancel a later accepted offer. Before widening search, recompute route availability and ETA. Terminal no-supply frees preauthorization and offers explicit retry/schedule behavior.

Acceptance, cancellation, quote-scope change and timeout all compete through the same booking revision and transaction boundary. Clock authority is database/server time with monitored clock synchronization; client time is metadata only. If cancellation wins, later acceptance fails; if acceptance wins, cancellation applies the assigned-stage policy. Lease release is conditional on the same offer/assignment ID and revision, never an unconditional `driver=available` update that might free a driver newly committed elsewhere. Current same-order atomic SQLite claim is a valuable baseline; multi-instance database constraints and driver-resource checks extend it. For parcel runs, capacity reservations are a locked/versioned resource with a different invariant from exclusive ride/freight allocation.

#### D12 — Passenger trip state and guards

`draft -> quoted -> requested -> searching -> assigned -> driver_en_route -> arrived -> in_progress -> completed`; alternative terminal branches `customer_canceled`, `operator_canceled`, `no_supply`, `failed`. Keep payment state orthogonal. Every transition has actor/role, allowed prior state, expected version, guard, reason, timestamp and idempotent command ID. Arrived requires plausible recent driver proximity OR explicit audited poor-GPS exception; start requires matched driver plus rider PIN where enabled, no server trust of a client boolean. PIN stored as hash, limited attempts, no PIN in logs or driver prearrival payload; authorized support recovery is audited. Complete requires allowed state and final fare/evidence settlement proposal. Cancellation after start is a safety/early-end workflow with reason and support, not rollback to searching. One booking cannot go back from completed to active. Driver cancel before pickup may redispatch preserving booking with new assignment ID and timeline; once passenger onboard, transfer requires support and new consent.

#### D13 — Pickup, waiting, cancellation and no-show

Waiting clock starts from server-confirmed arrival with trustworthy recent proximity and optionally customer notification acknowledgment. Pause/dispute clock for stale GPS or incorrect pickup. Versioned city/product policy defines grace period, per-minute waiting, maximum, customer cancellation reason waivers, driver no-show evidence and fee cap. For prototype use nonpunitive clear defaults until operations approves fees; never copy Uber's US/UK numeric rules into Palestine. Cancellation decision function returns `{allowed, feeMinor, payeeAllocation, refund/preauthAction, reasonCode, evidenceRefs, policyVersion}`. Avoid charging both cancellation and an overlapping wait charge unless policy explicitly justifies distinct time. Test simultaneous cancellation/acceptance, no-show with remote driver, driver not moving toward pickup, wrong entrance, already closed route and customer accessibility delay exception.

#### D14 — Parcel chain of custody, proof and returns

Parcel states: `requested -> searching/offer_selection -> assigned -> to_pickup -> at_pickup -> custody_accepted -> to_dropoff -> at_dropoff -> delivered`. Failure adds `handoff_failed -> return_required -> returning -> returned`, or explicit loss/damage case. A canceled task with driver custody cannot simply disappear. Each handoff checks item ID/barcode/pieces, parties, time/location and policy-selected proof. PIN validates recipient knowledge; photo confirms placement; signature acknowledges a named person—none alone conclusively proves contents or condition. Evidence uploads use restricted short-lived upload authorization, limits, checksum, malware/type validation and private object access. Completion command references uploaded evidence IDs and required verification results; server rejects missing proof or double-use. Recipient contact timeout and permitted leave-at-location/return rules are explicit before pickup. Create linked return leg with quote/cost responsibility, expected route, proof and cash liability; do not mutate the original successful custody record. High-value/fragile/restricted goods require explicit policy; exclude unsupported categories.

#### D15 — COD, customer cash and driver settlement

Track transportation fee, goods COD principal, tip, tax and commission as distinct liabilities. Example: driver collects 120 (100 merchant goods, 20 delivery); delivery driver pay 15 and platform revenue 5. Operational ledger records 120 cash held/receivable from driver, 100 payable to merchant, 15 payable to driver and 5 earned platform fee under approved accounting policy; the 100 goods principal is never platform revenue. Net settlement may reduce driver payable against cash owed only with explicit policy and auditable journal. Customer cash handoff has amount due, amount collected, collector and receipt; partial collection/change/recipient refusal needs a case, never fabricate success. Set driver cash exposure and COD job limits using actual unsettled liability; pause new COD when exceeded without losing active jobs. Reconciliation compares booking completion, cash receipts, collector deposits, bank/PSP records and ledger daily. Settlement adjustments create reversing journals instead of editing history. Test transport cash only, prepaid transport + COD goods, partial cash, counterfeit dispute, return with collected funds and duplicate deposit confirmation.

#### D16 — Digital payments, refunds, ledger and payouts

Use a locally supported licensed PSP selected after country/currency/payout validation; do not assume Stripe/Connect availability. Client uses tokenized hosted/mobile payment collection; server creates intent, confirms provider status via signed webhook or authoritative lookup. Payment states: created -> authorization_pending -> authorized -> capture_pending -> captured; parallel void/refund/dispute states with amounts and provider IDs. Trip completion and payment collection are different facts: failed capture creates recoverable debt/support, not a fake incomplete physical ride. Persist every provider request with idempotency key and reconcile uncertain timeout before retry. Verify webhook signature over raw body, deduplicate provider event ID, apply allowed monotonic business transitions and fetch authoritative resource for out-of-order ambiguity. Use integer minor currency units, immutable balanced journals (`sum debit = sum credit` by currency), unique business references and no manual balance edits. Refund <= captured minus previous refunds; tip never counted twice; payout <= available settled driver earnings after applicable holds. Payout states initiated/processing/succeeded/failed/reversed reconcile to provider/bank; a retry cannot pay twice. Gate new payment methods behind sandbox + small real-money reconciliation, not successful happy-path UI.

#### D17 — Realtime, command synchronization and reconnect

Standard command envelope `{commandId, expectedVersion, clientRecordedAt, payload}`; standard event `{eventId, aggregateId, aggregateVersion, type, occurredAt, correlationId, schemaVersion, payload}`. Mutation first commits authoritative state and outbox in one DB transaction; worker publishes events with at-least-once delivery. Consumers inbox-deduplicate. Use event type-specific ACLs so only booking participants and authorized staff subscribe; location sharing expires when job/access ends. Clients maintain last seen version/cursor; ignore duplicate/older event, buffer small gaps, fetch full snapshot when gap persists, rebuild after reconnect. Push notification cannot be trusted as current state and cannot itself accept/start/complete a job. Expose stable `GET /bookings/{id}` snapshot plus timeline; active UI always reconciles from server. Background/terminated app receives permitted push hints; on resume fetch reality before showing actionable controls. Test lost/duplicated/out-of-order events, reconnect after assignment/cancel, app reinstall and queue replay after session revocation.

Snapshots/events must carry `assignmentEpoch`, `itineraryRevision`, `quoteRevision`, `routeRevision` and `restrictionVersion` where relevant. A route computed for an old destination cannot replace a newer route; a previous driver's location cannot appear after reassignment; an old price event cannot overwrite an accepted change order. Cache/provider responses are checked against their input revision before write-back. Money commands additionally bind an exact quote/settlement amount and currency. Add tests with intentionally reordered route/quote computations and assignment changes, not only reordered websocket messages.

#### D18 — Communication and tracking links

Authorize chat per current booking and retain according to documented purpose/retention; rate-limit content, block/report, moderate attachments and never expose customer phone to every marketplace driver. Separate public listing from participant private details. Prefer masked call/relay where provider supports Palestine; otherwise explicitly consent to limited direct number disclosure and scope it to the assignment. Tracking links use high-entropy revocable time-bound tokens; recipients see only necessary job status/approximate position and vehicle facts. Never use sequential booking ID as secret. After completion/revocation token loses live location access. Test guessed IDs, former assigned driver, blocked user, customer phone change and copied expired link.

#### D19 — Safety and risk operations

Emergency/help action should surface current location, trip/vehicle details, trusted contact sharing and local supported contact routes, with accurate availability. Do not promise automated police dispatch or 24/7 human response without the staffed integration. Rule-based operational alerts initially: prolonged unexpected stop, stale tracking, significant route deviation and unresolved handoff; thresholds calibrated per checkpoint context to avoid false alarms. Alert -> ask both parties privately -> provide help -> escalate by staffed policy -> document resolution. A deviation signal is not proof of danger/fraud. Keep access scoped and audited, allow false-positive dismissal, and never let LLM-generated safety judgment cancel transport autonomously. Financial risk signals include repeated OTP abuse, impossible GPS movement, suspicious same-party transfers, excessive promo reuse, fabricated proof and repeated cash shortages; route to review with explanation and appeals. Avoid automatic suspension from sparse/noisy data.

#### D20 — Ratings, blocks, complaints and disputes

Only completed eligible participants can rate once per booking within policy window. Store raw rating and moderation state; compute aggregates with minimum-sample handling rather than letting one rating dominate a new driver. Preserve safety block independently of public star average; exclude blocked pairs in dispatch. Complaint attaches to booking, message/evidence snapshots, category/severity, owner and service deadline. Refund decision, safety decision and rating moderation are distinct permissions/workflows. Status: open -> triaged -> investigating -> action_pending -> resolved -> appealed/reopened. Every action has reason, audit record and notification. For a hostile access incident revoke location/chat immediately while keeping evidence for the authorized case. Test user deletion during dispute, false report, conflicting proofs and partial refund after payout.

#### D21 — Freight and negotiated marketplace

Freight quote captures origin/destination access constraints, load weight/volume/dimensions, pallet/item count, equipment, crew/lifting needs, timing, loading/unloading responsibility, damage/insurance terms and price scope. Capacity feasibility checks volume AND weight AND vehicle/equipment, not just a category name. Offers have expiry, minimum scope and immutable accepted snapshot. Acceptance atomically reserves vehicle/crew and task; change-order requires new quote and approval. Stops include loading, inspection, transport, unload and acceptance proof. Waiting, rescheduling, failed access, partial delivery and return responsibilities are explicit. Do not auto-reassign an accepted specialized freight vehicle to a normal ride. Later optimize partial-load combinations only after dimensional capacity/time-window constraints and custody are tested. Shared ride seats and freight capacity should never be accidentally interchangeable.

#### D22 — Reservations and commitments

Separate requested pickup window, tentative supply planning, confirmed driver commitment and dispatch activation. Server jobs schedule confirmation reminders and pre-dispatch feasibility checks with durable due times; worker restart must catch overdue jobs exactly once logically. Earliest dispatch = pickupTarget - predictedPickupTravel - readinessBuffer; recalculate before activation. No vehicle confirmed means communicate unconfirmed state, not a guarantee. If driver drops or cannot arrive, reassign with customer notice and defined fallback/no-fee cancellation. Store local timezone explicitly and schedule instants in UTC; test Palestine daylight-saving boundaries, customer travel timezone, device clock change and booking edit around worker firing. Reserve does not mean merely delaying an immediate push notification.

#### D23 — Multi-stop and delivery batching

Represent ordered stops with pickup-before-dropoff precedence, stop windows, per-stop service time and capacity delta. Preserve current courier batching/manual run sheet and replace count-only capacity with verified load/stop feasibility. Exclusivity applies to ride/freight and incompatible work, not all parcels. Automatic insertion optimization is disabled in v1. Future-only insertion evaluates added travel, window violations, capacity/custody/incompatibility under a separately versioned bounded policy, locking the itinerary against concurrent additions. Requote customer stop edits. Re-plan closures with support fallback; test precedence, missed pickup, overflow, cancel while cargo onboard and return insertion.

#### D24 — Promotions, referral, subscription and business accounts

Promo eligibility server-side by campaign version, currency, product, geography, valid interval and budget; atomic redemption caps per user/campaign prevent concurrent overspend. Funding source and discount allocation recorded in ledger. Referral qualifies only after settled genuine job, with anti-abuse review and reversal rules. Subscription benefits are entitlement snapshots with purchase/refund/renewal status, never client booleans. Business account has organization membership/approvals, spend limits, cost centers, employee travel privacy and invoice settlement policy. Defer complex programs until unit economics and reconciliation are stable; test stackability, quote expiry, last-budget race, refund and account closure.

#### D25 — Accessibility, guest and household use

Product capabilities explicitly represent wheelchair accommodation, assistance, child-seat/pet needs where offered, vehicle capacity and support notes with user consent. Do not infer medical information. Guest booking separates requester/payer from passenger contact and shared tracking consent; assigned driver sees necessary passenger facts, and changes cannot transfer ownership silently. Support low literacy, Arabic address input and weak connectivity through behavior contracts; Claude decides visual presentation. Avoid turning ordinary delays caused by accessibility into automatic penalties. Minors and specialized transport need launch-specific rules and operator validation before enablement.

#### D26 — Administration and financial controls

Role-based permissions for dispatcher, driver reviewer, support, safety, finance and platform admin; deny by default and require server checks per object/action. Operational tools need queue of unassigned/stale/late/failed tasks, reassignment with history, restricted evidence access, cash exposure, reconciliation exceptions and incident escalation. High-risk refunds/payout or policy changes can require two distinct staff actions above policy threshold. Admin impersonation is time-limited, explicit and audited. Policy edits versioned with preview and effective time; rollback creates a new version. A generic admin role is insufficient for protecting financial and identity records. Audit cannot live only in editable customer records.

#### D27 — Data/privacy, retention and abuse resistance

Data inventory maps each field to purpose, access, retention and deletion rule. Exact location, addresses, phone, documents, chat and proof need separate access controls; analytics gets minimized/coarsened identifiers. Keep precise live location only for operational need, evidence per approved dispute/legal policy, and irreversible deletion/anonymization after applicable holds. Redact auth tokens, OTP, phone, precise location and payment data from logs; no production data pasted to Claude. Signed object access is short-lived; private blobs must not be guessable public files. Export/delete account requests must preserve legally required financial records through pseudonymization and separate access rather than silently deleting balanced ledger. Define retention with local counsel/operational policy; proposed durations are not legal conclusions.

#### D28 — Operations, measurement and resilience

Instrument correlation ID from quote -> dispatch -> state -> payment -> support; log decision reason and policy/model version. Pilot gates: no double assignment, balanced ledger on every journal, no missing accepted custody, authorization tests pass, deterministic recovery of interrupted work. Proposed performance goals subject to measured baseline: non-provider API p95 <500ms, critical command acknowledgment p95 <1s, tracking freshness p95 <10s while connected, search terminal answer <=90s, successful event reconnect reconciliation and no lost committed booking. Availability/capacity targets must match paid Azure configuration; these are product targets, not achieved SLAs. Track quote conversion, accept time, pickup ETA error, cancel/no-supply reasons, driver paid utilization, completion, cash reconciliation age, disputes, gross/net margin, support response and alert false positives. Chaos-test process restarts, storage failover, duplicated queue deliveries, slow routing/SMS/PSP, regional disconnect and restored backup; operations runbook covers manual dispatch and reconciliation.

#### D29 — Concrete service contracts

Recommended API boundary (adapt existing server routes; avoid a needless rewrite): `POST /auth/otp`, `POST /auth/verify`, `POST /sessions/refresh`, `POST /quotes`, `POST /bookings`, `GET /bookings/{id}`, `POST /bookings/{id}/cancel`, `POST /driver-sessions`, `POST /locations/batch`, `POST /offers/{id}/accept|decline`, `POST /bookings/{id}/arrive|start|complete`, `POST /bookings/{id}/changes/quote`, `POST /bookings/{id}/changes/accept`, `POST /evidence/uploads`, `POST /bookings/{id}/proof`, `POST /payments/intents`, `POST /webhooks/{provider}`, `POST /refunds`, `POST /settlements`, `POST /support-cases`. Role and ownership checks sit beside schema validation. Quote creation is rate-limited and optional idempotent; all money/assignment/state mutations require idempotency. Booking request includes quote ID, expected scope revision, payment preference and command ID; server never accepts a client total or driver approval flag.

Example event: `{eventId:'evt_opaque', aggregateId:'booking_opaque', aggregateVersion:12, type:'assignment.accepted', occurredAt:'UTC_ISO', schemaVersion:1, correlationId:'...', payload:{assignmentId:'...', driverPublicProfileId:'...', pickupEtaSec:240, policyVersion:'dispatch-v1'}}`. Sensitive phone, documents, OTP and payment secrets are not broadcast. Client reducer tests cover duplicate version 12, older version 11 and missing version 13 before 14. #### D30 — Dispatch pseudocode and database acceptance criteria

```text
on booking_requested(id):
  if booking.state != searching: return
  candidates = eligible_fresh_drivers(booking.product, booking.region)
  pairs = route_feasible_candidates(candidates, booking.pickup, restriction_version)
  ranked = stable_sort(pairs, cost, driver_id)
  issue_durable_offer(next_non_cooldown(ranked), ttl, booking_revision)

accept_offer(command):
  begin transaction
  if idempotency_record(command.id) exists: return original_result
  lock booking, driver_session, offer in deterministic order
  assert role/ownership, live offer, server_now < expires_at
  assert booking.revision == offer.booking_revision and booking is searching
  assert driver_session is available/offered_to_this_booking and eligible_now
  insert assignment with unique active_booking and unique exclusive_driver constraints
  mark offer accepted; revoke competing offers; transition booking and driver_session
  append audit/event and transactional outbox; record command result
  commit
```

Acceptance tests must run with two server processes/database connections, not just two promise calls against an in-memory mutex: 100 concurrent accepts across drivers -> exactly one booking assignment; one driver accepting two bookings -> one success; timeout and accept at same instant -> one valid transition; worker restart between DB commit and publish -> event eventually delivered with no duplicated assignment; cancellation during offer -> no valid late accept; idempotency key reused with altered payload -> conflict. Lease uniqueness must survive database migration and rollback.

#### D33 — Local route and ETA validation corpus

Create a versioned evaluation corpus from consenting local drivers/operators: city-pair/entrance, route graph/profile/version, vehicle/permit class, known legal access restriction, checkpoint observation timestamp/source, predicted route/ETA band and actual departure/arrival/dwell. Keep sensitive traces access-controlled; publish only aggregate evaluation. Include urban one-way streets, same-city short trips, rural landmarks, multiple checkpoint corridors, inaccessible/restricted routes, stale/unknown/contradictory reports, nighttime, weak network and vehicle-class differences. Separate transport time from customer loading/waiting. No inference of Gaza, East Jerusalem or cross-border permission from West Bank city proximity. Validate legal/operational serviceability before route speed. Block confidently prohibited route; unknown route returns uncertain/manual-review state, not an optimized safe path claim. Evaluate quoted-time coverage and systematic underprediction by corridor; widen bands where data is sparse. Parent app audit identifies the current 15km coverage circles, haversine*1.3 fallback, fixed checkpoint delays and geometric-detour fallback as specific code deltas.

#### D34 — Notifications as a recoverable workflow

Replace process-memory notification intent with transactional outbox rows bound to durable booking events. A worker sends native Expo/APNs/FCM as supported by exact SDK/build guidance plus current Web Push for browsers, records provider receipts/errors and retries transient failures with bounded backoff/jitter; invalid tokens are disabled, TTL-expired offers are never re-sent as actionable. Device token registration belongs to authenticated user/device session and is revoked on logout/account switch. Payload exposes only safe preview data and event/resource reference; phone retrieves current state before action. Every important event remains in app timeline even if push never arrives. Native push delivery/background processing is best effort, not a dispatch correctness lock. For urgent unacknowledged work, use an operator dashboard escalation and consented locally supported SMS fallback only where policy/coverage permits. Tests: dead token, provider timeout, push duplicated, wrong account token, app uninstalled, deep link after booking terminal, quiet hours vs transactional notification category and notification access disabled.
