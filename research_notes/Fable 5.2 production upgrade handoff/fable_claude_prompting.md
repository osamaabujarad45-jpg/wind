# Fable 5.2 identity and official Claude guidance for the Fastship implementation handoff

## Is there an officially documented Anthropic/Claude model or product named Fable 5.2 as of 2026-11-13?

### Takeaway

Yes. **Claude Fable 5.2 is an official, current Anthropic model**, released November 9, 2026, with Claude API model ID `claude-fable-5-2`. The handoff can name it directly and use its model-specific guidance; the conditional fallback to a purely model-agnostic handoff is not needed.

### Cited Findings

- Anthropic's model overview lists **Claude Fable 5.2** among its latest models, describes it as intended “for demanding reasoning and long-horizon agentic work,” and gives the Claude API ID `claude-fable-5-2`. — [Official models overview](https://platform.claude.com/docs/en/models/overview) (accessed 2026-11-13)
- The dedicated model page says Fable 5.2 was released **November 9, 2026**, is **Active (latest)**, and has a retirement commitment of not sooner than November 9, 2027. — [Official Claude Fable 5.2 overview](https://platform.claude.com/docs/en/models/fable-5-2/overview) (accessed 2026-11-13)
- Documented capabilities are a **1M-token context window**, **128K-token maximum synchronous output**, text and image input with text output, adaptive thinking always on, and API default effort `high`. Its reliable knowledge cutoff is June 2026. — [Official Claude Fable 5.2 overview](https://platform.claude.com/docs/en/models/fable-5-2/overview) (accessed 2026-11-13)
- Anthropic publishes a dedicated **Prompting Claude Fable 5.2** guide covering effort calibration, finishing long tasks, approvals, code ownership, progress updates, subagents, accumulated caution, inherited prompts, final reports, and refusals. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)
- Claude Code documentation also names Fable 5.2 and says `/model fable` selects it where available. That documentation does not establish that every plan, provider, or local installation exposes the same option. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)

### Inferences

- Address the downstream agent as **“Claude Fable 5.2, running at explicitly selected `high` effort”** if that is what the owner configures. Do not substitute another model name or speculate about an alias. This follows the verified model ID and Anthropic's recommendation to start Fable 5.2 at `high` and evaluate adjacent levels. — [Official model overview](https://platform.claude.com/docs/en/models/fable-5-2/overview); [official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (both accessed 2026-11-13)
- Keep the implementation instructions largely portable anyway: explicit acceptance criteria, repository-derived evidence, phased implementation, and verification are current general Claude practices, not tricks tied to one snapshot. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices); [official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (both accessed 2026-11-13)

### Gaps

- Public documentation verifies that the model exists, not which model the owner's downstream session is actually routed to, whether the selected provider exposes it, or whether the effort control is honored. The launcher/session configuration must supply that evidence separately.
- No non-official source is needed to resolve the name ambiguity, and none is used here.

## What official Claude prompt-engineering guidance applies to complex coding handoffs?

### Takeaway

Define observable success and tests first; give explicit scope, context, actions, and output requirements; use real artifacts rather than a repository dump; select effort through the harness; and require environmental verification and iteration. Fable 5.2-specific guidance adds persistence through ordinary obstacles, narrow approval rules, restrained delegation, and caution against prompts inherited from older models.

### Cited Findings

- Anthropic's prompt-engineering overview says to establish **clear success criteria**, a way to **test empirically** against them, and a draft prompt before optimizing the prompt. — [Official prompt engineering overview](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview) (accessed 2026-11-13)
- Current prompting guidance recommends clear, direct, specific instructions; sequential steps when order or completeness matters; and explicit requests for any work beyond the minimum literal reading. It also recommends explaining the purpose or motivation behind a constraint so the model can generalize appropriately. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (accessed 2026-11-13)
- Examples are a reliable way to steer format and structure. Anthropic recommends relevant, diverse, structured examples, normally 3–5 for general prompting, wrapped in `<example>`/`<examples>` tags. XML tags are recommended to separate instructions, context, examples, and variable inputs in complex prompts. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (accessed 2026-11-13)
- For large data-rich inputs, Anthropic recommends placing long documents before the final query/instructions, labeling documents and metadata with XML, and grounding responses in relevant quotations. This is guidance for long-document inputs, not a requirement to paste an entire codebase into a coding-agent prompt. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (accessed 2026-11-13)
- Tool-use guidance distinguishes **“suggest changes”** from **“change this function”** or **“make these edits.”** Explicit action language is needed when implementation, not advice, is intended. Independent tool calls can be parallelized, while dependent calls should remain sequential and must not use guessed parameters. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (accessed 2026-11-13)
- Fable 5.2 uses **adaptive thinking**, always on. Anthropic recommends starting at `high` for hard coding, research, agentic work, and long unattended runs. `xhigh` is for the hardest long-running work **where evaluations show a gain**; gains above `high` are uneven and token use rises substantially. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)
- Anthropic's Fable 5.2 persistence guidance says the model can prematurely list remaining work, offer to continue, or stop at an ordinary obstacle. Its recommended instruction is to continue owed work, diagnose errors/timeouts/empty results/failing tools, respect deliberate blockers, preserve confirmation for risky or irreversible actions, and continue independent work while a user decision is pending. Anthropic reports that this roughly halved unfinished recorded coding sessions at `medium`, with about 30% more output tokens. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)
- Approval instructions should name the exact action being approved rather than saying only “continue” or “go.” Overbroad approval rules can suppress routine work; routine actions that need no approval should be named explicitly, while risky and irreversible actions retain confirmation. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)
- Anthropic recommends self-checking against concrete test criteria before finishing. Its multiwindow guidance recommends structured test state, convenience setup scripts, progress notes, git state, incremental progress, and environment-based verification tools such as browser automation for UI work. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (accessed 2026-11-13)
- The Fable-specific guide says a final report should stand alone for a low-context reader: key points first, plain language, consistent terminology, no undefined references, and enough detail to understand the outcome without seeing tool calls. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)

### Inferences

- The handoff should contain these labeled blocks: **objective and user impact; authoritative repository/spec artifacts; non-negotiable constraints; requirement inventory; explicit out-of-scope items; available tools and permissions; verification matrix; phased execution protocol; blocker/approval policy; final evidence format**. This is a direct application of Anthropic's clarity, context, structuring, action, and verification guidance. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices); [official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (both accessed 2026-11-13)
- Prefer links/paths to the actual spec, representative screens, failing logs, and exemplary implementation files over invented examples. Use a small example only when it demonstrates an expected output or test report format; do not pad the handoff with 3–5 hypothetical code samples merely to satisfy a general few-shot guideline. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices); [official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (both accessed 2026-11-13)
- Say **“implement, run, inspect, revise, and verify”**, not “review and suggest an upgrade.” Require the agent to read actual tool results and iterate on failures rather than treating the first plausible diff as completion. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices); [official building effective agents](https://www.anthropic.com/research/building-effective-agents) (both accessed 2026-11-13)
- Set `high` in the product/API rather than asking for “high effort” in prose. If evaluations show no benefit over `medium` for a bounded subtask, use the lower level there; do not assume `xhigh` or `max` improves this upgrade. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)

### Gaps

- Anthropic's published results are aggregate/internal evaluations, not a Fastship benchmark. The best effort level and the value of extra delegation must be measured on Fastship's own acceptance checks.
- The documentation does not supply Fastship's requirement inventory or define production acceptance; those must come from the owner and repository evidence.

## What current official Claude Code best practices apply to repository exploration, planning, tests, subagents, permissions, checkpoints, and common failures?

### Takeaway

Let Claude inspect the repository, but supply the knowledge it cannot infer. Give it executable pass/fail gates and end-to-end checks, plan before edits, isolate concurrent work, enforce zero-exception rules in the harness, and treat summaries/checkpoints as aids rather than proof or substitutes for review.

### Cited Findings

- Current Claude Code guidance says models are strong at discovering layout, conventions, tests, and components from code. Persistent instructions should focus on information unavailable in the repo, exact verification commands, misleading areas, team decisions, and repeatedly corrected issues; it recommends keeping `CLAUDE.md` short rather than restating discoverable code structure. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- Effective task prompts name the relevant file or symptom and what “fixed” means. Providing the actual file, screenshot, or command output is preferred to describing it indirectly. For a bug, an official example asks for a failing reproduction test before the fix. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- Claude Code's common workflows recommend broad-to-narrow repository exploration, tracing execution across components, small testable refactoring increments, behavior-specific tests, and running and fixing the resulting tests. Plan mode reads and proposes without editing until approval. — [Official Claude Code common workflows](https://code.claude.com/docs/en/common-workflows.md) (accessed 2026-11-13)
- A pass/fail artifact can be a test, build exit code, linter, fixture diff, or browser screenshot. Anthropic recommends asking for **the command and output or screenshot as evidence**, not accepting “all tests pass” alone. `/verify` builds/runs the app and inspects the result for problems tests and typechecks miss. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- A fresh reviewer can compare the diff against the spec and check every requirement and edge-case test. Anthropic advises restricting that review to correctness gaps and skipping style to avoid unnecessary abstraction and scope expansion. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- Long-running-agent research found two important failures: attempting too much at once and later declaring the whole job complete prematurely. Its tested pattern uses a comprehensive structured feature list, one feature at a time, clean mergeable states, progress notes plus git history, and status changes only after careful end-to-end testing. Browser automation exposed failures that unit tests and `curl` missed. — [Official effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents) (accessed 2026-11-13)
- Subagents are useful for independent parallel work, noisy searches/test output, fresh review, and reduced tool privileges. They consume additional tokens, repeat context discovery, and do not inherently produce a smarter answer. A read-only reviewer can be limited to `Read`, `Grep`, and `Glob` by configuration. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- Prompts and `CLAUDE.md` are non-deterministic guidance. Hooks, deny rules, managed settings, tests, CI, branch protection, and human approval provide deterministic enforcement. Auto mode uses a classifier and is not a hard security boundary; `bypassPermissions` is described as appropriate only for a disposable container. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- `/rewind` can restore code and/or conversation to an earlier prompt, but checkpoints cover files edited by Claude's file tools in the main conversation, **not changes made only through Bash**. Checkpoints work alongside git rather than replacing it. Parallel sessions should use separate worktrees to avoid edit collisions; fresh worktrees may lack gitignored environment files and installed dependencies. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md); [official common workflows](https://code.claude.com/docs/en/common-workflows.md) (both accessed 2026-11-13)
- Automatic compaction is available, but unrelated tasks should be cleared and long sessions compacted with a focus to reduce distraction and cost. If two corrections fail, current guidance recommends clearing and supplying a better prompt rather than stacking a third correction. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- Before unattended execution, Anthropic says to establish what done means, how work is checked, what may be touched, what stops the run, where the result goes, and who approves irreversible outcomes. Turn/spend caps and human merge/deploy approval remain relevant. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)

### Inferences

- Begin in read-only/plan mode: inventory the requirement-to-code map, trace real data and navigation flows, identify existing reusable patterns, run baseline checks, and only then approve an implementation plan. Do not ask for a giant up-front architecture document that repeats what the repository already proves. — [Official common workflows](https://code.claude.com/docs/en/common-workflows.md); [official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (both accessed 2026-11-13)
- Fastship's required `npx expo lint` and `npx tsc --noEmit` gates and its physical-Android/no-emulator acceptance rule should be instantiated directly in the verification matrix. These are repository requirements, not Anthropic recommendations. — [Fastship repository instructions](../../AGENTS.md) (read in supplied session context, 2026-11-13); general evidence-loop rationale from [official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- Do not broaden tool permissions merely to avoid interruptions. Preserve repo restrictions on secrets, native generated directories, git mutations, deployment, and device/backend state. Where a rule truly has no exceptions, rely on existing deny/hook/CI controls as well as prose. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md); [Fastship repository instructions](../../AGENTS.md) (accessed/read 2026-11-13)
- Use an independent reviewer after implementation, with the requirement matrix and diff as inputs. Delegate bounded read-only exploration only when it saves meaningful main-context noise or enables real parallelism; one writer should own each file. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- Checkpoint after each verified vertical slice with a progress record and clean tree state, but request owner approval before any git mutation as Fastship requires. Do not claim `/rewind` protects command-generated changes. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md); [Fastship repository instructions](../../AGENTS.md) (accessed/read 2026-11-13)

### Gaps

- The research did not test the installed Claude Code version or confirm which documented commands (`/goal`, `/verify`, `/code-review`, `/rewind`) are available in the downstream surface. The handoff should describe the required behavior and use commands only when the session supports them.
- Official browser examples are web-centric. Fastship still needs its repository-specified physical-device path for mobile acceptance; a web screenshot alone cannot establish React Native behavior.

## How should the handoff be structured for safe phases, preserved constraints, validated claims, and more than a superficial UI refresh?

### Takeaway

Use a requirement-driven, vertical-slice implementation contract with explicit stop/evidence gates. Every requested behavior must be traced through state, data, navigation, errors, and device-level execution; visual polish is only one layer, and no requirement becomes “done” without reproducible evidence.

### Cited Findings

- Anthropic's long-running-agent work specifically warns that a high-level prompt and compaction alone can yield one-shot implementation, half-finished undocumented work, premature completion claims, and features marked complete without end-to-end validation. — [Official effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents) (accessed 2026-11-13)
- Coding agents benefit from environmental ground truth at every step and automated tests as feedback, but Anthropic says human review remains crucial for alignment with broader system requirements. — [Official building effective agents](https://www.anthropic.com/research/building-effective-agents) (accessed 2026-11-13)
- Fable 5.2's “ownership” prompt can increase consolidation and extra changes, including behavior changes; a scope-limiting rule did not reliably cancel that effect in Anthropic's tests. Anthropic therefore advises omitting the ownership sentence when the user owns the code and wants minimal changes, and reviewing the actual diff as well as the summary. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)

### Inferences

- **Recommended handoff preamble:** “Implement the complete approved Fastship production upgrade, not merely a visual reskin. Work from the cited specs and repository evidence. Preserve all existing constraints and unrelated behavior. Treat each requirement as open until its listed checks pass with captured evidence. Continue through ordinary diagnosable failures; stop only for a genuine owner decision, deliberate access boundary, or risky/irreversible action, while continuing independent work.” This combines Anthropic's explicit-action, persistence, and verification guidance. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices); [official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (both accessed 2026-11-13)
- **Phase 0 — Baseline and requirement ledger, no edits:** read all governing instructions/specs; identify every requested user journey and non-UI requirement; map each to current screens, state, services, navigation, tests, and gaps; record baseline lint/typecheck/test results and a basic physical-device smoke result; identify pre-existing failures separately from new ones. Produce a requirement ledger with stable IDs, acceptance steps, evidence required, and dependencies. Do not narrow the ledger to screens named in a mockup. This applies Anthropic's baseline, feature-list, and early-failure detection pattern. — [Official effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents); [official common workflows](https://code.claude.com/docs/en/common-workflows.md) (both accessed 2026-11-13)
- **Phase 1 — Plan and test contract:** propose the smallest coherent vertical slices and their file/caller impact. Include loading, empty, error, retry, validation, persistence/state restoration, navigation/back behavior, accessibility, permission denial, offline/network failure, and backward compatibility wherever applicable. Define focused and end-to-end checks before implementation. Preserve public contracts unless the approved spec changes them. Obtain plan approval where required. This derives from Anthropic's success-criteria, test-first, small-increment, and plan-mode guidance. — [Official prompt engineering overview](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview); [official common workflows](https://code.claude.com/docs/en/common-workflows.md); [official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (all accessed 2026-11-13)
- **Phase 2 — Implement one vertical slice at a time:** trace each flow from user action through UI, state/domain logic, backend/local data, response handling, and resulting navigation. Reuse established project patterns. Add or update behavior tests alongside the code, run focused checks, inspect actual runtime behavior, and fix regressions before starting the next slice. Do not count static styling, placeholders, mocked success, or a screenshot as implementation of the flow. Anthropic identifies one-feature-at-a-time progress and environment feedback as the remedy to one-shot and false-completion failures. — [Official effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents); [official building effective agents](https://www.anthropic.com/research/building-effective-agents) (both accessed 2026-11-13)
- **Phase 3 — Slice checkpoint:** leave each slice in an orderly, mergeable state; update the requirement ledger with exact evidence and remaining work; record generated files and side effects; preserve unrelated user edits. Use a session progress note if work crosses contexts. Commit only if the owner has explicitly authorized that git mutation. This follows Anthropic's clean-state/progress-artifact pattern while preserving Fastship's git restriction. — [Official effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents); [Fastship repository instructions](../../AGENTS.md) (accessed/read 2026-11-13)
- **Phase 4 — Full integration and device acceptance:** run the complete required test suite, `npx expo lint`, and `npx tsc --noEmit`; exercise all requirement journeys end to end on Fastship's connected physical Android phone with its prescribed backend route, not an emulator. Test real failure paths and regressions, not only the happy path. Capture commands, exit results, device/build identity, and relevant screenshots/logs. If a gate was already failing at baseline, prove whether the change worsens it rather than silently claiming a pass. This combines Anthropic's executable evidence/E2E guidance with the local acceptance rules. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md); [official effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents); [Fastship repository instructions](../../AGENTS.md) (accessed/read 2026-11-13)
- **Phase 5 — Independent spec and diff audit:** a fresh reviewer should map every requirement ID to implementation and evidence, inspect the actual diff for unreported behavior changes, and check that no constraint was weakened. Limit findings to correctness, security, regressions, missing requirements, and inadequate evidence rather than style-only expansion. Return gaps to implementation and rerun affected gates. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md); [official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (both accessed 2026-11-13)
- **Phase 6 — Final evidence handoff:** lead with overall status and any incomplete requirements; include the requirement-by-requirement evidence table, files changed and why, exact checks and outcomes, device/runtime evidence, known limitations, and precise owner actions for true blockers. Never convert an unrun check into “done,” and never describe the result as production-ready solely because lint/typecheck or visual review passed. The report must be understandable without the tool transcript. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2); [official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (both accessed 2026-11-13)
- **Required anti-superficiality clause:** “For every screen or component changed, enumerate the behavioral contracts exercised and their evidence. If a requested item has no data/state/navigation implication, explain why; otherwise implement and test those layers. A styled but nonfunctional or mock-only path remains open.” This is an application of Anthropic's finding that end-to-end tests catch failures missed by code inspection, unit tests, and simple endpoint calls. — [Official effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents) (accessed 2026-11-13)
- **Required scope clause:** “You are implementing the owner's approved requirements in the owner's repository. Make only changes needed for those requirements and their direct correctness/regression coverage. Do not use an ownership or long-term-maintainer persona to justify drive-by refactors.” Anthropic specifically warns against the ownership sentence for minimal-change work. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)

### Gaps

- The actual Fastship feature ledger cannot be completed from prompting documentation alone; Phase 0 must derive it from the owner's production-upgrade spec and repository.
- No prompt can guarantee compliance or production readiness. Deterministic checks, access controls, and owner review must back the handoff.

## Which prompt techniques are unsupported myths or unnecessary?

### Takeaway

Avoid magic words, performative capitalization, forced visible chain-of-thought, manual thinking budgets, standing delegation, giant instruction files, and ownership prompts. Use explicit effort, concrete scope, real tools, tests, and harness enforcement instead.

### Cited Findings

- **“Think hard,” “think harder,” and “be thorough” do not set effort.** They are ordinary prose that may nudge behavior within the current effort setting. Claude Code's effort control is the primary mechanism; `ultrathink` is a supported one-off Claude Code control, not a substitute for selecting the right session effort. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- **Repeated `IMPORTANT`, all caps, and stronger wording are not reliable enforcement.** They can cause over-application. Shorten lost instructions or convert true zero-exception rules to hooks/deny rules. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- **Manual `budget_tokens` extended thinking is the wrong pattern for Fable 5.2.** It supports adaptive thinking only; current guidance says later models reject `budget_tokens` and recommends effort plus `max_tokens` for cost/output limits. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices); [official Fable 5.2 model overview](https://platform.claude.com/docs/en/models/fable-5-2/overview) (both accessed 2026-11-13)
- **Asking Fable 5.2 to print private/internal reasoning is unnecessary and may be refused.** Anthropic lists `reasoning_extraction` as a refusal category and recommends removing such instructions; use supported thinking summaries when visibility is needed. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)
- **“You own this codebase” is not a harmless quality booster.** It increased unrequested changes and sometimes changed existing behavior in Anthropic's tests, even with a no-drive-by rule. Omit it for this owner-controlled upgrade. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)
- **More subagents do not inherently mean better answers.** Delegation provides parallelism, noise isolation, or independent review at additional token/context cost. Fable-specific guidance says to review standing delegation instructions first if it delegates excessively. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md); [official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (both accessed 2026-11-13)
- **Aggressive context-window micromanagement is no longer the default need.** Current models have large windows and automatic compaction, although focused sessions still improve cost and relevance. Subagents should not be justified solely as context protection. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- **Prefilling the final assistant response is unsupported on current model generations.** Use direct instructions, structured outputs, or tool calling where appropriate rather than relying on prefill tricks. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (accessed 2026-11-13)
- **Prompt text alone cannot enforce permissions, test success, or human approval.** Deterministic controls belong in the harness, CI, branch protection, and review process. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- **Large model-visible token budgets and inherited older-model cautions can be counterproductive.** Anthropic reports that removing a large displayed budget lowered cost with equivalent performance in tested Fable 5.2 coding tasks, and recommends deleting obsolete rules and testing inherited harness instructions rather than accumulating them. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)
- **Editing earlier system prompts/tools/messages mid-conversation is not a neutral prompt tweak for Fable 5.2.** Preserved-thinking prefix checks can reject altered histories. Start a new conversation for migrated instructions or put new instructions in the newest turn, keeping history append-only where applicable. — [Official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (accessed 2026-11-13)

### Inferences

- Do not include a ritual list of keywords, fake “activation” phrases, arbitrary token countdowns, demands to reveal reasoning, or blanket “always spawn agents” instructions. None substitutes for the selected effort, a requirement ledger, executable checks, or appropriate permissions. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md); [official Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2) (both accessed 2026-11-13)
- “Be ambitious” is not a myth: current Claude Code documentation says it can clarify that the requester wants full functionality and edge cases rather than the smallest literal implementation. For Fastship, a precise requirement inventory is still better than relying on that phrase alone. — [Official Claude Code best practices](https://code.claude.com/docs/en/best-practices.md) (accessed 2026-11-13)
- XML, few-shot examples, roles, and structured output are supported tools, not mandatory rituals. Use them only where they disambiguate the handoff or its evidence format; do not let formatting machinery obscure the actual implementation contract. — [Official prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (accessed 2026-11-13)

### Gaps

- The phrase “production-ready” has no universal prompt-engineering test. Its meaning must be operationalized through Fastship's approved requirements and release gates rather than asserted by the model.
