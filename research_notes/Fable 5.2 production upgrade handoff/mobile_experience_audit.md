# Fastship / Wind mobile experience audit: Uber-quality production gap inventory

**Scope and labels.** Static source review covers customer/auth/booking/order/receipt/tracking, driver work/jobs/trips/earnings/account, admin operations, shared UI, maps, push, localization and recovery. **implemented** means the current source contains the behavior; **missing** means the reviewed source does not expose the behavior; **unknown** means production/backend/runtime behavior cannot be established from this review. No emulator, physical-device test, production request or runtime test was performed. **P0** = release-blocking core-flow, safety, money or data-integrity risk; **P1** = major Uber-parity or operational gap; **P2** = polish, scale or secondary-workflow gap. Existing audit reports were treated only as leads; conclusions below cite current source.

### Inferences

- The highest-value customer work is **C1 then C2/C3**, not rebuilding maps, live tracking, proof codes, cancellation, chat or recovery that already exist.
- C2 is the clearest remaining Uber-parity deficit: city-plus-landmark entry can work for a local service, but visitors and imprecise addresses need remote search/reverse geocoding plus a manual fallback that preserves the current served-area rule.
- C1 should be solved as an explicit cached/read-only signed-in mode with visible staleness and disabled mutations; simply bypassing `/me` would weaken authorization and is not an acceptable shortcut.
- Push needs observable delivery health and device-level verification before being called reliable; the implemented fallback is a resilience feature, not proof of background delivery.
- Uber-quality acceptance should prioritize successful cash completion and recovery under interruption over visual imitation of Uber.
