# Google Maps fails on terms, not code

**Google Maps will drop into Fastship/Wind's native app behind the existing `RouteMap`/`PinMap` props in about two days of work, and it still should not be switched on now.** The component is not the obstacle: Google's terms make the choice binary — a full Google map carrying Google routes and places, or no Google content at all — so the current product cannot keep its checkpoint-aware OSRM lines and its public track page while adding Google. Web is a separate, larger job because the app's tested `script-src 'self'` policy forbids the Maps JavaScript API, and Google's own CSP guidance includes `'unsafe-eval'`. Palestine gets Google's road geometry and geocoding but not the traffic layer, speed limits, real-time disruptions or a checkpoint dataset, and the public record contains no 2026 Ramallah–Nablus route test. Cost is decided by refresh policy, not driver count: the app's 110 m re-route pattern bills roughly **$4,300–$7,450 a month for routes alone at 100 drivers**, against **$250** at one call per leg. The recommendation is to stay on MapLibre/OSRM, fix the refresh policy anyway, and build only the dark server proxy if a corporate, address-coverage or SLA requirement appears.

## The decision: a two-day integration that is not worth making yet

Fastship/Wind already has the seam. `RouteMapProps` and `PinMapProps` in `src/route-preview.tsx` describe pickup, dropoff, driver, road, approach and closed checkpoints; three renderers implement that contract — MapLibre on web (`src/route-map.tsx`), Apple Maps on iOS (`src/route-map.native.tsx`), and MapLibre inside a WebView on Android (`src/route-map.android.tsx`). No screen's JSX has to change to put Google tiles behind those props. What does not swap is the line itself: every polyline comes from `/api/route`, which is OSRM, and the same OSRM graph feeds `/price`, quote feasibility, dispatch ETA and the checkpoint detours (`server/main.ts`). A Google build is a second upstream with a second cost model, not a new renderer.

| Mode | What actually works | Monthly cost at 100 / 1,000 / 10,000 drivers | Terms risk | Verdict |
|---|---|---|---|---|
| **Current MapLibre/OSRM** | Android WebView MapLibre, Apple Maps on iOS, MapLibre web, OSRM lines, checkpoint detours, 15 s public ETA | **~$10 / ~$70 / ~$400** (estimate) for the map, routing and geocoding line | None | **Keep** |
| **Full Google native** | Google tiles and markers on both platforms, Google Routes lines, Geocoding and Autocomplete; OSRM stays internal for price and dispatch | **$1.1k / $7.8k / $27k** at a 1.1 km refresh; **$4.6k / $16.4k / $76.7k** at today's 110 m pattern | Medium: one provider per screen, no route cache, public track must leave Google | Only behind a contract or address-coverage failure |
| **Full Google web** | Maps JavaScript API, dynamic map loads, `@vis.gl/react-google-maps`; needs a new component and a weakened CSP | Native cost **plus $560 / $4,550 / $15,490** for map loads | High: removes a tested security boundary for no Palestine benefit | **Reject** |
| **Hybrid** | Google tiles with OSRM lines, or Google Places beside MapLibre — what people usually mean by "just the map" | Google native cost plus $0 OSRM | **Prohibited**, except Places UI Kit | **Reject** |

*Cost assumptions: 10 trips per driver per day, 30 days, routes + one geocode per trip + 0.3 autocomplete per trip, `TRAFFIC_UNAWARE` Essentials routing, USD list prices before tax and FX. Mobile map loads are free. Arithmetic is mine, from the price list ([Google pricing](https://developers.google.com/maps/billing-and-pricing/pricing)).*

The native path is genuinely small: set two keys, add `provider={PROVIDER_GOOGLE}`, and give Android a Google branch before its WebView. That is why the question keeps coming back. But a two-day integration that costs 17–30× the one-call-per-leg baseline, forbids the hybrid everyone wants, and removes the checkpoint semantics that are the product's differentiator is not a two-day decision. The cheapest honest first step is the dark server proxy, not the UI.

## Native is a props swap; routing, keys and web are the work

The sequence below is the smallest complete path. It keeps one provider per screen, one build-time flag, one server flag, and a whole-session downgrade. It does not add a Google screen beside a MapLibre screen.

| Step | File | Change | Proof |
|---|---|---|---|
| **0. Keys** | Cloud console | Billing profile in ILS; enable Maps SDK Android/iOS, Routes, Geocoding, Places API (New); four keys | A `curl` from the API host returns 200; a laptop key returns 403 |
| **1. Build config** | `app.config.js` | Split `GOOGLE_MAPS_API_KEY` into Android and iOS keys, add `iosGoogleMapsApiKey`, throw if `EXPO_PUBLIC_MAP_PROVIDER=google` and either key is missing; pass `undefined` in MapLibre builds so the plugin removes the manifest entry | `npx expo prebuild --clean` produces a manifest with `com.google.android.geo.API_KEY` only in the Google build |
| **2. Mode store** | `src/map-mode.ts` (new, ~30 lines) | Build flag, `configureMapMode()` from `/api/config`, `downgradeMapMode()`, `useMapMode()`, `useRouteBase()` | A forced `maps_disabled` response flips the session to MapLibre |
| **3. Native extraction** | `src/native-map.tsx` (new) | Move the body of `route-map.native.tsx`; take a `provider` prop; use `onMapLoaded` for Google and `onMapReady` for Apple Maps | iOS Apple path unchanged when `provider` is undefined |
| **4. iOS wrapper** | `src/route-map.native.tsx` | Thin wrapper: `<NativeMap provider={google ? PROVIDER_GOOGLE : undefined} />` | Device build shows Google tiles |
| **5. Android branch** | `src/route-map.android.tsx` | Branch **before** `MapPage`: Google mode renders `NativeMap`; the WebView stays as the fallback | Metro resolves `.android.tsx` before `.native.tsx`, so this is the file that matters |
| **6. Route base and refresh** | `src/map-math.ts`, `src/road.tsx`, `src/app/book.tsx` | `roadPath(..., base = '/route')`; `useRoad` uses `useRouteBase()`, grid 2 (~1.1 km), and a 1 km/60 s refresh ref | Two GPS fixes 200 m apart produce one route call |
| **7. Startup config** | `src/app/_layout.tsx` | Fetch `GET /api/config` once, call `configureMapMode()` | Server flag forces MapLibre on the next launch |
| **8. Proxy** | `server/domain/google.ts`, `server/main.ts`, `server/migrate.ts` | `GET /api/google/route`, `/api/google/geocode`, `/api/google/autocomplete`, `/api/config`; `google_usage(day, sku, count)` | Fake-upstream suite passes; no key in any body |
| **9. Public page** | `src/app/track/[token].tsx`, `/api/track/:token/eta` | No Google calls. In Google mode return `{ minutes: null }` and no `road`/`approach`; or keep the page on MapLibre | A shared link never draws an OSRM line on a Google map |
| **10. Tests** | `tests/google.test.mjs`, `scripts/check-google-browser.mjs` | Fake Google upstream, no-cache assertion, caps, PII guard, kill switch; browser stub for web only | `npx tsc --noEmit`, `npx expo lint`, device checklist |

Three details decide whether this works. First, the proxy returns the existing `RoadRoute` shape `{ km, minutes, line, avoids, through, closed }` with `line` as `[lng, lat][]`, so `useApi` and every screen stay unchanged; `avoids/through/closed` are empty in v1, because Google cannot reproduce the checkpoint detour. Second, `react-native-maps` needs a tile-ready signal: `onMapLoaded` fires when tiles have rendered, while `onMapReady` can fire before them, so the existing 20 s failure timer must key off the former on Google. Third, the Google request must be `POST https://routes.googleapis.com/directions/v2:computeRoutes` with `X-Goog-Api-Key` and a required `X-Goog-FieldMask`, `routingPreference: TRAFFIC_UNAWARE`, `polylineQuality: HIGH_QUALITY`, `languageCode: ar` ([Routes API](https://developers.google.com/maps/documentation/routes/compute_route_directions)). The proxy times out at 4 s, rejects queries with seven or more consecutive digits as probable phone numbers, and never forwards `contact`, `recipientPhone` or notes.

Web is the part that is not small. `webCsp` is `script-src 'self'` with `connect-src` limited to OpenFreeMap (`server/main.ts`), and `tests/map.test.mjs` asserts the web map contains no `new Function` or `eval`. Google's CSP guide's samples include `script-src ... 'unsafe-eval' blob:` plus Google domains in `img-src` and `connect-src` ([Google CSP guide](https://developers.google.com/maps/documentation/javascript/content-security-policy)). Beyond the policy, `src/route-map.tsx` is written against MapLibre's imperative API — loader, vector-tile readiness proof, camera follow, marker glide — so a Google web component is a 250–350 line reimplementation, not a provider switch. If web Google is ever required, use `@vis.gl/react-google-maps` (MIT) rather than `@react-google-maps/api` v3+, which its own README calls commercial software ([vis.gl](https://github.com/visgl/react-google-maps)).

The SDK reality bounds the ambition. `react-native-maps` is at **1.29.11** (27 September 2026) with Fabric marker fixes; the repo pins **1.27.2** on Expo **SDK 57 / RN 0.86.3**, compatible on paper, two minors behind ([releases](https://github.com/react-native-maps/react-native-maps/releases)). Expo Go renders a map without your key, but a build carrying your own Google key needs a development or production build and a native rebuild; Expo says so explicitly, and the key is baked into the binary ([Expo SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/map-view/)). The official `@googlemaps/react-native-navigation-sdk` is **Beta** and requires **RN 0.87+ with the new architecture**, tested on 0.87.0; at RN 0.86.3 the only fallback is the older 0.16.3, which predates that requirement ([navigation SDK](https://github.com/googlemaps/react-native-navigation-sdk)). It also replaces the Maps SDK — Google states the two cannot coexist in one app — so it is a one-way door, not an add-on. It is not usable at the current version.

## The bill tracks the refresh policy, not the driver count

Mobile map loads are the one free thing: the **Maps SDK** SKU is unlimited on Android and iOS. Everything else is metered, and the **$200 monthly credit was removed on 1 March 2025**, replaced by per-SKU monthly caps ([pricing overview](https://developers.google.com/maps/billing-and-pricing/overview)). The caps that matter are **10,000** for Essentials (Routes Essentials, Geocoding, Autocomplete requests, Dynamic Maps), **5,000** for Pro (Routes with traffic, Place Details Pro) and **1,000** for Enterprise (Navigation Requests). Overages are billed, not blocked; only a lowered daily quota stops service, and budgets are alerts, not caps ([manage costs](https://developers.google.com/maps/billing-and-pricing/manage-costs)).

| Meter | Free each month | First-tier price after the cap |
|---|---:|---:|
| Maps SDK (Android/iOS) | Unlimited | $0 |
| Dynamic Maps (web map load) | 10,000 | $7.00 / 1,000 |
| Compute Routes Essentials (`TRAFFIC_UNAWARE`) | 10,000 | $5.00 / 1,000 |
| Compute Routes Pro (`TRAFFIC_AWARE`) | 5,000 | $10.00 / 1,000 |
| Geocoding | 10,000 | $5.00 / 1,000 |
| Autocomplete Requests | 10,000 | $2.83 / 1,000 |
| Place Details Essentials | 10,000 | $5.00 / 1,000 |
| Navigation Request | 1,000 | $25.00 / 1,000 |

*All from the global price list, last updated 28 October 2026 ([pricing](https://developers.google.com/maps/billing-and-pricing/pricing)).*

The app's refresh behaviour turns a cheap product into an expensive one. `useRoad` routes the approach at grid 3, about **110 m** of latitude, and refetches on every grid change; the static trip line uses grid 5 (~1.1 km). OSRM absorbs that because its cache rounds to 10 m and an LRU holds 200,000 geometry points (`server/main.ts`). Google cannot: route geometry and duration may not be cached, only lat/lng for 30 days ([Service Specific Terms §19.3](https://cloud.google.com/maps-platform/terms/maps-service-terms)). At 100 drivers and 30,000 trips a month, 50 route calls per trip is **1.5 million calls**. At the first-tier rate that is **$7,450**; Google's marginal volume tiers cut it to about **$4,300** — either way it is 17–30× the **$250** that two calls per trip (one line, one approach) costs. The public track page is worse in kind: it polls `/track/:token/eta` every 15 s and the server recomputes the approach, so one viewer left open for an hour is 240 route calls before the driver moves.

| Refresh policy | Calls per trip | 100 drivers | 1,000 drivers | 10,000 drivers |
|---|---:|---:|---:|---:|
| Today: every ~110 m | 50 | **$4,300–$7,450** | **$13,300** | **$63,900** |
| Every ~1.1 km / 60 s | 6 | **$770** | **$4,750** | **$14,425** |
| Once per leg | 2 | **$250** | **$2,350** | **$9,925** |

Adding the non-route meters at 100 drivers is modest — one geocode per trip costs **$100**, 0.3 autocomplete per trip costs **$226** — so the route line is the decision. The totals are **$1.1k / $7.8k / $27k** at the 1.1 km policy and **$4.6k / $16.4k / $76.7k** at today's pattern. Web map loads would add **$560 / $4,550 / $15,490**. At 100 drivers the per-trip unit cost is **$0.14** at the current 110 m pattern and **$0.008** at one call per leg, before the fixed meters.

Two pricing traps deserve naming. `TRAFFIC_AWARE` is billed at the Pro rate — **$10 per 1,000 instead of $5** — because the SKU is triggered by the request modifier, not by whether traffic data exists ([Routes billing](https://developers.google.com/maps/documentation/routes/usage-and-billing)). Palestine has no documented traffic layer, so paying the premium there buys a higher price and no documented signal; A/B it against `TRAFFIC_UNAWARE` on real trips before defaulting. Second, a `computeRouteMatrix` call bills **per element** — 20 candidate drivers × one pickup is 20 billable elements — so a dispatch matcher built on Google would dwarf the map line. Fastship's dispatch already uses OSRM internally and should keep it.

Navigation SDK is the expensive fork. At **$25 per 1,000** after 1,000 free, one navigation request per trip costs **$725 / $6,475 / $33,975** at 100 / 1,000 / 10,000 drivers, and it cannot coexist with the Maps SDK. It is also unavailable to this app at RN 0.86. The cheap alternative is the existing deep link to the installed Google Maps app (`src/app/track/[token].tsx`), which costs nothing and uses no SDK.

Cost control is a design, not a dashboard. The client should use grid 2 (~1.1 km) and refresh only when the driver has moved at least 1 km **and** 60 s have passed, passing the `order` id so the server can cap per order. The server should enforce 40 routes per order per 24 h, 200 per user per day, and global daily caps of 2,000 routes, 1,000 geocodes and 2,000 autocomplete requests, failing closed with `maps_quota` before calling Google. A kill switch (`GOOGLE_MAPS_ENABLED=0`, or `MAP_PROVIDER=maplibre`) must return `maps_disabled` without an upstream call. Budget alerts at 50/90/100% are alarms; the daily quota is the only hard stop, and billing data can lag 48 hours. Four keys, not one: Android (package + debug and Play SHA-1), iOS (bundle ID), web (referrer), server (IP-restricted or secret-only). The server key never reaches the app, the repo, a log or an error body ([security guidance](https://developers.google.com/maps/api-security-best-practices)).

## The terms allow two products, not a blend

Google's terms are stricter than its prices, and they decide the architecture. "Customer will not use the Google Maps Core Services with or near a non-Google Map in a Customer Application," with examples that include displaying Places content on a non-Google map and linking a Google map to non-Google map content ([ToS §3.2.3(e)](https://cloud.google.com/maps-platform/terms)). The product-specific terms repeat it: Routes content must not be used with a non-Google map (§19.2), and Geocoding (§6.2) and Places (§14.2) say the same ([Service Specific Terms](https://cloud.google.com/maps-platform/terms/maps-service-terms)). The single documented exception is **Places UI Kit**, which may be used "with or without any map, including a non-Google Map" and prevails over the prohibition (§15.1). Fastship is not using Places UI Kit, so the exception does not cover raw Places or Routes.

| Action | Allowed? | What it means for Fastship |
|---|---|---|
| Full Google map + Google Routes/Geocoding/Places | Yes | The only compliant Google product |
| Google Routes line drawn on MapLibre | **No** | Kills the "just swap the tiles" plan |
| Google Places results beside MapLibre | **No** (except Places UI Kit) | No mixed search UI |
| Cache route geometry or duration | **No** | The OSRM LRU cannot be reused |
| Cache lat/lng from Routes/Places | 30 consecutive days | Not enough for saved trips |
| Cache `place_id` | Indefinitely | The safe durable key for saved places |
| Cache geocoding result per end user | Indefinitely, user-facing only | Isolated per user; no shared address table |
| Rebuild turn-by-turn from Directions + Geolocation + Maps SDK | **No** | The named prohibited example |
| Cover or move Google's logo/attribution | **No** | Check the 34 px recenter button on both platforms |
| Send phone, name, notes or user id to Google | **No** | The proxy accepts text and coordinates only |

Caching is the trap that looks like an optimisation. "Customer will not cache Google Maps Content except as expressly permitted" ([ToS §3.2.3(b)](https://cloud.google.com/maps-platform/terms)); the allowance is lat/lng for **30 consecutive calendar days** (§19.3), **Google IDs** indefinitely (§A.3), and a Geocoding exception letting lat/lng, `formatted_address` and structured components be cached indefinitely **solely** for the direct end-user functionality of the app that made the request, isolated per user and not shared (§6.3.2). A shared West Bank address-to-coordinate table is exactly the "index and rehost" pattern the terms ban. Store the `place_id` and the user's confirmed pin instead.

The terms also forbid recreating the product: the named example is combining Directions, Geolocation and the Maps SDK "to create real-time navigation functionality substantially similar to" the Google Maps app (§3.2.3(d)(iv)). Attribution may not be modified, obscured or deleted (§3.2.2(b)); the app's terms must flow down Google's End User Additional Terms and Privacy Policy (§3.2.2(a)(i)), and the privacy page must disclose that Google receives search terms, IP addresses and lat/lng (§4.4(a)). The service is "for planning purposes only" (§13), and liability is capped at 12 months' fees (§15.1(b)) — a business-continuity argument for keeping a fallback router, not a legal one.

Contracting from Palestine is possible. Google Cloud's currency table lists **"Palestinian Territory | ILS | credit/debit card"**, self-serve, and the billing account's currency is fixed at creation ([Cloud Billing currencies](https://docs.cloud.google.com/billing/docs/resources/currency)). Prices are published in USD and converted monthly, so an ILS budget is not a fixed cost. The customer bears all taxes (§2.3(a)); whether Google charges Israeli VAT, Palestinian VAT or zero-rates the supply is not documented on any page reviewed and needs a local accountant. The EEA terms do not apply to a Palestinian billing address, so the global ToS and global Service Specific Terms govern, with California law and Santa Clara County venue (§18.11(c)). Whether the $300 trial credit is available to a Palestinian account is unverified.

## Palestine gets Google's roads but withholds its dynamics

Google's own coverage tables are the cleanest statement of what works. For **PS Palestine**, the core table marks map tiles, geocoding, driving directions and walking directions as available (⬤), and **traffic layer, biking and speed limits as unavailable (—)** ([Maps Platform coverage](https://developers.google.com/maps/coverage), last updated 28 October 2026). The Navigation SDK table adds the details that matter for a driver app: driving and walking ⬤, but **traffic layer, two-wheeled, biking, speed limits, traffic lights/stop signs and real-time disruptions all —** ([Navigation SDK coverage](https://developers.google.com/maps/documentation/navigation/android-sdk/coverage-nav-sdk), last updated 20 October 2026). Israel is also blank on traffic and speed limits in the same tables, so the gap is regional; PS is distinguished from IL only by biking and real-time disruptions. Read the column as "is this layer sold and supported here", not "does traffic data exist here": Google says navigating to a place still yields traffic-aware routes and ETAs, and told WIRED that checkpoint queues are reflected in routing and ETA ([CNBC, 24 October 2023](https://www.cnbc.com/2023/10/24/google-disables-live-traffic-conditions-on-maps-in-israel-and-gaza.html); [WIRED, 23 December 2024](https://www.wired.com/story/google-maps-west-bank/)).

The traffic display is a separate story. Google disabled live traffic and busyness in Israel and Gaza on 24 October 2023, partially restored route-level conditions in December 2023, and WIRED reported in December 2024 that the overview was still off. Google has never published a restoration date, and the 2026 table is an API table, not the consumer app. The practical reading: **do not ship a traffic toggle in Palestine.** A control that draws nothing is a product lie.

Checkpoints are the larger absence. Google's Places taxonomy has no "checkpoint" primary type; a military crossing is not a business listing. Nothing in the coverage tables or terms describes checkpoint state, queue time or permit-road restrictions. The physical scale is documented: **925 movement obstacles** in December 2025, **942 by 25 September 2026**, with **121 obstacles affecting Road 60** ([OCHA](https://www.ochaopt.org/content/movement-and-access-west-bank-april-2026); [Al Jazeera](https://www.aljazeera.com/news/2026/9/29/israels-west-bank-road-closures-turn-routine-journeys-into-long-ordeals)). Local apps already own this layer — Azmeh tracks 800+ checkpoints and barriers, Doroob has more than 200,000 active users ([Rest of World](https://restofworld.org/2025/palestinians-digital-maps-west-bank-israel/)). Fastship's own checkpoint table, closures and detours remain the differentiator no Google SKU supplies.

Routing quality is the part where the evidence is reported rather than documented, and the reports are consistent enough to plan around. In April 2018, 7amleh found Google sending Ramallah–Nablus on a 4.5-hour route through Israel instead of a 45-minute West Bank drive, with checkpoints and settlements unmarked ([7amleh, *Mapping Segregation*](https://www.apc.org/sites/default/files/Mapping-Segregation-Cover_WEB-5.pdf)). In January 2019, a Nablus–Ramallah test returned "no route found" while routes between Israeli settlements computed normally ([Deutschlandfunk](https://www.deutschlandfunk.de/google-maps-routenplaner-scheitert-im-palästinensergebiet-100.html)). In December 2024, WIRED replicated "could not calculate driving directions" for Hebron–Ramallah and quoted a Google employee attributing it to directions never being enabled between the West Bank's A, B and C areas. In December 2025, a single-author field essay reported warnings, repeated proposed U-turns and then **navigation withdrawn entirely** on the approach to Qalandia, with location tracking continuing but guidance stopped ([Zenodo, DOI 10.5281/zenodo.22133262](https://doi.org/10.5281/zenodo.22133262)). In September 2026, WIRED described Google Maps as "practically useless for Palestinians" and "blind to the checkpoints" ([WIRED](https://www.wired.com/story/all-the-west-banks-checkpoints-mapped/)).

The failure mode changes over time — absurd detour, then no route, then guidance withdrawal — which is why the 2018 numbers cannot be inherited as a 2026 conclusion. Google denies bias, says it cannot distinguish Palestinian from Israeli routes without knowing citizenship, and says it has added about **5,000 miles of roads** and updated thousands of names since 2021. The documented basis for the complaint is real: roughly **79 km of roads are Israeli-only** and **155 km are restricted** for West Bank Palestinians, with arrest, fines or violence for unauthorised use ([7amleh](https://www.apc.org/sites/default/files/Mapping-Segregation-Cover_WEB-5.pdf)). A routing engine that computes for the most permissive vehicle profile is systematically wrong for a green-plate fleet, not randomly wrong. **No 2026 Ramallah–Nablus test exists in the public record**; the most recent direct datapoint is 2019.

Geocoding is the strongest Google argument and the weakest evidence. Google marks PS geocoding ⬤ and shipped a West Bank address-lookup update around November 2024, but there is no independent Palestine-specific accuracy study. The best global benchmark gives Google Maps v3 **100% candidate return and 88.3% accuracy at geohash-6 precision (about ±0.6 km)**, best of 12 geocoders — on a set that is **98% Latin-script and 49% North America / 43% Europe**, with Palestine not a stated stratum ([MESSY STREETS](https://arxiv.org/html/2609.01612)). Colloquial Arabic, transliteration variants and landmark-based addresses are exactly where that benchmark is silent. Street naming is also unstable in practice: Ramallah officials change one-way directions frequently, and Google's crowd-edit backlog was reported as a freshness problem. Autocomplete for "رام الله" will find the city; autocomplete for a neighbourhood shop or "حاجز قلنديا" is untested. Checkpoints are the worst case — three naming systems, no street address, no stable official entry — so the correct design is an app-owned alias table joined by proximity, not a geocoder default.

The labels are a product decision, not a technical one. Google has never labelled "Palestine" on Maps; the area renders as **"West Bank" and "Gaza Strip" inside a dashed grey disputed boundary**, with names following the device language, and Google localises borders by viewer country ([Google Maps Help](https://support.google.com/maps/answer/3145721); [AFP Fact Check](https://factcheck.afp.com/doc.afp.com.362D3LA)). A Palestinian rider opening Fastship would see "West Bank" on a Google basemap. That is Google's rendering, not Fastship's position, but users will not necessarily make the distinction, and overlaying a "Palestine" label or redrawing the boundary would modify licensed map content. Both directions need a deliberate decision; the current MapLibre/OpenFreeMap stack avoids it entirely.

## Twenty trips and a dark proxy would settle it

No Google API key, device build, billing run or live Palestine route test was performed for this report. Everything above is documentation, dated reporting, list-price arithmetic and repository reading. The matrix below is the minimum field evidence that would replace a vendor claim with a measured result; the pass bars are proposed product thresholds, not Google-published SLOs.

| Claim | Test | Pass bar |
|---|---|---|
| Google routes West Bank trips legally | 20 trips: Ramallah–Nablus (6), Nablus–Ramallah (3), Ramallah–Jerusalem via Qalandia (5), Ramallah–Qalandia (3), Nablus–Huwwara loop (3), across three time windows | **0%** of polylines on the Israeli-only road list; every segment green-plate drivable |
| ETA is usable | Same 20 trips, Google ETA at T-0 vs GPS ground truth, p50/p90 and share over 2× | p50 ≤25%, p90 ≤50% **after** checkpoint correction; raw p90 expected to fail |
| Guidance survives the seam | Log every warning, U-turn and dropped guidance with timestamps | **0%** guidance drops; any drop is a safety defect |
| Arabic addresses resolve | 25 addresses (5 each Ramallah, Nablus, Hebron, Bethlehem, Jenin): 10 street+number, 10 street-only, 5 colloquial | ≥80% top-3 for street-only, ≥60% colloquial, ≤150 m median error |
| Landmarks resolve | 10 queries: Qalandia, Huwwara, Checkpoint 300, Damascus Gate, Al-Manara, Joseph's Tomb junction, Eyal, Tarqumiyah, Taybeh, Atara | Correct entity in top 3 for ≥7/10; pin on the correct side for ≥8/10 |
| Traffic is honestly absent | Compare `TRAFFIC_AWARE` vs `TRAFFIC_UNAWARE` on the same OD pairs; check `duration_in_traffic` population | No measurable difference means no traffic product; hide the toggle |
| Keys, quotas and billing work | Wrong SHA-1 must produce a blank map and fallback; daily cap must return `maps_quota`; reconcile `google_usage` to the Cloud Billing export | Cap fires before spend; usage within 10% of the bill |
| Web CSP is contained | Staging web build with the widened CSP; console clean except Google's own frames | No `unsafe-eval` outside the Google build; MapLibre build unaffected |
| Both builds ship | Android with Play services, Android without, iOS with the GoogleMaps pod; measure IPA/APK delta | Map renders, sheet gestures work, attribution uncovered, size recorded |

The cheapest high-value subset is not the 20 trips: it is the 10 landmark autocomplete queries plus the five Qalandia trips. Those answer "can a rider select the right destination" and "does guidance survive the main crossing", which are the two failures that generate support load.

If Google is adopted, the shape is fixed by the evidence. **Native only in v1**: Android and iOS use Google tiles and Google Routes; web, the public track page and the admin stay on MapLibre/OSRM. **Hide traffic** everywhere in Palestine. **Keep checkpoints app-owned** — Google returns no state, and the OSRM detour is more valuable than Google's geometry. **Fix the refresh policy first**, before the first production key is used: grid 2, 1 km/60 s, per-order caps, no route cache. **No hybrid screen**, ever: a Google map with an OSRM line is the exact arrangement §3.2.3(e) names, and a Places panel beside MapLibre is the same violation without the Places UI Kit exception. The downgrade is whole-session: `maps_quota` or `maps_disabled` flips the map, the line and the ETA together, and never flips back at runtime.

If Google is not adopted — the recommendation — the triggers that would reopen it are specific. A corporate or government contract that names Google Maps; expansion into a market where Google has traffic and street-address coverage (Jordan and the Gulf are the plausible next step); a measured address-coverage failure that costs bookings outside Palestinian city centres; or an SLA requirement the self-hosted stack cannot meet. Until one of those is true, the current stack keeps the moat: OSRM as the pricing and dispatch graph, the checkpoint table, the 15 s public ETA, and a CSP without `unsafe-eval`. Building the dark proxy and the four keys is still worth doing if a trigger is plausible within a year — it costs a few days, ships behind `MAP_PROVIDER=maplibre`, and proves the key restrictions and error mapping before any money is spent.

## Conclusion

The integration question is smaller than it looks and the decision is larger. Google Maps fits the component contract almost perfectly, which is why the "just swap the provider" instinct is reasonable; what it does not fit is the data path, the terms and the West Bank. The product's advantage is not tiles — Google's are better — it is the checkpoint graph, the OSRM detour and a public track page that costs nothing to poll. A Google switch trades those for address coverage and an SLA, and in Palestine it does not even buy traffic.

The number that should decide the next twelve months is not the $27k at 10,000 drivers; it is the **17–30×** gap at 100 drivers between the refresh policy the app has and the one Google requires. That gap is a product decision about how often an ETA refreshes, and it is worth closing regardless of vendor: a 1 km/60 s policy makes OSRM cheaper too, makes the ETA more stable and removes the main reason a future Google pilot would fail on cost. Fix that first, build the dark proxy second, and let a corporate requirement or a measured address failure — not a vendor demo — be what finally moves the map.
