## Explicitly absent or conditional

The historical capability map records no in-app digital wallet/card payment, cash-on-delivery payout ledger, delivery photograph, automatic driver-document upload, tipping, cancellation fee, pooling or customer-defined multi-stop route. Phone/email verification, native push and road routing need service configuration. Newer PostgreSQL-backed capabilities are gated; their tests do not mean that the production service has them switched on. A second-approver workflow for large cash adjustments exists only as the PostgreSQL ops API (`financial_approvals`), not as an admin screen; the live SQLite cash screen can still forgive up to the per-entry cap.

## This pass

- `npm run lint` and `npm run typecheck` passed, including the latest tracking changes. The full integration run passed 85 suites before the last tracking refinement; its focused presentation regression passed afterward. Final end-to-end reruns are in progress.
- The original load fixture contained no searching jobs, so its earlier passing numbers did not measure a populated driver board. The revised local SQLite fixture includes 120 searching jobs, 10,000 historical orders, 60 assigned orders and 121 synthetic accounts. With 60 concurrent requests, read p95 was 246.97 ms, mixed p95 346.74 ms (272 requests hit the expected 429 limiter, not errors), and populated jobs p95 was 244.39 ms and 344.17 ms; critical command acknowledgement p95 was 293.61 ms. There were no errors or timeouts, and 497 idempotent bookings were stored once. This is local synthetic evidence, not PostgreSQL, production-provider, real-user or field capacity evidence.
- The job board exposed only its first 50 matching jobs. The versioned opt-in API now supplies 20-job cursor pages, batches customer statistics and the requesting driver's offers, and preserves the legacy 50-job array. An old or rolled-back API produces a visible compatibility notice instead of a silently repeated page. SQLite and isolated PostgreSQL HTTP tests cover six pages, ties, an eligible scheduled boundary, release/heading filtering and malformed cursors. The fresh three-page browser regression is being rerun. A large accumulation of searching jobs still needs operational monitoring.
- A populated board and the admin dashboard competed for the event loop: the dashboard formatted every historical row into a date. Daily chart totals are now grouped in the database using local-midnight boundaries, retaining zero days and daylight-saving transitions. An isolated HTTP regression covers DST, access control, totals and out-of-window rows; the PostgreSQL HTTP dialect test exercises its numeric results.
- Cached order data could remain visible after definitive access refusal. The client now clears that snapshot on terminal access errors and retains it on transient failures; `npm run test:access` passed on a fresh export, checking refusal, the live watcher and a real driver release.
- A recipient's slow or backward-changing phone clock during an outage could extend a cached public marker. Both polling and live fixes now use the server-adjusted clock, reported age and elapsed monotonic time for the same fix; the ETA/freshness display uses the same age. Unit boundaries and the updated browser outage/clock-change regression passed.
- If road routing is unavailable, the smart quote uses an estimated distance. The booking screen now displays the existing bilingual estimate notice only for that fallback; the customer-location browser regression is being rerun against a fresh export.
- The PostgreSQL logging fixture and isolated migration CLI inherited a 500 ms advisory-lock timeout. They now use a bounded 30-second migration budget; the real CLI passes a regression that holds the lock for 800 ms. Production API request lock limits remain separate. The full `npm run test:persistence` suite passed, including the legacy PostgreSQL workflows.
