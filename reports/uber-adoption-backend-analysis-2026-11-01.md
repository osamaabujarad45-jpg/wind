# Uber knowledge adoption: backend, contracts and operations

Date: 1 November 2026. Scope: read-only analysis of Wind/Fastship against all 910 lines of `C:/UberAppKnowledge/UBER-APP-COMPLETE-KNOWLEDGE-2026-11-01.md` (called **KB** below). No app/backend code, configuration, database, cloud resource or vendor system was changed. This report is the only file created by this research task.

## Decision

Take the study's **explicit contracts, feature-owned client state, bounded failure handling, typed configuration and evidence discipline**. Keep Wind's server-authoritative modular monolith and transactional database. Wind already contains much of the ride lifecycle that the study suggests: leased dispatch offers, revision-bound eligibility/capacity, GPS arrival, a grace clock, passenger-only boarding PIN, locked attempts and reasoned operator recovery. Rebuilding these from the Uber catalogue would duplicate existing work.

The next useful work is to finish the operational proof for those existing protocols, persist driver commands across app restart, and make capability/configuration/diagnostic status precise. A route or module in source is not an activated, tested or field-ready service.

## Evidence limits

- **Uber:** KB lines 6–24 distinguish package measurements, converted source, one bounded runtime session and public material. Lines 17 and 878 say no vendor traffic was captured and no account action was performed by the analyst. Its 1,032 product-call literals, generated models and gRPC names establish the **shipped client's contract surface** (KB 599–663), not the vendor's server implementation, database, assignment algorithm, transaction isolation, SLA, currently callable endpoints or fraud effectiveness. The ordering of route names in KB §23.1 is a useful journey interpretation, not a captured call trace or proven server state machine.
- **Storage:** KB 665–684 describes storage inside the Android client. “No single application database” does **not** mean the vendor's backend has no relational database. Store encryption at rest remains unknown (KB 859). Do not replace Wind's PostgreSQL/SQLite backend with client key-value stores.
- **Driver:** the separate driver binary was not studied (KB 772, 861). A driver route bundled in a rider package does not establish a complete driver experience. In particular, the rider app's lack of background-location permission (KB 382) does not justify removing background tracking from Wind's combined customer/driver app.
- **Wind:** source citations below describe static implementation observed in the current dirty working tree. No tests, cloud probes or physical-device acceptance were run for this report. Tests cited below exist; their presence is not a passing result. Earlier results in [study-implementation-2026-11-01.md](study-implementation-2026-11-01.md:61) are historical claims with their own scope; they were not independently replayed here.
- **Production:** the earlier report explicitly leaves dispatch/boarding activation off and the observed service's PostgreSQL/worker deployment unproven ([study-implementation](study-implementation-2026-11-01.md:134)). Source independently confirms the gates: [runtime.ts](../server/db/runtime.ts:4), [eligibility.ts](../server/domain/eligibility.ts:21), [ride-lifecycle.ts](../server/domain/ride-lifecycle.ts:19). Nothing below asserts production readiness.
- **Source priority:** [PRODUCT.md](../docs/PRODUCT.md:49) sets Wind's three service types and local operating needs; [SYSTEM.md](../docs/SYSTEM.md:17) calls for a modular monolith. Some “current repository” text in [SYSTEM.md](../docs/SYSTEM.md:127) and historical study tracker material predates newer protocols. Current source and activation gates take priority over an old “absent” matrix or an old “built” paragraph. [CURRENT-WORK.md](../docs/CURRENT-WORK.md:35) also retains an earlier pending security-investigation decision; KB 743–745 closes that register. This analysis does not reopen it.
