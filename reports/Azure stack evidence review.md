# Keep OSRM and phone OTP, adopt Azure hosting

**Fastship/Wind cannot buy an Uber-quality stack from Azure in Palestine, but it can buy the half that matters.** A live test on 29 October 2026 overturned the earlier documentary reading of Azure Maps: it rendered Ramallah streets at z16, geocoded Ramallah and Nablus in English and Arabic, and routed Ramallah–Nablus at 54.5 km/55 min against the public OSRM demo's 53.5 km/62 min. It still cannot supply what Uber-quality dispatch needs — real-time Palestinian traffic, checkpoint/closure semantics, truck restrictions, or landmark geocoding (Qalandia and Huwwara return zero; "Checkpoint 300" resolves to the Philippines) — so maps and OTP stay with the current OSRM/MapLibre stack and an app-owned phone verification flow. Entra External ID has no phone-first factor and blocks +970 by default, and Azure Communication Services' direct SMS has no Palestinian destination. Azure does supply the operational layer credibly: Web PubSub for fix fan-out, Container Apps for API and worker, PostgreSQL/PostGIS as the system of record, Blob and Key Vault for evidence and secrets, all in Israel Central at a documented price. The catch is that Israel Central has **no paired region**, the composite single-region SLA is about **99.75%**, and the Container Apps request meter costs **$2,627 a month at 10,000 drivers** updating every four seconds — more than the realtime service. This report closes the five items the 26 October report left unverified and turns each into adopt/augment/defer/reject plus the test that would overturn it. **No application was deployed, no real tenant, real SMS, or device run was performed**; evidence is documentary, a live price-API reading, a temporary Azure Maps account used for the coverage test and deleted the same day, or repo code at commit `df43da8`.

All URLs were retrieved on **2026-10-29**, with Microsoft's own page dates where published. Labels: **[D] documented**, **[O] observed** (live Retail Prices API, public repo, this codebase), **[U] unverified**. The working tree held uncommitted edits during research, including a malformed `package.json` dependency named `"undefined"`; that is a transient concurrent edit, absent from `df43da8`, and excluded here. All code statements refer to `df43da8`.

## Azure Maps has Palestinian data — the docs understate it

Microsoft's coverage pages are internally inconsistent and do not match the live service. The current routing table lists `Palestinian Authority¹` with a check only for Route Directions and Snap to Roads; footnote 1 means partial road data covering at least major roads. An older table on the same page omits the row entirely ([Routing coverage](https://learn.microsoft.com/en-us/azure/azure-maps/routing-coverage), 2026-10-02). The render, geocoding and traffic pages contain no Palestinian entry ([Render coverage](https://learn.microsoft.com/en-us/azure/azure-maps/render-coverage), 2026-09-17; [Geocoding coverage](https://learn.microsoft.com/en-us/azure/azure-maps/geocoding-coverage); [Traffic coverage](https://learn.microsoft.com/en-us/azure/azure-maps/traffic-coverage)), yet live calls return West Bank tiles, city geocodes and routes. Documentation alone cannot settle coverage; the live call can.

A temporary Gen2 account was created on 29 October 2026 and tested from this host, then deleted. The full method and results are in the [live test note](<../research_notes/Azure stack evidence review/azure_maps_live_test.md>); the short version:

| Test | Live result | Consequence |
|---|---|---|
| Render Ramallah z16 | 16,699-byte PNG with Al Manara Square, Al-Muntazah Park, Sharia Jaffa, Al-Ahli Hospital and street geometry | Rendering works; the render-coverage page is wrong for the West Bank |
| Route Ramallah → Nablus | 54.5 km, 55 min, 1,317 points | Within 1 km of the public OSRM demo's 53.5 km; time is 7 min faster |
| Route Ramallah → Hebron / Jerusalem / Qalandia | 56.5 km/61 min; 23.4 km/32 min; 6.9 km/18 min | Major-road routing works across the sample |
| Geocode `Ramallah`, `Nablus`, `رام الله` | West Bank, High/Medium confidence | City-level English and Arabic geocoding works |
| Geocode `Qalandia`, `Huwwara`, `Checkpoint 300` | 0 features; 0 features; Philippines, Low | Landmark and checkpoint geocoding is unusable |
| Route with `travelMode=truck` | 55.5 km/64 min returned | No Palestinian truck coverage, so restrictions are not trustworthy |
| Traffic flow tile and route delay | Blank 1,241-byte tile (same as Tel Aviv control); every route `trafficDelayInSeconds: 0` | No usable real-time Palestinian traffic |

The "partial" label still bounds the win: major roads are covered, not address points, traffic, truck limits, or checkpoint state. The live Ramallah→Nablus route is credible, but the API has no concept of a closed checkpoint, a permit-gated segment, or a settlement bypass road. The repo treats closures as first-class — drivers report checkpoint state, routes within 200 m of a closed checkpoint are rerouted, and public ETA flags delay without naming the checkpoint ([server/main.ts](<../server/main.ts>)) **[O]**. Replacing that with a provider that has no such concept would be a downgrade even though the tiles load.

Cost is the second reason not to make Azure Maps primary. Gen2 bills **$4.50 per 1,000 transactions** below 500K/month, with 15 tiles per render transaction and one request per route transaction ([Transactions](https://learn.microsoft.com/en-us/azure/azure-maps/understanding-azure-maps-transactions); [Pricing](https://azure.microsoft.com/en-us/pricing/details/azure-maps/), built 2026-10-27). Two hundred drivers panning 100 tile-transactions a day is 600,000 transactions, roughly **$2,678/month**; 10,000 trips at 20 route calls each is **$895/month**; the same load on self-hosted OSRM and OpenFreeMap has zero marginal cost **[O]**. Autocomplete is the one favourable meter (10 requests = 1 transaction, 50,000 free requests/month), but city-only geocoding and failed checkpoint queries limit its value.

Two secondary facts limit even the "augment" path. Azure Maps has only EU and US residency geos and shares every location query with TomTom as a subprocessor ([Geographic scope](https://learn.microsoft.com/en-us/azure/azure-maps/geographic-scope); [What is Azure Maps](https://learn.microsoft.com/en-us/azure/azure-maps/about-azure-maps)). And there is no first-party React Native SDK: both native SDKs are retired, the migration guide says to embed the Web SDK in a WebView, and the only RN wrapper is explicitly unofficial ([Android migration](https://learn.microsoft.com/en-us/azure/azure-maps/android-sdk-migration-guide); [react-native-azure-map](https://github.com/ibrahimMH13/react-native-azure-map)). A second rendering engine in a WebView, on low-end Android, to duplicate tiles the app already renders is not a trade worth making.

## Entra can hold the account but not the phone number

External tenants support exactly two local first factors — email with password and email with one-time passcode — plus social/OIDC/SAML federation ([Identity providers](https://learn.microsoft.com/en-us/entra/external-id/customers/concept-authentication-methods-customers)). SMS exists, but the documentation is unambiguous: "SMS is available at an additional cost for second-factor verification and for self-service password reset in external tenants. **It isn't currently supported for first-factor authentication**" ([MFA in external tenants](https://learn.microsoft.com/en-us/entra/external-id/customers/concept-multifactor-authentication-customers)). There is no phone-as-username, no phone-only local account, and the preview username/alias option still pairs with a password. For a product whose promise is "enter your number, get a code, you're in", Entra cannot be the system of record for that step.

The workaround is real but has a price. Either the app/BFF verifies the phone and maps it to an Entra account keyed on a synthetic email, or a custom OIDC provider doing phone OTP is federated in. The second path is supported, but federated users cannot register passkeys and cannot use native authentication for that leg ([MFA in external tenants](https://learn.microsoft.com/en-us/entra/external-id/customers/concept-multifactor-authentication-customers)). Passkeys are narrower than the marketing: only email+password local accounts can register one, and **authentication strengths cannot be enforced in Conditional Access**, so "phishing-resistant MFA required" is not a policy you can set for riders ([Passkeys in External ID](https://learn.microsoft.com/en-us/entra/external-id/customers/how-to-sign-in-with-passkey), 2026-10-06).

Then there is Palestine specifically. The **Palestinian National Authority sits in the "Phone Authentication High Cost" bucket**, the most expensive of four tiers, and SMS is billed **per verification attempt**, including retries and abandoned flows ([MFA in external tenants](https://learn.microsoft.com/en-us/entra/external-id/customers/concept-multifactor-authentication-customers); [External ID pricing](https://learn.microsoft.com/en-us/entra/external-id/external-identities-pricing)). The 50,000 free MAU tier is therefore not the constraint; the SMS meter is. More decisively, **+970 is on the list of country codes deactivated by default for SMS verification**; enabling it requires a Graph `onPhoneMethodLoadStart` event listener with `includeAdditionalRegions`, a **preview** feature applied per application, and a blocked number surfaces the message "Try another verification method" ([Regional opt-in](https://learn.microsoft.com/en-us/entra/external-id/customers/how-to-region-code-opt-in), 2026-04-17). The opt-in lever is a country-code allowlist, not an identity model. Per-number throttles are 15 texts per 15 minutes, 30 per 24 hours, 50 per 7 days ([Service limits](https://learn.microsoft.com/en-us/entra/external-id/customers/reference-service-limits)).

The per-IP limit is a Palestine-specific hazard. Sign-in and sign-up are capped at **20 requests/second per IP**, and a sign-in consumes four dynamic-endpoint requests, so one carrier NAT can throttle a morning peak for many users at once ([Service limits](https://learn.microsoft.com/en-us/entra/external-id/customers/reference-service-limits)). Palestinian mobile traffic commonly sits behind carrier NAT **[U]**; this needs a test from a real carrier egress, not a lab.

ACS does not rescue the SMS path. Its sender-availability table lists 26 destinations — US, Canada, Puerto Rico, UK and a set of EU countries — with **no Palestine, no Israel, and no MENA country**, and senders are explicitly country-scoped ([SMS overview](https://learn.microsoft.com/en-us/azure/communication-services/concepts/sms/concepts), 2026-09-23). There is no +970 price because there is no +970 offer ([SMS pricing](https://learn.microsoft.com/en-us/azure/communication-services/concepts/sms-pricing)). The only Microsoft-blessed route is **Messaging Connect in public preview with Infobip**, where the partner determines country availability, Azure charges **$0.0025 per submitted request whether or not it delivers**, delivery reports arrive asynchronously, and the preview carries no SLA ([Messaging Connect](https://learn.microsoft.com/en-us/azure/communication-services/concepts/sms/messaging-connect)). If an alphanumeric sender is the only realistic type for +970, the channel is one-way and opt-out handling becomes the app's problem.

Email does work, and is the sensible home for receipts and recovery fallback: ACS Email supports a managed subdomain or a custom domain with ownership proof plus SPF and DKIM ([Email domains](https://learn.microsoft.com/en-us/azure/communication-services/concepts/email/email-domain-and-sender-authentication)). WhatsApp is a candidate channel but a moving target: Meta's BSUID change allows `from`/`to` to be empty when a user hides their number, breaking the assumption that the number is the notification identity ([WhatsApp overview](https://learn.microsoft.com/en-us/azure/communication-services/concepts/advanced-messaging/whatsapp/whatsapp-overview)). Every ACS SMS and WhatsApp page also carries Microsoft's breaking-changes banner; the specific 2027 retirements were not read **[U]**.

The integration reality reinforces the earlier report's decision to exclude Entra from the initial migration. React Native is absent from Microsoft's supported-framework lists for both browser-delegated and native authentication, so the supported path is system-browser authorization code + PKCE with the app as a public client and the BFF validating issuer/JWKS ([Choose an authentication approach](https://learn.microsoft.com/en-us/entra/external-id/customers/concept-choose-authentication-approach)). That is standards-based and should work, but is not documented as supported **[U]**. Tenant configuration is Graph-only — no Bicep resource for user flows, identity providers, or auth methods was found — so IaC becomes a Graph scripting step.

The recommendation is narrow and cheap. Keep current auth for riders: it already returns generic `wrong_credentials`, throttles per identity and IP, revokes all sessions on logout/reset/role change, and stores native tokens in SecureStore ([server/main.ts](<../server/main.ts>); [src/api.ts](<../src/api.ts>)) **[O]**. Use Entra workforce for the ~30 staff accounts, where passkeys and Conditional Access are a genuine upgrade and no Palestinian SMS is involved. Revisit External ID only if social login or enterprise SSO becomes a product requirement, and budget phone verification as your own service either way.

## Web PubSub is the right primitive, with no React Native client

Web PubSub maps almost one-to-one onto the current design: one group per order, one connection per viewer, a server-issued short-lived token carrying `userId` and group-scoped roles, and 1 MB frames ([Client access URL](https://learn.microsoft.com/en-us/azure/azure-web-pubsub/howto-generate-client-access-url); [Key concepts](https://learn.microsoft.com/en-us/azure/azure-web-pubsub/key-concepts)). The planning numbers are **1,000 concurrent connections per unit**, with Microsoft advising no more than **80% utilisation** before scaling, and **2 GB outbound per unit per day** included, billed per 2 KB of outbound rather than per frame ([Billing model](https://learn.microsoft.com/en-us/azure/azure-web-pubsub/concept-billing-model)). Standard carries a **99.9%** SLA and Premium **99.95%**, with autoscale and geo-replication only on Premium; the subscription soft quota is 150 units per region ([Pricing](https://azure.microsoft.com/en-us/pricing/details/web-pubsub/); [Manual scale](https://learn.microsoft.com/en-us/azure/azure-web-pubsub/howto-scale-manual-scale)).

The client is the work. The JavaScript SDK is documented for Node.js and browsers, Metro fails on its `events`/`ws` requires, the RN support issue was auto-closed as stale without a fix, and Microsoft's maintainers say a React Native app should speak the native `WebSocket` object and fetch a token from a `/negotiate` endpoint ([SDK README](https://github.com/Azure/azure-sdk-for-js/blob/main/sdk/web-pubsub/web-pubsub-client/README.md); [issue #26400](https://github.com/Azure/azure-sdk-for-js/issues/26400); [azure-webpubsub#445](https://github.com/azure-webpubsub/issues/445)). That is a modest but real client deliverable: connect, refresh on 401/expiry, reconnect after airplane mode, Android Doze, and Wi-Fi↔4G handover, plus snapshot reconciliation for missed messages. No first-party RN sample exists, so this is **[U]** until the field walk in the acceptance matrix passes.

SignalR is the wrong twin even though price and capacity are identical, because it bills server connections against the quota at **five initial connections per hub per app server** — two replicas across three hubs consume 30 connections before a rider connects — and its JavaScript client has an open, unresolved React Native issue ([Messages and connections](https://learn.microsoft.com/en-us/azure/azure-signalr/signalr-concept-messages-and-connections); [dotnet/aspnetcore#60606](https://github.com/dotnet/aspnetcore/issues/60606)). With a Node backend there is no ASP.NET hub machinery to gain; Web PubSub wins on the absence of a server tax and the raw-WebSocket contract the app must write anyway.

The repo has already made the procurement decision and not the wiring decision. `infra/main.bicep` provisions `Microsoft.SignalRService/webPubSub` Standard_S1, capacity 1, local auth disabled, AAD enabled, while `server/main.ts` still holds `LIVE_HOLD = 12_000, LIVE_WATCHERS = 20, LIVE_TOTAL = 200` and an in-process `fixWaiters` map whose own comment says several instances need shared pub/sub ([infra/main.bicep](<../infra/main.bicep>); [server/main.ts](<../server/main.ts>)) **[O]**. The 200-watcher cap is a process-local slot limit, not a protocol limit; one Standard unit replaces it at **$2.30/day**. That is the highest-value adoption in the whole stack: it removes the single-replica correctness constraint that currently makes `maxReplicas: 2` worse rather than better.

Chat belongs on the same hub, with history in Postgres rather than in the service, because Web PubSub is a delivery channel and not durable storage. Event Hubs is a separate decision and should stay deferred: at 10,000 drivers sending one fix every four seconds the load is **2,500 events/s**, which is event-rate-bound at **3 throughput units** (~$88/month) plus **$263/month** in ingress events, and it only becomes justified when a second consumer appears — ETA model, surge, fraud — or when GPS writes exceed roughly 20% of database CPU ([Event Hubs quotas](https://learn.microsoft.com/en-us/azure/event-hubs/event-hubs-quotas); [Retail API](https://prices.azure.com/api/retail/prices)) **[O]**.

## One region, no pair, and a request meter that follows the driver

Container Apps is a credible host: HTTP/1.1 and HTTP/2 ingress with WebSocket and gRPC, a 240-second request timeout, KEDA/HTTP/TCP scale rules, managed identity, and a **99.95%** SLA ([Ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview), 2026-10-22; [Scaling](https://learn.microsoft.com/en-us/azure/container-apps/scale-app)). It is also stateless and single-region by design: local storage is deleted on restart, there is no built-in backup, and a regional outage takes the environment with it ([Reliability](https://learn.microsoft.com/en-us/azure/reliability/reliability-container-apps)). Zone redundancy must be enabled at environment creation, needs at least two replicas to matter, and does not raise the SLA number.

The cost surprise is the request meter. At 0.25 Hz per driver, 10,000 drivers produce 2,500 requests/s, or **6.57 billion requests a month**, which at $0.40/M is **$2,627** — larger than Web PubSub's **$1,748** at the same scale. At 100 drivers it is $26; at 1,000 it is $263. Batching client fixes to 0.1 Hz and interpolating on the handset cuts that line to **$1,051/month** at 10,000 drivers, a 60% reduction for a change in one client constant ([Retail API](https://prices.azure.com/api/retail/prices)) **[O]**. This is the single highest-leverage cost decision in the stack, and it is a product decision about perceived smoothness, not an infrastructure one.

PostgreSQL is the other place where the cheap tier is a trap. B1ms allows **35 user connections**; Burstable supports neither HA nor the built-in PgBouncer pooler, and Microsoft recommends PgBouncer sized at 2–5× vCores ([Limits](https://learn.microsoft.com/en-us/azure/postgresql/configure-maintain/concepts-limits), 2026-07-08). A multi-replica API plus worker plus admin sessions does not fit in 35. B2s at **$58/month** is the cheapest configuration that avoids connection gymnastics, and PostGIS 3.6.1 plus pgRouting 3.8.0 are available on PG 16–18 ([Extensions](https://learn.microsoft.com/en-us/azure/postgresql/extensions/concepts-extensions-versions)). Zone-redundant HA reaches **99.99%** with 60–120 s failover, but requires General Purpose or Memory Optimized and bills a standby at the primary's rate; no-HA is **99.9%**, about 43 allowed minutes a month ([Reliability in PostgreSQL](https://learn.microsoft.com/en-us/azure/reliability/reliability-database-postgresql)).

Region choice is where the earlier report's West Europe baseline needs revision, not reversal. Israel Central has **3 availability zones, opened in 2023, and paired region "N/A"** ([Region list](https://learn.microsoft.com/en-us/azure/reliability/regions-list), 2026-10-12). It carries a **~43% premium** on realtime — $2.30/unit-day and $1.43/M messages versus $1.61 and $1.00 in UAE North, Qatar, and West Europe — while Container Apps requests are actually cheaper there ($0.40/M vs $0.56/M) **[O]**. It is the only region with a plausible single-digit-to-low-tens-of-milliseconds last mile to the West Bank, but **no Microsoft page quantifies user-to-region latency**; the published latency dataset is datacenter-to-datacenter, and the Ramallah number does not exist yet **[U]**.

Data residency cuts both ways: Israel Central means "stored at rest in Israel", which is a datacenter statement, not a legal opinion about Palestinian users' data or Israeli jurisdiction over it ([Data residency](https://azure.microsoft.com/en-us/explore/global-infrastructure/data-residency)). That question needs counsel before production, and it is the gate that decides whether the latency win is available at all. If counsel rejects Israel-resident data, West Europe remains the fallback and the latency target must be measured and probably loosened.

The reliability arithmetic is unforgiving and should be stated plainly rather than buried. `0.9995 × 0.999 × 0.999 = 99.750%`, about **1.83 hours** of allowed platform downtime per month; with Postgres HA it rises to `99.840%`, about 1.17 hours. Neither figure includes Front Door, DNS, OSRM, the mobile network, or deploy cadence, and **neither survives an Israel Central regional failure**, which is a 100% outage with no paired region to fail over to. Cross-region read replicas are asynchronous, lag "at least several minutes", and promote **manually** — Azure never auto-promotes on region failure ([Reliability in PostgreSQL](https://learn.microsoft.com/en-us/azure/reliability/reliability-database-postgresql)). The honest promise to riders is measured p95 latency and a tested runbook, not 99.99%.

## A phased path from $183 to $3,270 a month

Costs below are list-price arithmetic on the 2026-10-29 Retail API readings for Israel Central, before tax, discounts, storage, egress, logs, SMS, push, OSRM compute, and support. They are planning figures, not quotes **[O]**.

The pilot floor is deliberately boring: one Standard Web PubSub unit ($70), one always-on 0.5 vCPU/1 GiB replica ($55), one B2s ($58). The $55 replica is the price of avoiding an unmeasured cold start — Microsoft publishes no scale-to-zero latency figure, so `minReplicas: 0` is a gamble, not a saving **[U]**. Now is mostly not Azure work: fix the release blocker, keep the 74-suite gate green, instrument crash-free sessions and p95, and finish the dispatch/Postgres migration. Pilot the thin slice: Web PubSub behind a token endpoint, one API replica, B2s, Blob and Key Vault in Israel Central, with the OTP adapter pointed at a local aggregator and ACS Email for receipts. Defer everything with a trigger — Event Hubs at a second consumer, HA at a funded reliability target, multi-region at funded DR, External ID at a social/SSO requirement.

## Conclusion

The evidence changes the shape of the Azure question. In October the open items were unknowns that might have gone either way; they are now a documented negative for phone-first identity, a usable-but-undifferentiated map, and documented positives for hosting and realtime. The path to an Uber-quality bar in Palestine therefore runs through **fewer Azure services, not more**: Azure supplies the operational floor — durable compute, a real database, a 99.9% realtime channel, private storage — while the two services that touch the rider most directly, the map and the phone number, stay local and owned.

The trap is buying the wrong half. Azure Maps is the most expensive option in the stack and adds no traffic, checkpoint, truck or landmark-geocoding advantage, and Entra External ID would add a tenant, a Graph-only configuration surface, and a preview telephony opt-in without removing the need to run phone verification yourself. The cheapest wins are unglamorous: batch driver fixes to 0.1 Hz, keep OSRM, move waiter state into Web PubSub, and size Postgres at B2s so a second replica is possible. The honest reliability promise is a measured p95, a tested failover, and a runbook — not a composite SLA that drops to zero the moment Israel Central does.

## Session recommendation

1. **Do not migrate maps to Azure Maps.** Keep MapLibre + OpenFreeMap + OSRM as the system of record. Azure Maps is a credible server-proxied fallback for city geocoding or raster tiles if OpenFreeMap/OSRM fails, never for checkpoint routing, truck restrictions, or traffic ETA.
2. **Keep phone OTP and password auth app-owned.** Use Entra workforce for staff MFA/passkeys. Revisit Entra External ID only when social login or enterprise SSO becomes a requirement; it cannot be the phone-number system of record.
3. **Adopt the Azure operational floor.** Web PubSub Standard (one hub, `order:<id>` groups, raw WebSocket client), Container Apps at ≥2 replicas, PostgreSQL Flexible B2s + PostGIS, Blob Hot LRS, Key Vault + managed identity, Israel Central primary.
4. **Make the cost decisions now.** Batch driver fixes to 0.1 Hz before sizing; pilot at about **$183/month** (plus OSRM compute), and plan **$3,270–5,062/month** at 10,000 drivers. Reconcile the request meter in month one.
5. **Treat reliability as a runbook, not a badge.** Israel Central has no paired region; measure p95 from Ramallah/Nablus/Hebron, drill a Postgres failover, and defer HA/multi-region until a funded target exists.
6. **Do not claim Uber quality.** Run the remaining field tests (phone carriers 4–8, raw WebSocket 10, latency 11, unit sizing 12, failover 13, cost 14) and publish measured results before any launch claim.
