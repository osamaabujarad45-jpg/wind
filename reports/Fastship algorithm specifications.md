## D01 — Core domain and ownership

Model `User`, `Session`, `DriverProfile`, `Vehicle`, `DriverSession`, `ServiceRegion`, `Product`, `Quote`, `Booking`, `Offer`, `Assignment`, `Itinerary`, `Stop`, `FulfillmentEvent`, `PaymentIntent`, `LedgerJournal`, `Payout`, `Evidence`, `SupportCase` and `PolicyVersion`. Shared identifiers are opaque server IDs. Booking stores product (`ride`, `parcel`, `freight`), customer, immutable quote/policy snapshot, locations and revision. Driver sessions distinguish offline/available/offered/assigned/occupied/paused; driver and vehicle approval are separate conditions. Keep product-specific fields typed: rides require seats/accessibility, parcels require pieces/weight/handoff/declared value/COD beneficiary, freight requires dimensions/load class/crew/vehicle capacity/handling/windows. Do not turn one parcel boolean into all product logic. Invariants: one active exclusive assignment per driver; one active assignment per booking; no cross-city accidental allocation; all monetary records carry currency and integer minor units with checked overflow.

## D02 — Authentication and account lifecycle

Normalize phone to E.164 with explicit country context; preserve display form. Make OTP issuance server-only, cryptographically random, short-lived and single-use. Store an HMAC of OTP + challenge ID with secret held outside client code, attempt count, expiration, resend time and audit reason; return generic account responses. Rate-limit by phone, IP and device using conservative shared limits and abuse escalation. A verified OTP proves phone control, not driver identity. Use short-lived access tokens with rotating refresh families; detect refresh reuse, revoke device or all sessions, and support logout/recovery, phone change with re-verification, role change and account deletion workflow. Admin accounts need stronger authentication and server permissions. Initial pilot hypothesis: 5-minute OTP validity, 5 attempts, 45-second resend cooldown, hard phone/device limits of 3 challenges per 15 minutes and 10 per day, provider-wide spend budgets, and an abuse-review signal at 30 challenges per IP per hour; shared-carrier NAT alone must not hard-block legitimate users; test real SMS delivery and false blocks before release. All endpoints reject expired/replayed challenge, revoked role and user-supplied role escalation. Keep development/test OTP isolated by environment; production startup must reject a bypass flag.

Migration delta: preserve existing scrypt passwords, hashed tokens, verification/reset flows and SecureStore behavior. Add OTP as the phone-verification extension after validating the prescribed local-provider adapter; preserve password login for installed users. Do not force existing users to re-register or replace working identity with mock SMS. Shorter/rotating sessions require a compatible migration, active-device revocation and explicit recovery path.

## D03 — Driver and vehicle eligibility

Onboarding lifecycle: draft -> submitted -> under_review -> approved OR changes_required/rejected -> suspended/expired. Documents have type, issuer, expiry, review history and restricted storage; vehicle inspection/capacity and legal operator permissions are recorded independently. Availability eligibility is computed server-side from current approval, document expiry, vehicle match, service zone, settlement/debt policy and active duty restrictions. Suspend future matching immediately on expiry; define an operations workflow for an already active trip instead of abandoning the passenger. Every approval/override has named operator, reason and audit timestamp. Avoid automatic biometric or criminal-background claims until a lawful supported vendor/process exists.

## D04 — Location ingest and battery/network behavior

Extend the existing age-based ingest; do not replace it with trust in a phone clock. The additive sample envelope is `{deviceSessionId, seq, ageMs, recordedAt?, lat, lng, horizontalAccuracyM, speedMps?, headingDeg?, source}`. `recordedAt` is diagnostic metadata only. The server uses its own `receivedAt` and the validated age to derive effective fix time, preserves the current stale/outlier/replay checks and binds each fix to the current authorized device session and assignment epoch. Existing clients sending the current `age` field remain compatible; no-age legacy requests retain their current behavior while supported. Sequence numbers add ordering within a session; they do not let stale fixes become current. A location from a former driver or assignment must never enter the current tracking channel. ([Current ingest](<C:/Users/osama/OneDrive/Documents/ChatGPT/Fastship/server/main.ts:1754>), [client age contract](<C:/Users/osama/OneDrive/Documents/ChatGPT/Fastship/src/location-delivery.ts:22>))

Keep production persistence at the latest accepted fix by default. Add pre-assignment latest-location collection only during the driver's explicitly consented online session; stop collection when offline, logout, suspension or permission revocation ends that authority. Do not introduce continuous customer tracking, automatic raw history or a stale offline-location queue. Only separately consented field-validation sessions can retain short-lived trace samples, with a declared purpose, restricted access, a 24-hour pilot retention default and automatic deletion; a documented case hold is a separate authorized process. Commands can queue with stable IDs; stale GPS cannot refresh availability after reconnect. Map interpolation never creates payable distance. Replies distinguish accepted/deduplicated/rejected; freshness and last-known status remain separate facts.

Prescribed initial configuration, pending pilot validation: moving online driver sends at most every 5 seconds when the OS supplies a fresh fix, stationary online driver every 15 seconds, matching requires fix age no more than 30 seconds, and a 60-second server presence lease without its 15-second heartbeat renewal expires new-job availability. Preserve the existing 2-second transport rate floor. These are explicit pilot test values, not platform background-delivery guarantees. An active order remains recoverable after availability expires. Physical-device tests cover app kill/relaunch, background/foreground, low-power mode, consent revoked, device clock skew, wrong session/epoch, old sequence, provider errors and stale replay. Changing these values requires passing battery, network and freshness regression checks.

## D05 — Geocoding, addresses and serviceability

Store structured address plus Arabic/English free text, landmark, building/floor/unit, contact instructions, coordinates, provenance, precision/confidence and chosen entrance/pickup point. Geocoding disagreement requires user confirmation; do not move a known building to a nearby city to satisfy routing. Serviceability = pickup polygon AND destination corridor permissions AND product/vehicle eligibility AND operational hours/capacity. Boundary rules use one deterministic geometry policy with versioned zones and an exception workflow. Use PostGIS for coarse candidate selection; exact polygon/corridor checks remain authoritative. Test duplicate names, transliteration, rural landmarks, apartment access, boundary points and addresses without street numbers.

## D06 — Palestine checkpoint and closure policy

Maintain versioned road restrictions with directed geometry/edge IDs, affected vehicle/products, validity interval, source, last confirmation, confidence, status (`open`, `closed`, `restricted`, `unknown`) and operator review. `unknown` or stale is not equal to open. Route result records provider version, restriction version, timestamp and feasibility decision. If a corridor closes after quote, re-route and estimate delay; if no verified feasible route remains, pause assignment/request reconfirmation or cancel through an explicit no-fee/exception policy. Passenger/driver support must be able to stop/replan an active job. Never market a route as safe or promise that an app knows live checkpoint conditions. Crowd reports need corroboration, expiry and moderation; do not automatically publish identifiable movement reports. Route uncertainty should widen ETA intervals or prevent a guaranteed booking. Test conflicting reports, no data, stale update, reverse-direction restriction and closure during pickup/in-progress.

## D07 — Routing, travel distance and ETA

Use road-network routing and a duration matrix for the small shortlisted candidate set; Euclidean distance is only a coarse search bound. Cache only where map-provider terms permit, with time bucket/product/vehicle and restriction-version keys. Pickup ETA = dispatch latency estimate + driver road travel + pickup-access allowance. Delivery ETD = remaining drive + known stop service times + handoff allowance + delay adjustment; freight adds loading/unloading. V1 uses the validated road-provider baseline plus measured zone/time median bias and quantile intervals, with no ML predictor enabled. The later gated phase trains the residual model `ETA = max(0, baselineETA + f(originZone,destinationZone,hour,weekday,vehicle,jobStage,traffic,checkpointState))`; never train on future information or leak one job across train/test sets. Monitor MAE, median/p90 absolute error, promised-window coverage and error by geography/network/product; a model ships only if temporal holdout and shadow mode improve over baseline. Recompute on material route/stage changes, not each animation frame. Provider outage uses a clearly degraded last route or blocks fresh precise quotes; straight-line distance must not become a normal billable road price.

## D08 — Immutable quotes and pricing

Represent each quote as `{quoteId, expiresAt, currency, lineItems, routeSnapshot, routeVersion, policyVersion, product, scope, limits, cancellationPolicy, adjustmentPolicy}` with a fixed v1 lifetime of 120 seconds. Preserve existing tariff settings and whole-ILS payable rounding while storing authoritative amounts as integer minor ILS; do not silently change prices because the storage unit changes. Sample recommended equation in integer-money-safe arithmetic: `subtotal = max(minimumFare, baseFare + distanceRate*billableKm + timeRate*billableMinutes + productSurcharges)`; `total = subtotal + reservation/handling/waiting/tolls + tax - fundedDiscount`. V1 surge multiplier is exactly 1 and cannot alter a quote; retain the versioned configured base tariff. The deferred surge experiment applies only to base transportation, never tax, tip, COD principal or pass-through charges. Currency rounding happens once per policy-defined line, and line sum must equal total. Rides use an upfront price for the accepted scope; parcels use the existing tariff with typed size/weight scope and return rules; freight uses negotiated accepted offers with expiry and scope. V1 preserves current configured payable fares while the immutable quote representation is added. Destination/stop change obtains a new quote revision and explicit customer acceptance; preserve the previous price history. Idempotent booking creation consumes a valid quote without generating different totals on retries.

Keep surge disabled throughout v1. Fixed existing tariffs with operator-managed versioned zones are the prescribed launch policy. A later separately gated shadow experiment uses smoothed surge: `ratio = weightedUnservedDemand / max(eligibleIdleSupply, supplyFloor)`; `target = clamp(1 + alpha*max(0, ratio-targetRatio), 1, cap)`; smooth over time and neighboring cells, apply hysteresis, movement rate limit and minimum sample size, and freeze multiplier in the quote. Prevent duplicated requests/artificial location signals from inflating demand. Log explainable factors; disaster/emergency controls can freeze surge. No model based on protected traits, battery level, desperation or guessed willingness to pay. Simulate oversupply/undersupply/no supply, boundary oscillation and attacks; confirm quoted prices do not change while waiting.

## D09 — Dispatch candidate generation

Candidate pool = approved eligible drivers whose fresh location lies within the permitted road-service region; product vehicle/seats/cargo limits match; driver is not paused, already exclusively assigned, blocked by safety pair or outside financial policy. Use spatial index to retrieve coarse nearest candidates, then route-time matrix and restriction feasibility. Expand search gradually only within published pickup-time ceiling, never across inaccessible corridors. Exclude recently declined/timed-out same request for a cooldown; driver refusal is not a reason to silently lower safety checks. Distinguish automatic dispatch from negotiated marketplace bidding: standard passenger rides use `instant_dispatch`, freight uses `negotiated_offer`, and parcels retain `courier_batch` with capacity-aware acceptance. Policy is per product and shown consistently in booking semantics.

## D10 — Dispatch ranking and assignment optimization

Launch with deterministic sequential offers. Remove every infeasible pair before ranking; estimate pickup by road time and use the fixed initial score `C = pickupETAsec - min(60, floor(idleAvailableSec / 10))`, then break ties by opaque driver ID. The capped one-minute idle credit cannot rescue an inaccessible route or a driver outside the pickup ceiling. Record the road ETA, idle credit, policy version and reason for each decision. This is an independently proposed, testable default; it is not Uber's cost function. Rating is not a distance proxy and does not replace safety blocks or hard eligibility.

Defer learned acceptance/no-show models and global batch optimization until the deterministic dispatch pilot passes. The prescribed later experiment is a 2-second request microbatch solved with min-cost bipartite matching over feasible exclusive ride/freight pairs, minimizing `sum(Cdr*xdr) + unservedPenalty` under one request per exclusive driver, one driver per request and maximum-wait constraints. Benchmark a bounded solver deadline; timeout falls back to deterministic ranking. Courier insertion is the separate capacity-aware D23 algorithm. Shadow replay must improve wait time without worsening cancellations, service coverage or driver earnings concentration before any live rollout. Uber public documentation does not establish these weights, interval or solver choice.

## D11 — Offer lease, race safety and retries

Offer states `issued -> accepted | declined | expired | revoked`; includes offer ID, booking revision, driver session, lease expiry and opaque nonce. A notification is only a hint. Acceptance transaction locks/checks booking, driver and live offer, compares expected revisions, checks server-time expiry, claims both resources, writes assignment and outbox event, commits; uniqueness constraints enforce both invariants even across processes. Return conflict for late/double acceptance. Initial test defaults: 15-second offer TTL, at most 3 sequential offers within a 90-second customer search ceiling; tune with drivers. Expiry/retry is a durable worker action, not a phone timer. Retry only while booking remains searchable, scope unchanged and no live assignment exists. Worker restart reconstructs unfinished leases; duplicate expiry messages cannot cancel a later accepted offer. Before widening search, recompute route availability and ETA. Terminal no-supply frees preauthorization and offers explicit retry/schedule behavior.

Acceptance, cancellation, quote-scope change and timeout all compete through the same booking revision and transaction boundary. Clock authority is database/server time with monitored clock synchronization; client time is metadata only. If cancellation wins, later acceptance fails; if acceptance wins, cancellation applies the assigned-stage policy. Lease release is conditional on the same offer/assignment ID and revision, never an unconditional `driver=available` update that might free a driver newly committed elsewhere. Current same-order atomic SQLite claim is a valuable baseline; multi-instance database constraints and driver-resource checks extend it. For parcel runs, capacity reservations are a locked/versioned resource with a different invariant from exclusive ride/freight allocation.

## D12 — Passenger trip state and guards

Preserve the installed-client order lifecycle `searching -> assigned -> at_pickup -> in_transit -> completed`, including current cancellation and `on_hold`/`returning`/`returned` branches. Internal booking/assignment sub-states such as searching, driver-en-route and arrived are an additive server model mapped to these existing API statuses; never silently rename stored values or reset an order. Every transition records actor, role, prior status, expected version, guard, reason, server timestamp and idempotent command ID. Payment state stays orthogonal. ([Current statuses and custody](<C:/Users/osama/OneDrive/Documents/ChatGPT/Fastship/src/model.ts:21>), [advance transaction](<C:/Users/osama/OneDrive/Documents/ChatGPT/Fastship/server/main.ts:1638>))

Server-confirmed arrival requires plausible recent proximity or a named audited poor-GPS exception. Standard ride start requires the matched driver and a hashed four-digit rider PIN, with five attempts per challenge and operator-audited recovery; do not expose that PIN in driver prearrival payload or logs. Completion requires allowed status and final fare/evidence settlement proposal. Early end after a ride starts is a safety/early-end command, not a rollback to searching. Completed/returned orders never reactivate. A driver cancel before pickup creates a new assignment epoch and can redispatch the same order; an onboard passenger transfer requires support handling and renewed consent. Preserve existing safety holds and exception decisions during migration and replay.

## D13 — Pickup, waiting, cancellation and no-show

Waiting clock starts from server-confirmed arrival with trustworthy recent proximity and optionally customer notification acknowledgment. Pause/dispute clock for stale GPS or incorrect pickup. Versioned city/product policy defines grace period, per-minute waiting, maximum, customer cancellation reason waivers, driver no-show evidence and fee cap. At pilot launch retain existing configured fares and whole-ILS payable rounding, record a 5-minute arrival grace period for alerts and add no new waiting/cancellation/no-show fee; never copy Uber's US/UK numeric rules into Palestine. Cancellation decision function returns `{allowed, feeMinor, payeeAllocation, refund/preauthAction, reasonCode, evidenceRefs, policyVersion}`. Avoid charging both cancellation and an overlapping wait charge unless policy explicitly justifies distinct time. Test simultaneous cancellation/acceptance, no-show with remote driver, driver not moving toward pickup, wrong entrance, already closed route and customer accessibility delay exception.

## D14 — Parcel chain of custody, proof and returns

Keep the existing order ID and lifecycle: `searching -> assigned -> at_pickup -> in_transit -> completed`, with `on_hold -> in_transit` for approved reattempt or `on_hold -> returning -> returned` for a sender return. `on_hold` and `returning` retain the driver's custody/assignment. Preserve the existing sender-only return code (`return_code` / API `returnCode`), sender handoff/PIN check, proof, security events, completed timestamp and cash/commission semantics. A richer internal stop/leg entity attaches to that same order; it must not turn a currently returning parcel into a new searching booking, reset custody or charge twice. Existing return codes and events survive migration. ([Custody statuses](<C:/Users/osama/OneDrive/Documents/ChatGPT/Fastship/src/model.ts:41>), [sender-only code](<C:/Users/osama/OneDrive/Documents/ChatGPT/Fastship/server/main.ts:432>), [return decisions](<C:/Users/osama/OneDrive/Documents/ChatGPT/Fastship/server/main.ts:1699>), [finished-order settlement](<C:/Users/osama/OneDrive/Documents/ChatGPT/Fastship/server/main.ts:1993>))

Add per-item barcode/pieces and policy-selected handoff verification without removing the working code flow. Every custody transfer records parties, time, location and evidence. The initial proof contract is the existing handoff/return PIN plus an item-count acknowledgment; photo/signature capture remains disabled until its private upload and consent policy is implemented as a separate release. A PIN confirms recipient knowledge; neither PIN nor a photo alone proves contents/condition. Future evidence uses restricted short-lived upload authorization, limits, checksum/type scanning and private object access. Completion references valid evidence IDs; missing or replayed proof fails server-side. Recipient-contact timeout, reattempt, authorized leave-at-location and return responsibility are recorded before custody. Return-leg costing and cash liability attach to the original immutable custody history. Test sender PIN privacy, code migration, return confirmation duplication, custody cancellation, partial item mismatch, failed reattempt, lost/damaged item and return cash reconciliation.

## D15 — COD, customer cash and driver settlement

Track transportation fee, goods COD principal, tip, tax and commission as distinct liabilities. Example: driver collects 120 (100 merchant goods, 20 delivery); delivery driver pay 15 and platform revenue 5. Operational ledger records 120 cash held/receivable from driver, 100 payable to merchant, 15 payable to driver and 5 earned platform fee under approved accounting policy; the 100 goods principal is never platform revenue. Net settlement may reduce driver payable against cash owed only with explicit policy and auditable journal. Customer cash handoff has amount due, amount collected, collector and receipt; partial collection/change/recipient refusal needs a case, never fabricate success. Apply the fixed v1 unsettled exposure cap of 100,000 minor ILS using actual liability; review settlement daily and block only new cash work at the cap, preserving active jobs and unrelated noncash eligibility; pause new COD when exceeded without losing active jobs. Reconciliation compares booking completion, cash receipts, collector deposits, bank/PSP records and ledger daily. Settlement adjustments create reversing journals instead of editing history. Test transport cash only, prepaid transport + COD goods, partial cash, counterfeit dispute, return with collected funds and duplicate deposit confirmation.

## D16 — Digital payments, refunds, ledger and payouts

Use a locally supported licensed PSP selected after country/currency/payout validation; do not assume Stripe/Connect availability. Client uses tokenized hosted/mobile payment collection; server creates intent, confirms provider status via signed webhook or authoritative lookup. Payment states: created -> authorization_pending -> authorized -> capture_pending -> captured; parallel void/refund/dispute states with amounts and provider IDs. Trip completion and payment collection are different facts: failed capture creates recoverable debt/support, not a fake incomplete physical ride. Persist every provider request with idempotency key and reconcile uncertain timeout before retry. Verify webhook signature over raw body, deduplicate provider event ID, apply allowed monotonic business transitions and fetch authoritative resource for out-of-order ambiguity. Use integer minor currency units, immutable balanced journals (`sum debit = sum credit` by currency), unique business references and no manual balance edits. Refund <= captured minus previous refunds; tip never counted twice; payout <= available settled driver earnings after applicable holds. Payout states initiated/processing/succeeded/failed/reversed reconcile to provider/bank; a retry cannot pay twice. Gate new payment methods behind sandbox + small real-money reconciliation, not successful happy-path UI.

## D17 — Realtime, command synchronization and reconnect

Standard command envelope `{commandId, expectedVersion, clientRecordedAt, payload}`; standard event `{eventId, aggregateId, aggregateVersion, type, occurredAt, correlationId, schemaVersion, payload}`. Mutation first commits authoritative state and outbox in one DB transaction; worker publishes events with at-least-once delivery. Consumers inbox-deduplicate. Use event type-specific ACLs so only booking participants and authorized staff subscribe; location sharing expires when job/access ends. Clients maintain last seen version/cursor; ignore duplicate/older event, buffer small gaps, fetch full snapshot when gap persists, rebuild after reconnect. Push notification cannot be trusted as current state and cannot itself accept/start/complete a job. Expose stable `GET /bookings/{id}` snapshot plus timeline; active UI always reconciles from server. Background/terminated app receives permitted push hints; on resume fetch reality before showing actionable controls. Test lost/duplicated/out-of-order events, reconnect after assignment/cancel, app reinstall and queue replay after session revocation.

Snapshots/events must carry `assignmentEpoch`, `itineraryRevision`, `quoteRevision`, `routeRevision` and `restrictionVersion` where relevant. A route computed for an old destination cannot replace a newer route; a previous driver's location cannot appear after reassignment; an old price event cannot overwrite an accepted change order. Cache/provider responses are checked against their input revision before write-back. Money commands additionally bind an exact quote/settlement amount and currency. Add tests with intentionally reordered route/quote computations and assignment changes, not only reordered websocket messages.

## D18 — Communication and tracking links

Authorize chat per current booking and retain according to documented purpose/retention; rate-limit content, block/report, moderate attachments and never expose customer phone to every marketplace driver. Separate public listing from participant private details. Prefer masked call/relay where provider supports Palestine; otherwise explicitly consent to limited direct number disclosure and scope it to the assignment. Tracking links use high-entropy revocable time-bound tokens; recipients see only necessary job status/approximate position and vehicle facts. Never use sequential booking ID as secret. After completion/revocation token loses live location access. Test guessed IDs, former assigned driver, blocked user, customer phone change and copied expired link.

## D19 — Safety and risk operations

Emergency/help action should surface current location, trip/vehicle details, trusted contact sharing and local supported contact routes, with accurate availability. Do not promise automated police dispatch or 24/7 human response without the staffed integration. Rule-based operational alerts initially: prolonged unexpected stop, stale tracking, significant route deviation and unresolved handoff; thresholds calibrated per checkpoint context to avoid false alarms. Alert -> ask both parties privately -> provide help -> escalate by staffed policy -> document resolution. A deviation signal is not proof of danger/fraud. Keep access scoped and audited, allow false-positive dismissal, and never let LLM-generated safety judgment cancel transport autonomously. Financial risk signals include repeated OTP abuse, impossible GPS movement, suspicious same-party transfers, excessive promo reuse, fabricated proof and repeated cash shortages; route to review with explanation and appeals. Avoid automatic suspension from sparse/noisy data.

## D20 — Ratings, blocks, complaints and disputes

Preserve the existing finished-order set `{completed, returned}` for history, trips/statistics, disputes and cash settlement. The current rate endpoint permits only `completed`; v1 preserves that eligibility for customer, driver and price ratings. `returned` remains finished for history/statistics/disputes/cash. ## D30 — Dispatch pseudocode and database acceptance criteria

```text
on booking_requested(id):
  if booking.state != searching: return
  candidates = eligible_fresh_drivers(booking.product, booking.region)
  pairs = route_feasible_candidates(candidates, booking.pickup, restriction_version)
  ranked = stable_sort(pairs, cost, driver_id)
  issue_durable_offer(next_non_cooldown(ranked), ttl, booking_revision)

accept_offer(command):
  begin transaction
  if idempotency_record(command.id) exists: return original_result
  lock booking, driver_session, offer in deterministic order
  assert role/ownership, live offer, server_now < expires_at
  assert booking.revision == offer.booking_revision and booking is searching
  assert driver_session is eligible_now and fits exclusive_or_courier_capacity_policy
  reserve product resources; insert assignment with unique active_booking and exclusive_driver constraint for rides/freight
  mark offer accepted; revoke competing offers; transition booking and driver_session
  append audit/event and transactional outbox; record command result
  commit
```

Acceptance tests must run with two server processes/database connections, not just two promise calls against an in-memory mutex: 100 concurrent accepts across drivers -> exactly one booking assignment; one exclusive ride/freight driver accepting two bookings -> one success; concurrent courier acceptances -> all accepted items fit the locked capacity vector; timeout and accept at same instant -> one valid transition; worker restart between DB commit and publish -> event eventually delivered with no duplicated assignment; cancellation during offer -> no valid late accept; idempotency key reused with altered payload -> conflict. Lease uniqueness must survive database migration and rollback.
